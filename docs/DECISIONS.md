# Decisions

Newest at the bottom. Each entry gives the choice, what was rejected, and why.

## D-001 — Public repository (2026-11-20, John)
Oculus is developed in a public GitHub repository. Nothing private goes in it: no secrets, no private data about real people, and no code from John's private repositories (see D-002).

## D-002 — MIT license; permissive dependencies only (2026-11-20, John)
The code is MIT-licensed, so any archive, museum or historical society can use it. Dependencies must be MIT, BSD, ISC, Apache-2.0 or similarly permissive. GPL, AGPL and LGPL are not allowed, because they would change the terms for anyone installing Oculus. Code from John's private repositories (Polybius, Blueprint and others) may be brought in only by an entry here written by John.

## D-003 — Built by autopilot, no human approval (2026-11-20, John)
Three scheduled sessions each night (build, upkeep, security) do one task each, check it against the gate, and merge to `main` themselves. This is the same model as John's Blueprint, Argus and FerroJS projects. John can switch to pull requests he approves by changing step j of AUTOPILOT.md and recording it here.

## D-004 — No AI inside the product (carried over from the Polybius project)
Oculus contains no hosted AI, no AI SDKs and no pretrained models. Suggestion features use classical retrieval: BM25 plus a curated synonym list. One exception: OCR may use an engine's trained text-recognition models (D-033).

## D-005 — Platform name and parts (2026-11-20, John)
The platform is **Oculus**. Its staff back end is called **Polybius** and its public sites are called **Hermes**. These are names for parts of one product, not separate products. **Superseded by D-018.**

## D-006 — Toolchain, Node version and the license allowlist (2026-11-20, autopilot T-001)
npm workspaces (`packages/*`), TypeScript 6.0 in strict mode (plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`), ESLint 10 with typescript-eslint's strict type-checked rules, Prettier 3 and Vitest 5. `.nvmrc` is Node 26, the Active LTS line ("Lithium", LTS from October 2026, supported to April 2029); `engines` allows Node 22 and later, because the build sandbox runs 22. ## D-007 — Record kinds and the arrangement levels (2026-11-20, autopilot T-002)
Six record kinds: object, archival unit, digital asset, agent, place and event. An archival unit has a `level` (fonds, series, collection, file or item) and an optional `parentId`.
- **The levels follow how Polybius works today:** Fonds (whose records) › Series (what kind of records) › Collection (the group items are filed in, by topic or how the creator kept them) › File › Item. A unit can be filed under any higher level, so levels can be skipped: a collection can sit straight in a fonds, and an item straight in a collection. That keeps collections and series independent (PLATFORM_PLAN.md §1). Series and files can contain more of their own level (sub-series, sub-files), so the tree goes as deep as needed, up to a safety limit of 64.
- **A unit with no parent is allowed.** It's either a top-level fonds or collection, or something not filed yet (the "Needs Sorting" list).
- **Rejected: ISAD(G)'s level list as-is** (fonds, subfonds, series, subseries, file, item). It has no "collection" level between series and file, which is where Polybius files items today. Subfonds can be added later as a level if an organization needs it.
- **Rejected: collections as a separate many-to-many grouping outside the tree.** That would mean two ways to file the same item, which is harder to explain to volunteers and to show in a finding aid. A topical grouping that cuts across the tree can come later, as exhibits or tags.
- **Validation is strict.** Unknown properties, untrimmed titles, control characters, non-JSON field values and the keys `__proto__`, `constructor` and `prototype` are all reported. Nothing is fixed silently.

## D-008 — How dates are stored, bounded and sorted (2026-11-20, autopilot T-003)
Dates are stored as EDTF text (Library of Congress EDTF, 2019; ISO 8601-2). `parseEdtf` derives everything else from that text, so nothing derived is stored as the truth.
- **Supported:** levels 0 and 1 in full, and from level 2: qualifiers on single parts, X digits anywhere, sub-year groupings 25–41 and sets. **Rejected:** exponential years and significant digits (geological and astronomical time, not collections). Each part takes one qualifier and a date takes one trailing qualifier; that is stricter than some readings of the level 2 grammar, and can be loosened later without breaking stored data.
- **Bounds hold every possible day, and can be wider.** `earliest`/`latest` are for search and filtering, so leaving out a real possibility is worse than being wide. Seasons 21–24 don't name a hemisphere, so they cover both; winter covers December of the year before to February of the year after. `~` and `?` don't widen bounds: inventing a "± N years" range would be making things up.
- **Sort key** is `year*10000 + month*100 + day` of the earliest day (latest when the start is open). It's an exact integer up to year 999,999,999 and orders BCE years correctly. Dates whose year starts with X get no sort key and sort last, rather than as year 0.
- **Free text is converted only when the reading is safe.** Two-way forms ("1900s", "6/5/1920", "1920-25", "1901-05", "c1920", a leading dash, "'50s") are flagged, not guessed. Where EDTF can't say all the text said ("late 1920s" → `192X`, centuries), the result keeps the original words as a note.
- **Rejected: an EDTF package from npm** (such as edtf.js). The parser is small enough to own and test here, and owning it keeps the bounds, sorting and flag-don't-guess rules exactly as above. It can be compared against edtf.js in tests later if useful.

## D-009 — Typed identifiers: safe formats, comparison keys, uniqueness and numbering (2026-11-20, autopilot T-004)
Each identifier type has a key, a label, an optional format, a uniqueness rule (`none`, `current` or `all_time`) and optional auto-numbering: `year` (`2026.015`) or `prefix` (`DHS-0001`). A record has current identifiers, exactly one of them primary, and former ones. Former identifiers are history: they are never checked against today's format and may name a type that has since been removed.
- **Formats are a small language of our own, not regexes.** `#` is a digit, `@` an ASCII letter, `*` either, `{n}`/`{n,m}` repeats, `\` escapes. A format compiles to at most 200 single-character slots, and matching tracks every reachable slot at once, so it never backtracks. *Rejected:* compiling admin-written regexes (ReDoS) and regex "safety" checkers (incomplete).
- **Values are stored exactly as typed and compared by a key.** The key applies NFKC, maps Cyrillic, Greek and Armenian letters that look Latin and all dashes to `-`, folds case, and removes spaces and invisible characters. It errs towards calling identifiers the same. `0`/`O` and `1`/`l` stay distinct. *Rejected:* changing stored values, and the full Unicode TR39 confusables table (large; not read, so nothing claims to follow it).
- **The next number is the highest in use + 1,** counting former values, so retired numbers are never reused and gaps are not filled. Numbers the type's format could never produce are ignored. The caller supplies the year.

## D-010 — Field templates: field definitions, value shapes and the checker hook (2026-11-20, autopilot T-005)
A template is untrusted data: `{ key, label, description?, appliesTo: RecordKind[], fields }`, checked by `validateTemplate`, and checked again inside `checkRecordAgainstTemplate`, which fails closed with `invalid_template`. Each field definition holds `key`, `label`, `help?`, `kind`, `required`, `repeatable`, `visibility` (`public` or `staff`), `inherited`, `standards?` (`{standard, element, uri?}`) and kind-specific `options`, `vocabularies`, `identifierTypes` or `maxLength`. The flags and `visibility` must always be stated, with no defaults, so a field can never become public by being left out.
- **Value shapes:** text (one trimmed line), long_text, date (EDTF, checked with `parseEdtf`), list (one option value; several choices means a repeatable list), controlled_term `{label, uri?, vocabulary?}`, identifier `{type, value}`, link `{url, label?}`, rights `{uri, note?}`, place `{label, uri?, recordId?}`. A repeatable field stores a non-empty list. An empty value is left out, never stored as null, "" or []. URLs must be http or https with no user name, password or backslash; this checks what is stored and is not a guard against server-side requests.
- **Kind-specific checks plug in** through `options.checkers[kind]`, a function `(value, field, record) => FieldProblem[]`. A checker that throws or returns something malformed makes the value fail.
- **Hardening:** optional settings are read as own properties only; template keys and codes refuse `constructor` and `prototype`. Limits: 200 fields, 500 options per list, 10,000 options per template.
- **Rejected:** defaults for `visibility` and the other flags (a missing value could make a field public by mistake); `link` as a link to another record (a separate relationship feature, since publishing it could reveal unpublished records); requiring a vocabulary on every term (T-009 decides that).

## D-011 — How rights are stored and the publish rule (2026-11-20, autopilot T-007)
A record's rights are one canonical URI in the `uri` of the template field `rights`, stored as `{ uri, note? }` (D-010, D-015). Accepted values are the 12 rightsstatements.org 1.0 statements, the six Creative Commons 4.0 International licenses, CC0 1.0 and the Public Domain Mark 1.0. Either a statement or a CC tool meets the rule that a record needs rights before it can be published.
- **The rule covers the kinds that hold copyrightable content:** object, archival unit and digital asset. Agent, place and event records can be published without rights. A record whose kind is missing or unknown is checked anyway.
- **What the check reads:** only own, enumerable data properties of the exact frozen record being published. Getters, hidden properties and Proxies are reported as unreadable.
- **Canonical forms are the ones each issuer publishes.** rightsstatements.org uses `http://`, the `/vocab/` path and a trailing slash (its technical requirements v1.2.2 say `/page/` URLs "MUST NOT be used" in metadata). Creative Commons uses `https://creativecommons.org/licenses/by/4.0/`.
- **Variants are fixed only through `normalizeRightsUri`, which lists every change** (http/https, `/page/`, trailing slash, `deed`/`legalcode` endings, `www.`, a query or fragment, spaces). Stored values that aren't canonical are refused with `not_canonical`.
- **Rejected for now:** CC versions 1.0 to 3.0 and national ports (reported as `unsupported_version`; the full list couldn't be confirmed and none is current; add them if the Omeka migration needs them); CC's "Certification 1.0 US" (not a current tool); several rights values per record (`edm:rights` takes one).

## D-012 — Standards presets and the Dublin Core mapping (2026-11-20, autopilot T-006)
Three frozen starting templates built with the D-010 model: `dacs-archival-unit`, `spectrum-object` and `dublin-core-digital-asset`. Fields cite their source in `standards`: DACS element number and name (SAA, second edition, saa-ts-dacs.github.io version 2022.0.4; no URIs, because none are stable), Spectrum 5.1 unit of information names (where only the information group was confirmed, for rights and valuation, the element says "(information group)"), and DCMI terms with `http://purl.org/dc/terms/` URIs, on public fields only. The record's own `title` is DACS 2.3, Spectrum Title and dcterms `title`, so it is not a template field.
- **Privacy defaults: staff, and the organization opts in.** Anything that can name a private person or is internal starts as `staff`: donor and acquisition details, custodial and object history, where originals and copies are, storage and current location, appraisal, valuation and insurance, other numbers, credit line, sources, rights holders, and notes (including DACS 7.1). Public on purpose: conditions governing access (researchers need it; the help text forbids personal or donor-confidential reasons), the repository's name and location, and `rights` (D-011).
- **The Dublin Core mapping is separate data,** `{ template, entries: [{ field, term }] }`. `validateDublinCoreMapping(mapping, template)` checks it every time it is used: the template must be valid, every field must exist and be `public` (otherwise `staff_field`), and terms come from a closed list of 31 confirmed DCMI terms. `mappingForTemplate` re-targets a preset's mapping to a copied template. Unmapped fields are not published as Dublin Core.
- Rejected: dcterms cites in `standards` as the publishing source (a field switched to staff would keep its cite, and two sources could disagree); publishing credit lines, custodial history or rights holders by default (they often name donors or private owners); citing DACS 8.2 for rights (8.2 covers rights in the description itself; 4.4 is cited).

## D-013 — The effective record: how inheritance, own values and visibility combine (2026-11-20, autopilot T-008)
`effectiveRecord(id, records | indexRecords(...), templateFor, { checkers? })` returns a frozen, staff-side result: `{ id, kind, title, fields, entries, chain, notes, record }`. Each entry gives the value, `own`, the record it came from and the effective `visibility`.
- **Public output only ever comes from `publicView(effective)`,** which keeps only entries that are public and in the template, with no notes, no stored record and no ancestors.
- **Rights are checked with `effectivePublishIssues`,** which refuses rights that aren't public here (since D-015 requires a public `rights` field, today only a left-over `rights` key), then runs `rightsPublishIssues` on the public view. `rightsPublishIssues` itself refuses an effective record (`use_effective_publish_issues`).
- **Own value wins entirely;** a repeatable field's own list replaces the inherited one. *Rejected:* merging lists (an item couldn't drop an inherited value).
- **An empty stored value means "none"** and blocks inheritance from that record up. *Rejected:* treating it as absent (a cleared value could be published from an ancestor).
- **Only the record's own template decides whether a field inherits.** Going up, a unit whose template lacks the key is passed over; one with `inherited: false` stops the search; the nearest stored value decides. Every definition on the way must have the same kind and `repeatable`, and the value must pass the record's own template check and the caller's checkers (which see a frozen record; exactly the checked value is kept).
- **Visibility is the strictest along the chain.** Left-over keys are `staff`, never inherited and never public.
- **Any doubt fails the whole result:** a missing parent, a duplicate or unreadable ID, an invalid record, a loop, the wrong level, more than 64 levels, a bad template, or options that aren't plain. *Rejected:* partial results.
- **Snapshots:** `indexRecords` validates every record when built, so an index is one consistent frozen snapshot and must be rebuilt after edits; templates are validated afresh on every call. *Rejected:* lazy validation and caching templates by object identity (a shared object changed between calls turned staff into public in review).
- Notes may quote values and labels, so they are staff only.

## D-014 — Controlled terms: vocabularies, URI rules and near-duplicate detection (2026-11-20, autopilot T-009)
Terms keep the D-010 shape `{label, uri?, vocabulary?}`. Six vocabulary codes: `lcsh`, `lcnaf`, `lcgft`, `nomenclature`, `gnis` and `local`; a template's `vocabularies` may list only these. A term with no vocabulary is local, and templates accept it wherever the field allows `local` or lists no vocabularies. Local terms can't have a URI; for the others a URI is optional (built LCSH headings often have no authority record). The rules run by default in `checkRecordAgainstTemplate` (`controlledTermChecker`).
- **LC URIs** must be exactly the form id.loc.gov publishes, `http://id.loc.gov/authorities/{subjects|names|genreForms}/{LCCN}`, with the control number checked against LC's "The LCCN Namespace". Variants are refused (`not_canonical`); only `normalizeTermUri` fixes them, listing every change.
- **Nomenclature and GNIS URIs** are stored as given, because neither issuer's URI form could be confirmed (their sites couldn't be reached). Nomenclature must be a page on nomenclature.info; GNIS must not be on an LC or Nomenclature host. `termUriKey` compares URIs loosely without changing what is stored.
- **Near-duplicates** use classical methods only (D-004): `same_uri`, `same_label`, `same_words`, `abbreviation` (including spaced initials) and `similar_spelling` (edit distance 1, or 2 for keys of 10+ letters). Designators (numbers, letter-digit tokens, single letters, Roman numerals) must match; accents are removed only from Latin, Greek and Cyrillic letters; invalid or over-long terms are skipped and listed; work is budgeted and every limit reached is listed in `limitsReached`. It reports pairs and never merges anything. 50,000 hostile terms run in under 2 seconds.
- **Rejected:** requiring URIs for LC terms; inferring the vocabulary from the URI; normalizing Nomenclature or GNIS URIs when stored; all-pairs comparison; failing the whole check on one bad term; stripping every Unicode mark (merges words in Indic scripts); free-form vocabulary codes; synonym matching (needs a thesaurus).

## D-015 — Default field checkers, the rights field, and identifier values need a checker (2026-11-20, autopilot T-007a)
`field-checkers.ts` holds the ready-made checkers. `checkRightsValue` (rights) and `controlledTermChecker` (D-014) run by default in `checkRecordAgainstTemplate`. `makeIdentifierChecker(types, organizationId)` validates the organization's identifier types once and returns a checker for the `identifier` kind.
- **A checker the caller gives replaces the default.** Leaving a kind out, giving `undefined`, or a checker on `Object.prototype` keeps the default, so a check can't be switched off by accident. To skip a check on purpose, pass `() => []`.
- **Identifier values without a checker are refused** with `unchecked`, never accepted. Uniqueness needs every record, so it stays with `checkNewIdentifier` and `uniquenessIssues` on the save path.
- **The stored rights value is `{ uri, note? }` in field `rights`.** The publish rule reads `fields.rights.uri` (own enumerable data properties only) and refuses a plain string, unknown properties and a bad note, so publishing doesn't depend on the template check having run.
- **The rights kind and the key `rights` go together:** at most one rights field per template, not repeatable, and always `public`.
- **Rights notes** (superseded by D-016: notes are not published and are left out of `publicView`). Keep them free of private details anyway.
- **Rejected:** an `identifierTypes` option on every check; letting identifier values pass unchecked; treating `undefined` as "off"; a bare URI string as the stored rights value; accepting both shapes; several or staff-only rights fields.

## D-016 — Public output: Dublin Core, JSON-LD and oai_dc (2026-11-20, autopilot T-010)
`publicOutput(view, mapping, { baseUrl, published, records, templateFor, checkers?, identifiers?, accessions? })` (`templateFor` added by D-020, `records` by D-021, both required since D-054, which also removed the original `currentTemplate?`) returns `{ id, dublinCore, jsonLd, jsonLdText, oaiDcXml }` or issues. It never throws.
- **Input is only a real `publicView` result,** recognised by a WeakMap mark `effective.ts` sets beside each view, never by its shape. Output is refused unless all of these pass: `effectivePublishIssues`; `validateDublinCoreMapping` against the view's template; for objects, archival units and digital assets, a mapping of `rights` to `rights` or `license` (`rights_not_mapped`); `checkRecordAgainstTemplate` on the view's values (default checkers plus the caller's, which replace the defaults); and that the records and templates now are the ones the view was built from (`record_changed`, `template_changed`; D-020, D-021, D-054). Views must be built at publish time.
- **Published records:** the caller lists published record IDs, and the record must be among them. A place's `recordId` becomes a link only if that record is listed; otherwise only its name goes out. Public values inherited from an unpublished ancestor may be published on a published child; the ancestor's title and ID never appear.
- **Values by kind:** text as text; a date as its EDTF text; a list choice as its option label (and, for a DCMI Type code under `type` on kinds with no type of their own, also `@type` and the DCMI Type URI); a controlled term or place as its label plus URI; an identifier as its value only; a link as its URL; rights as the URI only. URIs must be http(s), canonical (`new URL(v).href === v`), and contain no `<>"{}|\^`` or space, no bad `%` escape, and `[` `]` only around an IPv6 host.
- **Rights notes are not published,** and `publicView` leaves them out: a literal under `dcterms:rights` breaks its range. This supersedes D-015's "notes are public".
- **JSON-LD:** an inline context (`dcterms`, `dcmitype`, `rdfs`); `@id` is the base URL plus the record ID; `@type` by kind (PhysicalObject; Collection for archival units above item level; Event; `dcterms:Agent`; `dcterms:Location`). Each term is written by its DCMI range: literal-range terms get text; class-range terms get `{"@id"}` with a URI, otherwise `{"rdfs:label"}`; `type` gets a label node. `jsonLdText` is written by its own writer (no `JSON.stringify`), escapes `< > &` and U+2028/2029 for script elements, and is capped as it is written.
- **Dublin Core and oai_dc:** text only; `identifier` starts with the record URL and `type` with the DCMI Type URI; oai_dc writes refinements as their parent element and leaves out `rightsHolder` and `provenance`; characters outside XML 1.0 are refused; the caller encodes it as UTF-8.
- **Limits:** each form is capped at 5,000,000 characters as produced. Output objects have null prototypes.
- **Issues (added by S-007, 2026-11-23):** the issues `publicOutput` returns are for staff only: the admin shows them to whoever is publishing, and a public site, API or OAI-PMH response shows the record as not available without passing them on. Even so, their messages never quote a stored value, an identifier number or an identifier type key: the template check's issues (whose checkers' messages do, e.g. the identifier checker's `unknown_type` and `format_mismatch`) and the publish check's issues about a field (path starting with `fields`, e.g. a rights value quoted back) keep their code and path but get fixed text; the deed check's messages are fixed text already and are kept. Messages `publicOutput` writes itself name at most a field label, an option name or the base URL (configuration, not record data). *Rejected:* relying on staff-only alone (issues get logged and copied, and one careless public endpoint would show a number); dropping code and path too (staff need to know which field to fix).
- **Rejected:** `edm:rights` (Europeana-specific); choosing a type from `mediaType`; IRIs under literal terms (and, until D-042, under `dcterms:type`); linking unpublished records; a "simple dcterms" XML form (no schema).

## D-017 — EDTF qualifiers: two suffixes, and "?" after a free-text range (2026-11-21, autopilot T-003a)
Checked against the LoC EDTF specification (loc.gov/standards/datetime/edtf.html, 2019-02-04).
- **Two suffix qualifiers stay refused.** The spec's level 2 examples put at most one qualifier after the parts (`2004-06~-11`, `2004?-06-11`) and use prefixes for anything finer (`?2004-06-~11`, `2004-%06-11`). `2004?-06~-11` isn't among them, so D-008's strict reading stands. Since a suffix applies to its part and every part to its left, the error message gives the same meaning in prefixes (`%2004-~06-11`). Rejected: accepting it, which would let two spellings of one meaning into stored data. Loosening later won't break stored dates.
- **"?" after a free-text range is flagged, not guessed.** In EDTF a qualifier belongs to one interval end, but in free text "1920-1925?" can doubt the end year or the whole range. A qualifier in front ("probably 1920-1925", "ca. 1920-1925") still applies to both ends. A single date that reads as an interval ("19th century?") isn't a range and isn't flagged. Rejected: `?` on both ends (the old behaviour), which guessed.

## D-019 — One install, several organizations (2026-11-21, John)
One Oculus install can hold several organizations, each with its own catalog, ID number formats, rights settings, people and roles, and its own public site or sites. The case: the Dickinson Historical Society runs its own archives (IDs like `DS5C740001`) and also hosts the library on a separate site (IDs `DPL1`, `DPL2`, `DPL3` …). This replaces PLATFORM_PLAN.md decision 3 ("one organization with several public sites … not a hosted service for many organizations"). **Complete separation (John, same day):** treat each organization as if it were a completely separate copy of Oculus. Its records, templates, record types, ID number formats, vocabularies and terms, rights settings, people, roles, change log, files and public sites belong to it alone, and no search, report, API call or public page ever reads across. Staff choose which one they are working in from a switcher in the admin; a person who works for both (say a Society admin who also runs the library's site) has one sign-in with separate roles in each, and nothing they can do in one carries over to the other. Rejected: sharing templates, vocabularies or people lists between organizations, which would tie them together. **Also (John, same day):** the site selector sits in the sidebar under the Oculus name; a site can be password protected, so staff must enter its password before opening it even when they hold a role there; and there are **System settings** for the whole install (sites, who is a system admin and which sites each person can use, sign-in and security rules, password protection, email, backups and updates), separate from each site's own Site settings. **Users (John, same day):** system admins manage every user from one Users page covering all sites (invite, set a role per site or no access, make someone a system admin, reset passwords and two-step sign-in, deactivate). After signing in, a person sees only the sites they have a role on; with exactly one site they go straight to it. Site roles stay as T-041 defines them; a system admin can manage every site. How it's modelled is T-019.

## D-020 — Public output re-checks every template up the tree (2026-11-21, autopilot security S-001)
A public view now remembers each record on the way up with the template it was read with. `publicOutput` takes `templateFor` (the same lookup `effectiveRecord` takes) and asks it again for the record and every ancestor; any template that differs, is missing or invalid gives `template_changed`, and a lookup that throws gives `template_lookup_failed`. (At first `currentTemplate`, the record's own template alone, was also accepted, and refused for a record with parents as `ancestor_templates_unchecked`; D-054 removed it, since the required `templateFor` checks every template.)
- **Rejected:** a map of record ID → template (callers already have the lookup); checking only the ancestors a value came from (a parent's `inherited` or visibility change can matter even where no value came from it); making `templateFor` required (it would break every caller for views built and published in one step, which is the documented use). *Superseded by D-054:* `templateFor` is required and `currentTemplate` removed.
- **Not covered here:** the ancestry itself is the one the view was built with; the `records` option (D-021) checks it against the current records.

## D-021 — Public output can re-check the ancestry against the current records (2026-11-21, autopilot security S-001a)
Extends D-020. `publicOutput` takes an optional `records` (the current set: a list or a lookup from `indexRecords`, as `effectiveRecord` takes). When given, the record's ancestry is found again in it, the same way `effectiveRecord` finds it, and output is refused (`record_changed`, path `["records", <record ID>]`, never a title or value) unless it is the same records, in the same order, with the same stored content as the view was built from, compared as validated data with sorted keys. A record removed, a parent missing or invalid, a value changed or emptied, a move to another parent or a level change all refuse. `templateFor` is then asked with the current records. A `records` that isn't a list or an index is `invalid_options`.
- **Building the view at publish time stays the rule.** Only `records` and `templateFor` together catch every change to a kept view; either alone (and `currentTemplate`) is still allowed and catches only its own kind of change. *Superseded by D-054:* both are required for every view.
- **Rejected:** comparing only the fields a value came from (a parent's new value, emptied value or new parent changes what the child inherits even where nothing came from it before); making kept views expire (a time limit doesn't say whether anything changed); making `records` required (it would break every caller that builds and publishes in one step). *Superseded by D-054:* `records` is required.


## D-022 — Identifier types are staff only unless marked public (2026-11-21, autopilot security S-006)
An identifier type takes `public?: boolean`; left out or `false`, it is staff only. A donor file number in a public `identifier` field with no `identifierTypes` restriction used to be published as a bare value (D-016); now it can't be.
- **Refused at the template check.** The checker from `makeIdentifierChecker` reports `private_identifier_type` (at the value's `type`) for a staff type's value in any field that isn't `visibility: "staff"`, so the admin catches it when the record is saved and nothing private is published or quietly left out. Staff fields take any type. The flag is read as an own property, so a polluted `Object.prototype` can't make a type public.
- **The effective record and public view** (D-013). The identifier checker in `effectiveRecord`'s `checkers` says which types are public. Checkers judge an inherited value by its effective visibility, not the receiving field's: a staff-type number inherited as staff (staff anywhere along the way) stays in the effective record for staff. One inherited public-to-public is left out with a `not_valid_here` note, like any value that doesn't fit, not refused. A record's own value in a public field (own values aren't checked there) whose type, or any of whose types, isn't public is kept but marked `staff` with a `private_identifier_type` note. With no identifier checker from `makeIdentifierChecker`, every public identifier value is marked staff with `identifier_types_unknown` (fail closed). Either note makes `effectivePublishIssues` refuse publishing, so an own private number is never silently dropped. The public view holds an identifier as `{ value }` only, never its type (D-016 publishes only the value).
- **Checked again at the boundary.** `publicOutput` already runs the template check with the caller's checkers. It also asks the `identifier` checker for the public types it was made with (a WeakMap beside each checker `makeIdentifierChecker` made, never its shape), and refuses an identifier value whose type (read from the effective record, since the view has none) isn't among them (`private_identifier_type`). A hand-written identifier checker can't say which types are public, so with one, any identifier value refuses the output (`unchecked`). This narrows D-015's "pass `() => []` to skip a check" for identifier values in public output only.
- **Presets** don't define identifier types. Object numbers, accession numbers and call numbers, which the presets put in public fields, are usually published, so organizations should mark those types public; the tests' sample types do.
- **Rejected:** public by default (one forgotten flag publishes private numbers); leaving a record's own staff values out of output silently (a public field that drops values hides a cataloguing mistake); keeping `type` in the public view (nothing public needs it); a new `identifierTypes` option on `publicOutput` (a second copy of the types that could disagree with the checker's); per-field allow lists alone (`identifierTypes` on the field is optional, so the gap stays open by default). Unifying `RecordIdentifiers` and identifier fields is still T-014.


## D-023 — Template changes are compared before saving; making a field public needs confirmation (2026-11-21, autopilot security S-002, T-005a)
`templateChanges(oldTemplate, newTemplate, records?)` (template-changes.ts) validates both versions of one template (same `key`, else `different_template`) and every record given, and returns a frozen `{ changes, needsConfirmation, recordsChecked }`. Each change has a `code`, the field `key`, `needsConfirmation`, a message, and the IDs of the records holding a value for that key (`recordIds`, at most 10,000 listed, with the full `recordCount`). The codes:
- `made_public`: staff → public, or a new public field whose key records still hold left-over values for (left-overs are staff, D-013). **Always needs confirmation; the caller must get a person's confirmation before saving a template with a `made_public` change** (T-047 shows it).
- **Without records, every new field is reported:** a new public field as `made_public` and every new field as `key_reused`, both needing confirmation, since its key may hold left-overs nobody can see.
- `kind_added`: `appliesTo` gains a record kind. It is reported whatever the count, because the caller's records usually can't include that kind yet (they used another template); `recordIds` lists any given. Records of that kind may hold values, including staff ones from their old template, under keys this template publishes, so it needs confirmation whenever the template has a public field.
- `key_reused`: a new field takes a key records hold left-over values for. `key_removed`: the values stay as left-overs; removing an inherited field always needs confirmation. `kind_changed`; `repeatable_changed` (true → false also lists `recordsWithSeveralValues`); `option_removed` (with `option`); `max_length_lowered`, `vocabulary_removed` and `identifier_type_removed` (with `removedCodes`; a term with no vocabulary counts as `local`), listing the records holding a value the new field refuses; `made_required`, listing the records without a value. These need confirmation when records are affected, or when no records were given.
- `record_kind_removed` (T-015a, see D-055): a `record_link` field's `recordKinds` narrows (`removedCodes` names the kinds dropped). With `options.linkChecker` (the organization's `makeRecordLinkChecker`), `recordIds` are the records linking to a kind no longer allowed; without it, every record holding a link under the key. Another organization's checker or any other function refuses the comparison.
- `inherited_changed` needs confirmation when a field starts being inherited; stopping is informational, as is `made_staff`.
- **Descendants on other templates are not in `recordIds`.** Making a field inherited or removing an inherited field changes what lower levels receive, and can lift the strictest-visibility-along-the-way restriction of D-013 for descendants using other templates; this function sees only the records given, so those changes always need confirmation instead.
- **Left-over keys are found only through the records**, so a caller saving a template must pass the records that use it; without them `recordsChecked` is false. **An empty list means "these are all the records" (there are none)**: a caller must pass nothing, never `[]`, when it doesn't know them.
- **Messages name keys and counts only**, never a stored value. Any invalid record, duplicate ID, Proxy or getter refuses the whole comparison: an unreadable record could hide a staff value. Work is linear in records × changed keys.
- **Rejected:** refusing key reuse outright (an admin may legitimately bring a field back; reporting it with the records is enough, and refusing would need a history of removed keys the template doesn't keep); confirming `made_public` only when records hold values (records not given, or added before the save, would slip through).
- **Not covered:** identifier type edits (T-005a's second part) and aligning `identifierTypes` codes with identifier type keys stay open; renaming a key is seen as `key_removed` plus a new field. A record moving to another template through the caller's `templateFor` lookup (records don't name their template yet, T-012) can turn its staff values public without any template change; this function doesn't see that.


## D-024 — Identifier keys split accents before mapping lookalikes; blank characters (2026-11-21, autopilot security S-003)
`identifierKey` (D-009) now removes spaces, invisible and blank characters first (so none can sit between a letter and its accent), applies NFKC then NFD, maps lookalike *base* letters, folds case and recomposes with NFKC. Precomposed Cyrillic and Greek letters such as `Ӧ`, `Ӓ`, `Ӑ`, `Ά`, `έ`, `ό` (which NFKC keeps whole) now meet their Latin twins `Ö`, `Ä`, `Ă`, `Á`, `é`, `ó`; the Greek tonos and the Latin acute are one mark after NFD. The mark is kept, so `Ӧ` meets `Ö` but not `O`, and `Č` and `C` stay different as before. Visible characters that draw nothing (U+2800 Braille blank, U+16FE4, U+1D159; `BLANK_CHARACTERS`) are dropped from the key like spaces, and refused in identifier values, prefixes and formats (`invisible_characters` / `bad_characters`) like invisible characters. The Hangul fillers were already both, being default-ignorable. The table also gains lookalikes with no Latin decomposition (`Ү`, `Ӕ`, `Ә`, `Ө`, `Ѵ`, `Ҫ`, `Ϳ` and their small forms); the Greek perispomeni (`ᾶ`) maps to a tilde, since most fonts draw it as one; the Ogham space mark, a space to `\s` but drawn as a dash, becomes `-`.
- **Cost:** normalization sorts each run of combining marks in quadratic time. The key first removes spaces and invisibles and decomposes (NFKD one character at a time, which needs no sorting; whole-text NFKD is unsafe because non-marks such as `ﾞ` decompose into marks), then measures runs of marks. Text with a run of more than 8 marks (`MAX_MARK_RUN`) gets a key with its marks sorted by code point instead of normalized, behind a U+FEFF marker. The path depends only on the decomposed runs, so canonically equivalent spellings (`Ö`+marks, `O`+diaeresis+marks, reordered marks) always take the same path and meet; the key is linear at any length. Identifier values, auto-number prefixes and formats with such a run are refused (`too_many_marks`; `bad_characters` for formats), so only queries and old data take that path.
- **Rejected:** listing every precomposed lookalike in the table (hundreds of entries, easy to miss one); treating blanks only as spaces (a value made of nothing but Braille blanks would pass the empty check) or only refusing them (values imported before the check still need to clash); a new issue code (the existing one says the same thing to the person); deciding the path on the raw text or its length (a second review showed equivalent spellings could then get different keys); a higher mark limit (no identifier needs more than two or three marks on a letter).
- **Stored format:** no comparison keys are stored yet. Once T-026 stores each value's `identifierKey` beside it, any change to the key is a migration: recompute every stored key and re-run the uniqueness check, because values that were different can become the same and the unique index would refuse them.

## D-025 — System managers and site managers (2026-11-21, John)
Two levels of management, refining D-019's system admins and site roles:
- **System managers** can do everything, across the whole install. They sign in, create and set up the sites, install plugins and themes, manage every user and which sites each person can use, and run System settings.
- **Site managers** manage only the sites assigned to them, one or more. On those sites they have full control (content, catalog, Design, Site settings and the site's people and roles), and they choose among the plugins and themes a system manager has installed. They can't install anything, create sites, or see or change sites they aren't assigned to.
- **Site managers can change anything on their sites (John, same day):** every part of the site's design, including the installed theme they picked (colours, fonts, layouts, headers, footers, templates). Theme updates must not overwrite a site's own changes, so a site's changes are stored separately from the theme.
- Site roles below a site manager (cataloger, reviewer, read-only, Scanner, Donor relations, and custom roles made by system managers, D-036) are granted per site, as T-041 defines them.
- **Plugins** are new to the plan. What a plugin may do and how it is checked before install (it runs code on the server) is undecided and gets its own decision task before any plugin system is built (P-001).

## D-026 — Show or hide each field on a site's record pages (2026-11-21, John)
System managers and site managers decide which record fields a site's record pages show, with a show/hide toggle for each field of each template.

A staff field can't be shown by switching it on: making a field public stays a template change, with the confirmation D-023 requires. So the toggle is a display setting, not part of the publish boundary.
- **Hidden means not sent.** A hidden field is left out of that site's pages entirely, including the page's embedded JSON-LD, not just hidden by CSS, so it isn't in the page source either.
- **Per site.** One organization's sites can show different fields of the same records. Feeds for the whole organization (OAI-PMH) follow the Dublin Core mapping, not a site's toggles.
- **Rejected:** using the toggle as the public/staff switch (it would let a display setting publish staff data without D-023's confirmation); hiding fields only in the browser.

## D-027 — The check before publishing: serious problems block, minor ones warn (2026-11-21, John)
Publishing a site change runs a check first. Problems that break the WCAG 2.1 AA requirement (plan §5) block publishing until fixed: text that is too low in contrast to read, images with no alt text, controls with no accessible name, and click targets under 44 × 44 px (DESIGN.md §4). Minor problems only warn, and the editor can publish anyway: links that may be broken, and similar issues that can't be confirmed automatically. ## D-029 — Records name their template; no version pin; a template registry (2026-11-21, autopilot T-012)
A record stores `templateKey?: string`, the key of the template it follows, checked with the same rule as a template's `key` (`isTemplateKey`: 1 to 64 of `a-z 0-9 _ -`, starting with a letter, never `constructor`, `prototype` or `__proto__`; `invalid_template_key`). The checks find the template from the record, and **a record is never checked against a template with another key**: `checkRecordAgainstTemplate`, `effectiveRecord` and `publicOutput` refuse it (`template_mismatch`, naming keys only). This closes the S-002 review's leak, where a lookup that put a record under another template (a bug, a stale cache, a record "moved" without anything in it saying so) had its staff values checked and published under a key the other template makes public.
- **A template registry.** `indexTemplates(list)` validates an organization's templates once and indexes them by their own `key` into a frozen, opaque `TemplateRegistry` (recognised by a WeakMap, never by shape), for `checkRecordAgainstTemplate` (in place of the template), `effectiveRecord` and `publicOutput`'s `templateFor`. It is a snapshot like `indexRecords`: rebuild it after a template edit. Any invalid template, a hole, getter or Proxy, or two templates with one key refuses the whole list (`duplicate_key`); at most `MAX_REGISTRY_TEMPLATES` (1,000). Through a registry, a record with no key is `no_template_key` and a key it doesn't hold is `unknown_template`. *Rejected:* a `templatesByKey` object map (its keys could disagree with the templates' own `key`, and an object invites prototype keys); caching by object identity (D-013's reason still holds; the registry holds its own validated copies).
- **The lookup function still works** (`TemplateLookup`; `TemplateSource` is either). Its answer must have the record's `templateKey`, when the record has one, so the function can no longer choose a template for a keyed record, only fail to find it. A Proxy function is now refused by `effectiveRecord` too (`no_template_lookup`), as `publicOutput` already did.
- **"No key" means no own `templateKey` property at all.** An own property that is undefined, a getter or not a valid key is refused (`invalid_template_key`), never read as a keyless record, and `checkRecordAgainstTemplate` now validates the record first (`invalid_record`), so a hand-made record can't pass as an old one.
- **`templateChanges` checks the records belong to the template:** a record naming another template refuses the whole comparison (`record_not_for_template`), so it is never listed in this template's confirmation; keyless records are allowed and counted in `legacyRecords`, since nothing confirms which template they use.
- **Records without a key** (stored before this) still validate, and can be checked only through a template given directly or a lookup function, as before; a registry refuses them. They keep the old risk, so T-025 stores `template_key` as NOT NULL with a foreign key to the templates table and a migration fills it; once no keyless records remain, the function lookup and the optional key can go. `createRecord` takes `templateKey`; it is optional in the type only so existing callers keep working. *Rejected:* refusing keyless records outright (every stored record and caller would break at once, before the database exists to migrate them).
- **No version pin.** A record names a template key, not a version: every record follows the current version of its template. Reasons: making a field staff (often the fix for a leak) must apply to every record at once, not wait for each pinned record to be moved; public output re-checks the current templates (D-020, D-021), which a pin would turn into re-checking an old version nobody edits; and D-023 already makes every change that could publish something confirmed against the records that use the template, which a record's key now names exactly. The database (T-025) keeps template versions for the change log and for restoring, not for records to follow. *Rejected:* pinning `templateVersion` on each record (two records of one template could publish one key differently, and old versions would have to stay live and checkable forever).
- **Moving a record to another template is a record edit:** its stored `templateKey` changes, so a kept public view of it is refused by `publicOutput`'s `records` option (`record_changed`, D-021). Comparing the two templates for such a move (what becomes public, which values become left-overs), as `templateChanges` does for a template edit, is not done yet.

## D-030 — Organizations in the core model: an `organizationId` on everything, and mixed sets are refused (2026-11-21, autopilot T-019)
How D-019's complete separation is modelled in `packages/core`, before there is a database.
- **Organizations and sites.** `organizations.ts` adds `Organization` (`id`, `name`) and `Site` (`id`, `organizationId`, `name`), with `validateOrganization` and `validateSite(site, organizations)`; a site must belong to one of the install's organizations (`unknown_organization`). Both IDs are random version 4 UUIDs, branded `OrganizationId` and `SiteId` so code can't pass one for the other or for a `RecordId`, and never change; names can (one line, trimmed, at most 200 characters). Site passwords (D-019) are not modelled yet: how they are stored and rate-limited needs the security review.
- **Everything an organization owns carries a required `organizationId`** in its stored value, as each database row will carry an `organization_id` column (T-025 onward). Done in this run: catalog records (`validateRecord` refuses a record without one, `invalid_organization`; `createRecord` takes it), identifier types and a record's identifiers (`RecordIdentifiers`). Templates and record types, vocabularies and terms, and rights settings follow the same rule in follow-up tasks (T-019a, T-019b). Presets stay organization-free: they are starting points that an organization copies into its own template. An `organizationId` never changes; moving a record between organizations is a copy, not an edit.
- **A set that mixes organizations is refused, never filtered.** An entry whose `organizationId` is missing, not an organization ID or behind a getter counts as another organization's, at any position (an organization-less set could be any organization's). `templateChanges`'s `records`, `validateArrangement` and `unfiledUnits` refuse mixed sets too, and so do `findByIdentifier` and `findIdentifierConflicts`; those two and `unfiledUnits` now return a `Validated` list instead of a bare array, since an empty list would look like "nothing found" (the least breaking shape that can refuse: callers read `.value` when `.ok`). `indexRecords` counts every entry's readable `organizationId`, valid record or not. `indexRecords` and `effectiveRecord` (and so `publicOutput`'s `records` option) refuse a set holding records of more than one organization; `uniquenessIssues`, `checkNewIdentifier`, `nextIdentifier` and `validateRecordIdentifiers` refuse record identifiers and types of more than one organization; `validateIdentifierTypes` refuses one list holding two organizations' types. All with the code `mixed_organizations`, and none of them quote the other organization's values. So an item can't inherit from another organization's fonds, a number is unique only within its own organization (the Society's archives and the library can both hold `DPL1`, D-019), the check for a free number never reveals what another organization holds, and auto-numbering never counts another organization's numbers.
- **Checked inputs are copied once.** The identifier set functions copy their `RecordIdentifiers` list into a plain, frozen snapshot (Proxies and getters refused, `not_a_list` / `invalid_identifiers`) and validate the types before the organization check, then work on the snapshot only, so a list that reads differently the second time can't pass the check with one set and be searched with another. `indexRecords` refuses an entry whose `organizationId` is missing, invalid or behind a getter rather than keeping it as "invalid".
- **Every caller's list is read once.** `validateArrangement` and `unfiledUnits` read their units into frozen shallow copies first (Proxies, non-arrays and getters refused: `not_a_list`, `unreadable_entry`), and `validateRecordIdentifiers` validates its types once with `validateIdentifierTypes` and uses that copy for both the organization check and the format checks. No function checks one read of a caller's list and works on another.
- **Identifier checkers belong to an organization.** `makeIdentifierChecker` remembers the organization of its (single-organization) types (amended by S-009b: it is told the organization, `makeIdentifierChecker(types, organizationId)`, and `validateIdentifierTypes(types, organizationId)` refuses any entry not of that organization with `mixed_organizations` alone before anything about the list is read, so another organization's list, even one wholly theirs, gets no message naming a key; a checker made with no types still belongs to its organization). This narrows the "rejected: a per-call `organizationId` argument" below for these two: the argument is what the caller expects, checked before the data is read, not a second copy of the data's own organization. Its checker refuses every value of a record of another organization (`wrong_organization_checker`); `effectiveRecord` keeps such public identifier values staff with that note, which blocks publishing; `publicOutput` refuses a checker of another organization outright. Otherwise one organization's `public` type could publish another's staff number with the same key.
- **Templates (T-019a).** `FieldTemplate` has a required `organizationId`, checked by `validateTemplate` and `validateLegacyTemplate` (`invalid_organization`; a stored template without one is no longer readable, which is safe while nothing is stored). `templateOfRecord`, which the record check, `effectiveRecord` (lookup function or registry, for the record and every ancestor) and `publicOutput` all go through, refuses a template of another organization than the record's (`wrong_organization`, naming only the template key). `indexTemplates` and `legacyTemplateIssues` refuse a list naming two organizations; `templateChanges` refuses two organizations' templates and records of another organization; `identifierTypeChanges` and `identifierTypeDeletion` refuse another organization's templates. `publicOutput`'s `currentTemplate` (removed by D-054; `templateFor` compares the same way) is compared with the view's template including `organizationId`, so another organization's copy gives `template_changed`. Presets are now `TemplatePreset` (a template without `organizationId`, a breaking type change) and no longer pass `validateTemplate`; `templateFromPreset(preset, organizationId)` makes an organization's validated copy and refuses anything that already names an organization, as a guard against mistakes rather than a security boundary. Dublin Core mapping checks read a template's fields only (`validateTemplateShape`, internal), so a mapping can still be checked against a preset; mappings themselves carry no organization yet (T-019b). Record types follow when T-013 adds them.
- **Where the session's organization comes in.** A session works in exactly one organization (D-019). The service layer (T-032) loads only that organization's rows and checks the result's `organizationId` against the session; roles (D-025, T-041) will be granted per organization and per site, keyed by `(personId, organizationId)` and `(personId, siteId)`, with system managers outside any one organization. The checks here are the second line, so a query that forgets its organization filter fails loudly instead of reading across.
- **Events (D-028)** will attach as records of their organization like any other. Importing one from another site makes a new event owned by the importing organization, with a note of the site it came from; the import reads only a published event and copies it, so no set ever holds both organizations' records and nothing here needs an exception.
- **Rejected:** an organization-scoped container or registry passed to every function instead of a field on the data (the data itself couldn't show it was loaded from the wrong organization, and the container is a second source of truth that can disagree with the rows); an optional `organizationId` (a missing one would silently match any organization); putting the organization in the record ID (record IDs are permanent random UUIDs, `record-id.ts`, and an organization's records would be guessable by prefix); silently leaving out records of another organization (a filtered result looks complete when it isn't and hides the bug that mixed the set); a per-call `organizationId` argument checked against the data (the same check the service makes against the session, done twice with two values that could disagree).
## D-031 — Identifier type changes are checked before saving; one key rule for identifier types (2026-11-21, autopilot T-005a)
`identifierTypeChanges(oldType, newType, existing?)` and `identifierTypeDeletion(type, existing?)` (identifier-type-changes.ts) are the identifier type half of D-023. They return the same frozen `{ changes, needsConfirmation, recordsChecked }`; each change has a `code`, the old type key, `needsConfirmation`, a message naming the key and counts only, and `recordIds` (at most `MAX_LISTED_RECORDS`, with the full `recordCount`). The codes:
- `key_changed` and `type_deleted`: every stored value keeps the old key, so current ones stop passing the check and former ones stop counting for uniqueness and auto-numbering (their numbers could be given out again). `recordIds` are the records holding any value of the type: current, former, or in a template `identifier` field. A new key another type already has is refused (`key_taken`).
- `key_adopts_values`: a rename onto a key, or a new type (`identifierTypeCreation`), takes over values already stored under that key from a deleted type, which were staff. It lists those records, with `misfitRecordIds` (off the type's format) and `clashRecordIds` (clashing under its uniqueness rule, counting the renamed type's own values), and always needs confirmation; a public type also reports them as `made_public`. Without this, renaming a public type onto a deleted staff type's key would publish its left-over values silently.
- `templates_reference_type`: on a rename or deletion, the templates in `existing.templates` whose `identifierTypes` name the old key (`templateKeys`); needs confirmation.
- `made_public` (D-022): **always needs confirmation**, like a field made public; `recordIds` are the records holding a value. `made_staff`: a staff type is refused in public fields, so it lists the records holding a value in an `identifier` field that is public for their kind in some template in `existing.templates` (any field when templates aren't given, since records don't name their template yet, T-012), and needs confirmation when there are any.
- `reserved_key`: a stored type keyed `constructor` or `prototype` (valid before this decision) edited without a rename; needs confirmation. Renaming onto a reserved key is refused.
- `format_changed`: a format added or changed; the records whose current values (identifiers and field values) no longer fit. Former values are history and never checked (D-009). A format removed is not reported.
- `uniqueness_tightened`: the records whose values clash under the new rule, compared with `identifierKey`, former values counting under `all_time`. Field values aren't in the uniqueness check (D-009), so they aren't counted. `uniqueness_loosened` is informational.
- `auto_number_changed`: added or changed numbering needs confirmation when a record holds a number it would give out again: a value not of exactly the new form that reads as the type's whole prefix (or a four-digit year) then a sequence number once separators are ignored (`DHS-0009` after the prefix becomes `DHS`, `M1 0009` under prefix `M1-`, `2026015` under year numbering), above the highest number of the new form. Only values made of the head, separators and a single run of digits count (`DHS-2026-0015` isn't a `DHS-` number), and with no separator after the head the run must be at least as wide as the numbering's padding (`123456` isn't year 1234). Its key differs, so the uniqueness check can't catch it. The scan uses the numbers the type owns after the change: after a rename, `nextIdentifier` counts the new key's values (adopted left-overs), so every old-key value is a candidate; `identifierTypeCreation` with numbering runs the same scan over the adopted values. Numbers held only in template `identifier` fields count too, even of exactly the new form, because `nextIdentifier` reads only `RecordIdentifiers`. Padding changes and a new prefix (a new series) aren't reported as reissues. Removing numbering is informational.
- **`existing` is `{ identifierTypes, identifiers, records, templates? }`, the first three required:** the organization's current types (which must contain `oldType` exactly, else `type_not_listed`, so a caller can't claim the type was already public), every record's identifiers and every catalog record. Without it, `recordsChecked` is false and every change that could affect records needs confirmation; the old type can't be checked either, so a public new type always reports `made_public` (it may have been staff). As in D-023, an empty list means "none"; a missing one is refused.
- **Stored identifier sets are read leniently** (`readStoredIdentifiers`, internal): every shape and safety rule applies, but a current value of a removed type or one that doesn't fit its format is already stranded, so it is counted, not refused; otherwise the first deletion would block every later check. Templates are read with `validateLegacyTemplate`.
- **One organization (D-030):** both types, every listed type, identifier set and record must name the same valid `organizationId`, else `mixed_organizations`; a stored set without one is refused (`invalid_entry`). Templates carry one too since T-019a, and the templates listed must be the type's organization's.
- **Refuses on any doubt:** every type, identifier set, template and record is validated, and one malformed entry, a duplicate record ID, a Proxy or a getter refuses the whole check (an unreadable entry could hide a value). Types are read through own properties only, so a polluted `Object.prototype` can't hide `made_public`. Work is linear in the values, each matched against the new format at most once, about the cost of validating them.
- **One key rule for identifier types.** Identifier type keys never allowed hyphens, but template `identifierTypes` codes and the `type` of identifier values did, so a template could name a type that could never exist. Both now use `isIdentifierTypeKey` (identifiers.ts): 1 to 64 lower case letters, digits and underscores, starting with a letter, and not `constructor` or `prototype`. Other template codes (template keys, standards, vocabularies) still take hyphens.
- **Stored data keeps working.** `validateIdentifierType(s)` still accept stored types keyed `constructor` or `prototype` (so `makeIdentifierChecker` keeps working); `validateNewIdentifierType` refuses them for new types, and edits report `reserved_key`. A template stored with hyphenated `identifierTypes` codes is read by `validateLegacyTemplate`, which `templateChanges` uses for the old side, so it can be fixed (`call-number` → `call_number` is reported as `identifier_type_removed` with the records); `validateTemplate`, used for new and edited templates and by every other reader, refuses it, so such a template fails closed until re-saved. `legacyTemplateIssues(templates)` lists the stored templates `validateTemplate` refuses (`fixable` when only the identifier type codes are at fault, with those codes), so an upgrade can have them re-saved before records using them stop being checked and published.
- **Rejected:** allowing hyphens in type keys instead (type keys follow the record field key rule, and no preset or test used a hyphenated type, so narrowing the template side broke nothing real: one test fixture was renamed); allowing `constructor` for new type keys (templates already refused it in `identifierTypes`, so one rule had to pick; refusing is the safer, and stored ones are migrated by rename rather than broken); simulating `nextIdentifier` for every year to find reissues (the loose comparison finds the same numbers without needing the caller's year); treating a renamed key as delete plus add (a rename is visible here, unlike for template fields).
- **Not covered:** templates naming a deleted or renamed type are only reported (`templates_reference_type`, when `existing.templates` is given), not changed; the caller updates them through `templateChanges`. Values in `RecordIdentifiers` and template `identifier` fields are still two stores until T-014, and `nextIdentifier` still counts only `RecordIdentifiers` (follow-up).

## D-036 — Scanner and Donor relations roles, and custom roles made by system managers (2026-11-22, John)
John's answer to Q-4: add both roles, and let system managers create custom roles too.
- **Roles are made of permissions.** The code defines a fixed list of permissions (for example: view staff records, edit descriptions, upload and attach scans, publish and unpublish, see and edit donor and accession records, manage a site's people). A role is a named set of them. The service layer checks permissions, never role names, so built-in and custom roles are checked the same way.
- **Built-in roles** below the site manager: cataloger, reviewer, read-only, and the two new ones:
  - **Scanner:** uploads scans and other files and attaches them to existing records; can see the records it attaches to; can't edit descriptions, publish, or see donor or accession records.
  - **Donor relations:** sees and edits donors, accessions and deeds of gift (always staff-only data, T-016); can see the records an accession produced; can't edit descriptions or publish.
- **Custom roles.** System managers can create, rename, edit and delete roles built from the same permission list, for any organization. Each custom role belongs to one organization (D-019, D-030) and is granted per site or for chosen fonds or collections, like a built-in role. A custom role can never include system-manager powers (installing plugins and themes, creating sites, System settings, managing users across the install); those stay with system managers only. Built-in roles can't be deleted, so there is always a working set.
- **Safe changes.** Editing or deleting a role that people hold shows who is affected first; deleting one in use needs those people moved to another role. Adding a sensitive permission to a role (publish, donor data, manage people) needs confirmation, like making a template field public (D-023). Every role change goes in the change log.
- **Rejected:** fixed roles only (John asked for custom roles); letting site managers create roles (not asked; they assign the roles that exist); roles checked by name in code (a renamed or custom role would then be checked wrongly).

## D-037 — Record types are an organization's own types built on the six kinds; the record's templateKey still decides its template (2026-11-23, autopilot T-013)
PLATFORM_PLAN.md §1 says admins can add more record types. The six record kinds (D-007) stay a fixed list; what an organization adds is a **record type** built on one of them ("Oral history" is a kind of `digital_asset`, "Photograph" of `object`, "Scrapbook" of `archival_unit`). `record-types.ts` adds `RecordType` `{ key, organizationId, label, description?, kind, defaultTemplateKey }`; keys follow the template key rule, the label is one trimmed line of at most 200 characters, the description at most 2,000.
- **Validation.** `validateRecordType(input, templates)` takes the organization's template registry or the one template the type names: the template must exist (`unknown_template`, `template_mismatch`), belong to the type's organization (`wrong_organization`, checked before the key lookup so nothing about another organization's keys shows) and apply to the type's kind (`template_wrong_kind`). Getters, Proxies, prototype keys and unknown properties are refused; the result is a frozen copy.
- **A registry.** `indexRecordTypes(types, templateRegistry)` validates an organization's types once into an opaque, frozen `RecordTypeRegistry` (at most 1,000), refusing the whole list for any invalid type, duplicate key, hole, getter, Proxy, mixed organizations or another organization's templates. `recordTypeTemplateIssues(types, templateRegistry)` reports per type what would be refused (a default template deleted, renamed or no longer applying to the kind), so an admin screen can show which types to fix; run with the registry as it would be after a template edit, it shows what the edit breaks.
- **A record names its type** in an optional `recordTypeKey`, and then must also name a `templateKey` (`template_key_required`). `recordTypeDefaults(registry, key, organizationId)` gives `{ kind, recordTypeKey, templateKey }` for a new record, refusing another organization's registry; it returns no `organizationId`, so spreading it into `createRecord` can't move the record to another organization (found in review). `checkRecordType(record, registry | type)` checks that the type exists in the record's organization and has the record's kind (`no_record_type`, `unknown_record_type`, `record_type_mismatch`, `wrong_organization`, `wrong_kind`); messages name keys only.
- **The type's template is a default, not a rule.** The record's own `templateKey` stays the one source of its template (D-029); checking and publishing never take a template from the type, so editing a type never changes what a record publishes. The type itself isn't published yet.
- **Rejected:** new organization-defined kinds (the arrangement tree, media types, agent types, place positions and Dublin Core classes all depend on the six); requiring `templateKey` to equal the type's default (two sources of truth); allowed-template lists per type (a template's `appliesTo` already limits kinds); an optional `organizationId` (D-030); `recordTypeDefaults` returning the type's organization.
- **Not covered yet:** edits and deletions of a record type aren't checked against the records using it (T-013a).

## D-038 — One home for numbers: `RecordIdentifiers`; identifier fields only point at a current identifier (2026-11-23, autopilot T-014)
A record's numbers live only in its `RecordIdentifiers` (D-009): current ones with exactly one primary, and former ones, where uniqueness, auto-numbering, retiring and search already work. A template field of kind `identifier` stores no number of its own: its `{ type, value }` names one of the record's current identifiers exactly (same type key, same value character for character; no `identifierKey` or lookalike matching).
- **Saving.** `identifierFieldIssues(record, template, identifiers)` (identifier-fields.ts) is the save-path check beside `checkRecordAgainstTemplate`: `identifier_not_held` for a field value that isn't a current identifier (naming the field, never the number), `wrong_record`, `mixed_organizations` / `wrong_organization`. Its caller is the service layer (T-032); nothing in core calls it yet.
- **Effective record.** `effectiveRecord` takes `options.identifiers`, the sets for the record and its ancestors, read once and frozen; another organization's set or one naming none gives `mixed_organizations`, a record listed twice `duplicate_identifiers`, a malformed set or one without exactly one primary or with a current number twice `invalid_identifiers` (a number both current and former is allowed: a reinstated number). A public identifier value its source record (the record itself, or the ancestor it is inherited from) doesn't hold as current is kept staff with `identifier_not_held`; without the option every public identifier value is staff with `identifiers_unknown`. Both block publishing.
- **Boundary.** `publicOutput` requires `identifiers` (the sets as they are now) whenever the view holds an identifier value (`identifiers_unknown`), and each number must still be a current identifier of the record it came from (`identifier_changed`), so a kept view can't publish a number retired, moved or re-typed since (found in review). Sets must already have passed `validateRecordIdentifiers` and `uniquenessIssues` on the save path; a value of a type that isn't one of the organization's public types is refused anyway by the identifier checker.
- **Public types** stay as D-022: the primary number, like any other, reaches public output only through a public `identifier` field and only when its type is public. A staff-type primary relabelled in the field as a public type is caught because the pair isn't held.
- **Rejected:** fields as the home (former numbers, the primary mark, uniqueness and auto-numbering don't fit field values); projecting fields from `RecordIdentifiers` with no stored value (which number goes in which field would be a guess); matching by `identifierKey`; silently dropping values that aren't held; `identifiers` optional on `publicOutput`; re-running format and uniqueness checks at publish time.
- **Consequence:** field values are a subset of current identifiers, so `nextIdentifier` counting only `RecordIdentifiers` is correct for valid data (D-031's open note).

## D-039 — Links between records: a `record_link` kind, a record link checker, and links named only when safe (2026-11-23, autopilot T-015)
A record links to another record of its own organization through a new field kind, `record_link`, value `{ recordId, label }` (both required). A field may limit what it links to with `recordKinds` (1 to 6 distinct kinds; refused on other field kinds, `not_for_kind`). A creator from the Authorities list is `record_link` with `recordKinds: ["agent"]`; related records are a repeatable `record_link`. `label` is this record's own text for the link, published only with the link itself (**amended by D-045**: when the linked record may not be named, nothing of the link is published, not even the label). A place's existing `recordId` is the same kind of link, to a place record.
- **The checker.** `makeRecordLinkChecker(records)` (a list or an `indexRecords` lookup; mixed organizations refused) is passed as both `checkers.record_link` and `checkers.place`. It refuses another organization's record (`wrong_organization_checker`), an ID not in the set (`unknown_record`), an unusable record, a kind the field doesn't allow (`wrong_record_kind`) and a self link (`self_link`); its messages never quote the linked record. It snapshots each record's ID, kind and organization only, so it is made again after records change. Without it `record_link` values are refused (`unchecked`); a place's `recordId` is still accepted but never linked publicly.
- **The public view holds no linked IDs.** `publicView` holds a place as `{ label, uri? }` and removes `recordId` from values of every kind; it holds no `record_link` value at all (D-045; before, `{ label }`). An own public value that doesn't fit its field as the template has it now (a link, identifier or rights value left in a field since made text) is held back as staff with a `does_not_fit_field` note that blocks publishing (found in review).
- **Public output (supersedes D-016's place rule).** A link goes out as `baseUrl` + ID, labelled, only when the linked record is in `published`, the checker given for that kind was made by `makeRecordLinkChecker` from this record's organization's records and holds it, its kind is allowed and it isn't the record itself; otherwise nothing of a `record_link` goes out (D-045; before, its label), and a place goes out as its name (and gazetteer URI) without the link, when its place record is vouched for (D-048). The linked record's title and values are never read. Another organization's checker is refused outright. In JSON-LD a link under a class-range term is `{"@id","rdfs:label"}`; Dublin Core and oai_dc get the label. Links inherit like any other value (D-013); an inherited link no checker checked is left out with a note.
- **Breaking, on purpose:** callers that pass only `published`, with no record link checker, now get place names without a link: the published list carries no organization, so trusting it alone could link another organization's place (D-030).
- **Rejected:** separate `agent`/`event` kinds or extending `place`; a link with an optional `recordId`; publishing the linked record's current title; trusting `published` alone; a separate `publicOutput` option for link targets; IDs or misfit values in the public view.

## D-040 — Storage locations and moves: one move log is the truth, staff-only, per organization (2026-11-23, autopilot T-017)
Spectrum "Location and movement control" in `storage.ts`.
- **Storage levels** are named by the organization top down (`StorageLevels { organizationId, levels }`: 1 to 8 one-line names, no two alike ignoring case); the default is Room › Shelf › Box › Folder (mockup Settings).
- **Locations** (`StorageLocation`): a random v4 UUID, `organizationId`, `kind` (`storage`, `display`, `external`), `name`, `level` (storage and display only), optional `parentId`, `container`, `agentId` (external only) and `note`. A location sits in one at a strictly higher level (levels may be skipped, so loops are impossible); outside locations (conservator, vendor, borrower) have no level or parent. Sibling names are unique ignoring case and can't contain "›". A container moves by editing its `parentId`, and its contents follow.
- **Moves** (`StorageMove`): `recordId`, `locationId`, `movedOn` (an EDTF day, D-008), `reason` (`placement`, `rehousing`, `return`, `correction`, `exhibition`, `loan_out`, `conservation`, `digitization`, `photography`, `research`, `other`, and `departure`, added by D-044), optional `expectedReturnOn` (temporary reasons only, not before the move) and `note`, and `recordedAt`. `placement` and `rehousing` set the normal location; a `return` must go to the normal location in force then.
- **The move log is the only truth.** Current and normal location, history, the away and overdue lists and box contents are worked out from the moves, never stored separately, so they can't disagree (Spectrum: one location entry per object). Moves order by `movedOn`, `recordedAt`, ID. An expected return date stays outstanding until a `return`; while it is outstanding, a later dated move replaces it only as an extension (the same reason, to the same location as the move that gave it), and any other dated move keeps the earlier date. While a date is outstanding the record is away, even at its normal location, and stays on `overdueReturns`, so a record out on loan can't be taken off the overdue list on paper (amended by D-044). A record never placed that is out with a date comes back by a placement followed by a return there.
- **Snapshots** as in D-029: `indexLocations` and `indexMoves` validate whole lists once into opaque frozen snapshots; the queries (`whereabouts`, `moveHistory`, `awayFromNormal`, `overdueReturns`, `locationContents`, `locationPath`) read only those. `withMove` checks one new move in its place in the history and refuses a `recordedAt` in the future; `reindexLocations` checks any level or location edit against the whole history; `checkLocationDeletion` refuses deleting a location with contents or history. Caller lists are read once (Proxies, getters, holes and prototype keys refused).
- **Organizations (D-030)** are required on levels, locations and moves; mixed sets are refused. A move's `recordId` and a location's `agentId` are only checked as IDs here; the service layer (T-032) checks they belong to the session's organization.
- **Staff-only.** Storage data is never a record field; nothing in `effective.ts` or `public-output.ts` reads it, and a test checks no module but `index.ts` imports it.
- **Rejected:** stored current or normal location on records (a second truth); free-text paths; planned future moves in the log; fixed level names.
- **Not done yet:** a container's own moves in its records' histories; who moved or authorised a move (logins, Phase 2); concurrent saves (T-032).
- Source: Spectrum 5.0 "Location and movement control" as reproduced by a museum (pitstonemuseum.co.uk); Collections Trust's own 5.1 page couldn't be reached.

## D-041 — An inherited identifier value with a staff type stays as the child's staff value (2026-11-23, autopilot S-006a)
Narrows D-022. An identifier value inherited into a public field whose only problem is `private_identifier_type` is checked again as a staff field and, if it passes, kept in the child's effective record as `staff` with an `inherited_staff_identifier` note. Before, the whole value was dropped from the child, staff side too, and a repeatable list lost its public numbers with it. Nothing of it reaches `publicView` or public output, and publishing the child isn't refused: the mistake is on the record that holds the number, where D-022 already blocks publishing. A value refused for any other reason is still left out with `not_valid_here`, and that note never quotes a staff-type number (found in the integration review). ## D-042 — dcterms:type has no range; jsonld as a test-only dependency (2026-11-23, autopilot T-009a/T-010a)

## D-043 — Accessions and deeds of gift: a staff-only register per organization, and a deed check only as fresh as that register (2026-11-23, autopilot T-016)
Spectrum "Acquisition and accessioning" in `accessions.ts`.
- **Accession:** a random v4 UUID, `organizationId`, `number` `{ type, value }` of one of the organization's staff identifier types (D-009; a public type is refused, `public_type`), `sourceAgent` and the produced `records` as record links (D-039), `receivedOn` (an EDTF day), `method` (`gift`, `purchase`, `bequest`, `transfer`, `field_collection`, `found_in_collection`, `other`), `materials`, optional `restrictions` and `note`, `deedStatus` (`missing`, `sent`, `signed`, `not_needed`) and optional `deedSignedOn`. A gift can't be `not_needed`: Spectrum asks for the donor's signed offer as evidence of transfer of title. **Donor contact:** `{ agentId, organizationId, email?, phone?, address?, note? }`, one per agent.
- **Register.** `indexAccessions(organizationId, { accessions, contacts?, records, identifierTypes })` validates everything once into an opaque, frozen register. Numbers are unique and fit their type; `nextAccessionNumber` counts through `nextIdentifier`. Links are checked with `makeRecordLinkChecker` from the register's own copy of the records (the source must be an agent; produced records objects, archival units or digital assets). Queries: `accessionById`, `accessionsByNumber`, `accessionsOfRecord`, `accessionsAwaitingDeeds` (mockup Deeds), `deedHoldsOn`, `recordsHeldBack`, `donorContact`. Nothing here checks roles: the Donor relations permission (D-036) is enforced by the service layer (T-032, T-041).
- **Organizations (D-030).** The register takes its organization as an argument, so even an empty one says whose it is; anything of another organization refuses the whole input, naming nothing of it.
- **Held back:** the records an accession with a `missing` or `sent` deed produced, the units filed below them, and the digital assets that represent any of those.
- **The check.** `effectivePublishIssues(effective, { accessions })` runs the deed check last. For an object, archival unit or digital asset it refuses with no register (`accessions_unknown`), with anything not made by `indexAccessions` (`invalid_accessions`, `invalid_options`), with another organization's register (`mixed_organizations`), when the record, any record in its current ancestry, or for a digital asset the record it represents and that record's ancestry (asset chains followed up to 8 hops, cycles stopped) is unknown to the register (`accessions_out_of_date`, `represented_record_unknown`), and when any of them is held (`deed_not_signed`, naming no donor, accession or number). Agents, places and events need no register. `publicOutput` takes the same option; with `records` it finds the ancestry again as it is now.
- **Links to held records.** A `record_link` or place link to an object, archival unit or digital asset goes out as `baseUrl` + ID only when `publicOutput` is given `records` and the target's current ancestry and represented chain are all known to the register and none is held; otherwise only its label goes out. So a page published without `records`, and an agent, place or event page published without `accessions`, shows such links as labels only (found in review: partial and stale registers made held records live links). **Amended by D-045:** a `record_link` that isn't linked now puts out nothing, not its label; a place keeps its name.
- **Only as fresh as the register.** Make it at publish time from the organization's records, accessions and contacts as they are now. A register that doesn't know a record refuses it rather than clearing it.
- **Staff-only.** Accessions and contacts are never records or fields; `effective.ts` and `public-output.ts` import only `accession-holds.ts`, which exposes the organization and two lookups (`isHeld`, `isKnown`). Messages never quote contact details, materials, restrictions or notes.
- **How T-034 calls it:** build `indexAccessions` at the moment of publishing, refuse on any `effectivePublishIssues(effective, { accessions })` issue, and pass the same fresh register and `records` to every `publicOutput` call. When an accession is saved (a deed back to missing, a record added), list the published records among `recordsHeldBack(register)` and offer to withdraw them.
- **Rejected:** an optional check, or one that passes without a register or with one that doesn't know the record; an `effectiveRecord` option (a kept view would keep a stale answer); donor contacts on agent records (agent records can be public); accessions as a seventh kind (D-037); accession numbers in `RecordIdentifiers` or of a public type; refusing a record listed by two accessions (accruals happen; the stricter hold wins).
- **Not done yet:** ~~restrictions are text and hold nothing back (T-016a)~~ structured restrictions hold since D-056; who changed a deed and when (Phase 2 change log); concurrent saves (T-032).
- Source: Collections Trust, "Acquisition and accessioning: suggested procedure" (Spectrum 5.0), read 2026-11-23.

## D-044 — Loans and condition checks: loans point at moves, checks are dated entries, both staff-only (2026-11-23, autopilot T-018)
Spectrum "Loans in", "Loans out" and "Condition checking and technical assessment" in `loans.ts` and `condition-checks.ts`, built on the move log (D-040), which this entry amends.
- **A loan:** a random v4 UUID, `organizationId`, `direction` (`in`, `out`), `number` (unique per organization and direction ignoring case), `agentId` (lender or borrower), `beginOn` and `endOn` (both required: "All loans are for fixed periods"; an extension edits `endOn`), `status` (`requested`, `agreed`, `declined`, `cancelled`, `closed`) with `statusOn` (not after tomorrow, `future_status`), optional `purpose`, `terms`, `note`, and 1 to 500 items.
- **Where things are stays in the move log.** A loan out item names its `loanOutMoveId` (a `loan_out` to an outside location whose `agentId` is the borrower) and, once back, its `returnMoveId`; a loan in item names its `arrivalMoveId` (a `placement`) and `departureMoveId` (a `departure` to the lender, or the place a correction straight after it names). The start move must fall within the loan period (`move_outside_loan`); the end move must be the record's first return or departure after it (`end_out_of_order`); nothing may have moved on a requested, declined or cancelled loan.
- **Problems stay with their loans, and never hide one.** The whole book is refused only for invalid loans, duplicate IDs or numbers and another organization's loans. Move-link problems (`unknown_move`, `move_reused`, `wrong_move_reason`, `not_agent_location`, `end_out_of_order`, `move_outside_loan`, `overlapping_loans`) are reported on every loan involved, never only the later one. A loan with problems has phase `unknown` and stays on `overdueLoans` once past its end date. `withLoan` refuses an edit with any problem of its own or that gives another loan a new problem, and an edit that drops a recorded move link or removes an item whose start is recorded unless its end is recorded (`link_removed`). A closed loan out whose record has an unexplained `loan_out` to the borrower in the loan period has `closed_with_unlinked_move`; a loan in closes only when every item's departure is linked or the item never arrived (`closed_without_departure`). `unexplainedLoanMoves` and `unexplainedDepartures` list moves no loan names (found in three review rounds: decoy and self-edits, problem loans and back-dated moves could all take an overdue loan off the lists).
- **The due date feeds storage.** `loanOutMove` builds the `loan_out` with `expectedReturnOn` = `endOn`, refusing a day outside the loan; an extension is another `loan_out` to the borrower. `loanState` reports `dueBack` and `dueMatchesLoan`; `overdueLoans(book, today)` lists late loans out and loans in not yet gone back.
- **`departure` (amends D-040):** a record leaving the organization's care for good (so far, a loan in going back). It goes to an outside location, takes no return date, and is allowed only when the record is in care and no return date is outstanding (`departure_while_away`). Afterwards only a `placement`, or a `correction` to another outside location written down after it, may follow (`move_after_departure`), so a back-dated departure can't wipe a normal location while the record is out.
- **A condition check** is one dated entry per record: `checkedOn`, `checkedBy` (and optional `checkerId`), `condition` (`good`, `fair`, `needs_conservation`, as in the mockup), `reason`, optional `fitToMove`, `loanId`, `note`, and `recordedAt` (Spectrum's minimum: "the date, name of the condition checker and the reason for checking"). `fitToMove(log, recordId, { on, maxAgeDays })` answers `fit`, `unfit`, `stale` or `unchecked`; `needingConservation` lists records whose latest check says so.
- **Snapshots, organizations and staff-only** as in D-040: opaque frozen books and logs, caller lists read once, required `organizationId` with mixed sets refused; agent, record and loan IDs are checked as IDs only (T-032 checks ownership); nothing in `effective.ts` or `public-output.ts` reads them.
- **Rejected:** locations or an "on loan" flag on the loan (a second truth); open-ended loans; organization-defined condition terms for now; checks that edit earlier ones; departures from anywhere; refusing a whole book for one stale loan; flagging only the later of two loans.
- **Not done yet:** a borrowed item that stays for good (bought or given) can't close its loan in until acquisitions can link to it; authoriser, valuation and insurance fields; linking a check's `loanId` to the loan book; saving a move and its loan edit in one transaction (T-032).
- Sources: Spectrum 5.0 "Loans in", "Loans out" and "Condition checking and technical assessment", as reproduced by a museum (pitstonemuseum.co.uk/pims/spectrum-5.0/), read 2026-11-23; the 5.1 procedure text couldn't be reached.

## D-045 — Links to private records show nothing on public sites (2026-11-23, John)
John's answer for S-011: when a published record links to a record that isn't published, or belongs to another organization, the public site shows nothing for that link: no ID, no label, no placeholder. Staff still see the link.
- **Why:** a label copied from the target (a donor's name, a private item's title) would reveal the private record. Showing nothing is the only answer that can't leak.
- **Rejected:** publishing the target's label without its ID (the D-039 behaviour, which this replaces); a staff-written public label (more work for staff, and an easy place to type a private name).
- **Changes:** S-011 implements it; the `record-links.ts` header and D-039 are updated to match.
- **How (S-011):** `publicView` holds no `record_link` values at all, since it can't know which records are published; `effectiveRecord` records the keys of the public link fields beside the view, and `publicOutput` reads those values from the effective record, template-checks them, and puts out each one that may be named (D-039's rules plus the deed check of D-043) as its URL and label. The others are dropped; a term left with no values is left out of every form. A place value keeps its own name (and gazetteer URI) without the link, only when the organization's place checker vouches for its place record (D-048).
- **Amendment (S-011c, 2026-11-23, autopilot): links to deleted records.** A public `record_link` whose record the organization's record link checker doesn't hold (`unknown_record`: deleted since, or a checker made before it was added) no longer refuses the whole record's public output. It is dropped exactly as a link to an unpublished record is (nothing of it in any form: no ID, no label, no placeholder; a term left empty is left out), and `publicOutput`'s result lists it in a new `staffWarnings` field as `link_target_missing` (path to the value's `recordId`, fixed text naming no record or label). `staffWarnings` is staff only and is never part of `dublinCore`, `jsonLd`, `jsonLdText` or `oaiDcXml`. Only `unknown_record` on a `record_link` field is softened: every other template-check problem (`wrong_record_kind`, `unusable_record`, `self_link`, a bad shape, an identifier problem) still refuses, and the save-time check (`checkRecordAgainstTemplate` with the record link checker) still refuses unknown targets, so new dangling links can't be made. A place value naming a deleted place record was already left out of the view (D-048) and is unchanged. Why: failing closed on the record blocked publishing every record that pointed at one deleted authority; dropping the link shows nothing that D-045 doesn't already allow, so nothing leaks, and the warning keeps it visible to staff. Rejected: refusing as before (one deletion blocks many records); a placeholder or the label alone (D-045 forbids both); reporting nothing (staff wouldn't learn the link is dead); a separate staff function to find dead links (it would have to repeat the template check `publicOutput` already runs).

## D-047 — Dublin Core mappings belong to an organization; built-in mappings are presets (2026-11-23, autopilot T-019b1)
Extends D-030 and D-012 to Dublin Core mappings, the one kind of organization data in `packages/core` that still had no owner (T-019a review: a mapping was matched to a template by key only, so one organization's mapping passed for another's template with the same key).
- **Shape.** `DublinCoreMapping` is `{ organizationId, template, entries }`, with a required `organizationId`, as the database row will carry an `organization_id` column. `DublinCoreMappingPreset` is the same without `organizationId`; the built-in `DACS_DUBLIN_CORE`, `SPECTRUM_DUBLIN_CORE` and `DIGITAL_ASSET_DUBLIN_CORE` (and `presetDublinCoreMapping`) are presets now, a breaking type change like `TemplatePreset`.
- **Checks.** `validateDublinCoreMapping(mapping, template)` validates the template with `validateTemplate`, so a preset template without an organization is `invalid_template` (D-030 let mappings be checked against presets through an internal `validateTemplateShape`; that function is removed). In `validateDublinCoreMapping`, a mapping whose `organizationId` is missing, invalid, inherited or behind a getter is `invalid_organization` (`mappingForTemplate` and `mappingFromPreset` answer `unreadable` for a getter), and one of another organization than the template's is `wrong_organization`. Either gives **that one issue only**, decided before any entry is looked at, so the result never names the mapping's template key, fields or either organization's ID. The mapping is read once into a frozen copy and the decision uses the copy; when the copy can't be made, the organization is read from the input's own data property instead, and its issues (which can quote the mapping's keys) are returned only if the mapping's own `organizationId`, read without running a getter, is the template's. `publicOutput` goes through this check, and the template it uses is already tied to the record's organization (T-019a), so a mapping publishes only for records of its own organization.
- **Copies.** `mappingFromPreset(preset, template)` makes an organization's mapping from a preset for one of its templates: `template` becomes the template's key and `organizationId` the template's organization, then the whole copy is checked. A mapping that already has an `organizationId` (even `null`) is refused (`has_organization`), as a guard against mistakes rather than a security boundary, as with `templateFromPreset`. `mappingForTemplate(mapping, template)` still re-targets a mapping to another template, but only within its own organization: it keeps the mapping's `organizationId`, so another organization's mapping or one without an organization is refused.
- **Rejected:** letting a mapping without an organization match any template (a missing owner would silently match every organization, D-030); having `mappingForTemplate` adopt the template's organization for an organization-less mapping (one function would both re-target and change ownership, so stripping `organizationId` from another organization's mapping would be enough to take it over; a separate `mappingFromPreset` makes the adoption explicit); keeping `validateTemplateShape` so mappings can still be checked against presets (nothing outside tests did that, and a check that accepts an unowned template is the kind of path that reads across organizations); reporting the usual entry issues alongside `wrong_organization` (they would name another organization's field keys).
- **Vocabularies, terms and rights settings (T-019b2).** Not changed here: in `packages/core` vocabularies and rights terms are built-in standard lists, controlled terms are stored inside records (which carry an `organizationId`), and there are no stored rights settings yet. When local term lists, stored authority terms (T-027) or rights settings become data, they get the same required `organizationId`.

## D-049 — PostgreSQL 15 to 19, and a throwaway test database inside the gate (2026-11-23, autopilot T-020)
**Versions.** Oculus supports every PostgreSQL major version the community still supports, and no others. On 2026-11-23 that is **15, 16, 17, 18 and 19**. PostgreSQL 14 had its final release on 2026-11-12 and is not supported. The range moves with postgresql.org's versioning page. Each major gets 5 years, so 15 drops after its final release on 2027-11-11 (16: 2028-11-09). A new major is added once CI passes on it.
- **Write SQL for the oldest supported version.** Nothing newer than 15 may be used until the floor rises. For example, `uuidv7()` is new in 18 and `JSON_TABLE()` is new in 17. UUIDs come from `gen_random_uuid()` or from Node's `crypto.randomUUID()`.
- **`db:migrate` checks the server first.** It reads `server_version_num` and refuses to run below 15. Above the newest major CI tests, it gives a warning.
- **Hosting may narrow the range later.** Q-2/D-035/D-046 may narrow it, for example to the versions SiteGround's shared plans offer. Its knowledge base lists PostgreSQL but no version could be read here, so this is checked with SiteGround before T-051. The range never widens to a version the community no longer supports. If a host offers only an end-of-life version, that host doesn't meet D-035.

**Database tests in the gate.** `npm run gate` stays one command, and database tests are ordinary Vitest tests that count toward `tests_passing`.
- **Where the gate gets its database.** If `OCULUS_TEST_DATABASE_URL` is set, the gate uses that server (CI does this). Otherwise it starts its own throwaway server:
  - It runs `initdb` into a new temporary directory, finding the binaries through `PG_BIN` or `pg_config --bindir`.
  - It starts the server with `pg_ctl start -w`, listening only on a Unix socket in that directory (`listen_addresses=''`, so no TCP port) and with `fsync=off`.
  - It runs Vitest, then always stops the server with `pg_ctl stop -m fast` and deletes the directory, whether the tests passed or not. No server is left running.
- **No password anywhere.** Local tests use trust authentication on the private socket.
- **Running as root.** `initdb` refuses to run as root, and the build sandbox runs as root. So under uid 0 the gate runs `initdb` and `pg_ctl` as the `postgres` system user (`runuser -u postgres`), with the temporary directory owned by that user.
- **The sandbox.** It has PostgreSQL 16.15 at `/usr/lib/postgresql/16/bin` (`pg_config --bindir`). The current 16.x minor is 16.16. There is a client-only Docker with no daemon. The system cluster `16/main` is stopped and stays unused.
- **No silent skips.** If there is no URL and no PostgreSQL binaries, the gate fails with a message saying how to provide one. A database test with no database fails; it is never skipped.
- **Test isolation.** Each test file works in its own freshly created database and drops it afterwards. T-024 decides the details, such as cloning a migrated template database.
- **GitHub Actions.** The `gate` job runs `npm run gate` once per PostgreSQL version: 15 (the oldest supported) and 19 (the newest). Each uses an official `postgres:<major>` service container:
  - It has a `pg_isready` health check and port 5432 mapped to the runner.
  - It uses `POSTGRES_HOST_AUTH_METHOD: trust`, so there is no password in the repository, not even for tests. The container is reachable only from that job.
  - `OCULUS_TEST_DATABASE_URL` points at `localhost`.
  - If no `postgres:19` image is published yet when T-024 runs, it uses 18 and adds a follow-up task.

**Rejected:**
- Supporting 14 or older (14 is end-of-life).
- Testing only the sandbox's 16 (misses both ends of the range).
- Testing all five majors in CI (the oldest and newest catch use of newer features and breakage on a new release, at a fraction of the CI minutes).
- Pointing tests at the long-running system cluster (state leaks between runs, and a server is left running).
- Docker or Testcontainers locally (the sandbox has no Docker daemon).
- `embedded-postgres`-style npm packages (they download server binaries the license check can't see).
- Skipping database tests when no database is available, or mocking the database (both weaken the gate).
- A password in the workflow file.

## D-050 — Database access: the `pg` driver with hand-written SQL through one `sql` tag; plain `.sql` migrations run by our own runner (2026-11-23, autopilot T-021)
**The driver and the queries.** `pg` (node-postgres) with hand-written SQL. `pg` is a runtime dependency of `packages/db` only, and `@types/pg` is a dev dependency.
- **One place imports the driver.** `packages/db` is the only package that imports `pg`, and lint enforces this with `no-restricted-imports`.
- **Every query goes through one `sql` tagged template.** It is written in `packages/db` and turns each `${value}` into a `$n` parameter, returning `{ text, values }` for `pg`.
  - There is no raw-string escape hatch. Table and column names are written in the SQL text, never interpolated.
  - Lint bans calling `.query()` with anything but the tag's result.
- **JSONB without building strings.** Values go in as parameters (`${JSON.stringify(v)}::jsonb`). A template field's key is a parameter too (`fields -> ${key}`), never part of a path string.
- **Full-text search without building strings.** It uses `websearch_to_tsquery(${config}::regconfig, ${q})`, and the search text is always a parameter.
- **TypeScript types.** Each query function declares its row type. Types aren't generated from the database, so every query has a test that runs it against the migrated test database (D-050 T-020), and a mismatch fails the gate.
- **Type parsers.** T-024 sets them explicitly: `int8` and `numeric` come back as strings, not lossy numbers, and dates come back the way D-008 stores them.
- **Separate roles.** The public sites' read-only path is a separate connection pool with its own database role (D-034).

**Migrations.** Plain SQL files in `packages/db/migrations/NNNN_short_name.sql`, forward only, applied by a small runner in `packages/db` (`npm run db:migrate`, T-024). The runner:
- takes a `pg_advisory_lock`, so two runs can't migrate at once;
- runs each file in its own transaction;
- records the file name, a SHA-256 of its contents and the time in an `oculus_migrations` table;
- refuses to run if an applied file was edited, is missing, or a new file sorts before an applied one.
- **No down migrations.** Undoing a migration is a restore from backup (T-052).
- **Statements that can't run in a transaction** (for example `CREATE INDEX CONCURRENTLY`) are left for T-024 to decide, if they're ever needed.

**Candidates checked** (npm registry and npm's advisory database, 2026-11-23):
- **`pg` 8.23.1** (released 2026-09-30):

  - Unlicense; no dependencies; no advisories; tagged templates built in.

  - Four high-severity advisories in its 0.26–0.28 lines, injection through JSON path keys and `sql.lit`: GHSA-pv5w-4p9q-p3v2, GHSA-wmrf-hv6w-mr66, GHSA-8cpq-38p9-67gx, GHSA-fr9j-6mvq-frcv.

Plain SQL is exactly what the PostgreSQL docs describe, so JSONB, full-text search, roles and views (D-034) need no translation layer. Its 15-year record has one old advisory. It is also the driver Kysely, Drizzle and the migration tools are built on, so a query builder would add a layer, not replace `pg`.

## D-051 — The HTTP server: Fastify 5 (2026-11-23, John and autopilot T-022)
John chose a well-known framework over a hand-written layer, so a future maintainer meets something familiar. Oculus serves its JSON API, the admin's built files and the server-built public pages (D-034) with **Fastify 5** (MIT, an OpenJS Foundation project, five npm maintainers), pinned at 5.12.8 or later.
- **Why Fastify.** Of the frameworks compared it has the best defaults for this task: a 1 MiB body limit, protection against prototype poisoning in JSON bodies, schema-checked routes and an exact router (find-my-way) rather than route strings turned into regular expressions. It needs no WebSockets (D-035, D-046).
- **Its record, and what we do about it.** It installs 48 packages (all MIT, ISC or BSD-3-Clause, D-002) and has 20 GitHub advisories over its life, 10 high. Six were in 2026: Content-Type parsing that let bodies skip validation (GHSA-jx2c-rxcm-jvmq, GHSA-247c-9743-5963, GHSA-573f-x89g-hqp9), an authentication bypass through malformed URLs (GHSA-p68q-wchp-6fh7, fixed in 5.12.2) and X-Forwarded-* spoofing (GHSA-444r-cwp2-x5xf, GHSA-3m5p-2c4r-xxw2). So Oculus:
  - registers its own content-type parsers for exactly `application/json` and, on form routes, `application/x-www-form-urlencoded`, and refuses everything else with 415, including compressed bodies;
  - leaves `trustProxy` off unless an environment variable names the trusted proxy;
  - checks every body again with the core validators, never trusting the route schema alone;
  - doesn't use the default logger for request bodies or cookies.
- **The rules on top** (T-022a builds them; `(risky)`, independent review, an attack test for each):
  - **Bodies:** 1 MiB default, 8 KiB for sign-in, two-step and site password posts, counted for chunked bodies.
  - **Paths:** encoded slashes, backslashes, `..` and NUL refused; unknown routes 404, wrong methods 405, before any handler.
  - **Cookies:** `@fastify/cookie` (OpenJS, MIT), read only for Oculus's own names; the same Oculus cookie twice is refused; written only through one helper that sets `__Host-`, `Secure`, `HttpOnly`, `SameSite` and `Path=/` (ASVS 5.0 3.3.1–3.3.4).
  - **Changes:** any method other than GET or HEAD carries an `Origin` matching the host or `Sec-Fetch-Site: same-origin`, plus T-037's CSRF token (ASVS 5.0 3.5.1, 3.5.3).
  - **Timeouts** shorter than Node's defaults; **errors** without stack traces (T-042).
  - Any other Fastify plugin is its own dependency decision.
- **Rejected:**
  - **A small layer on `node:http`** (the autopilot's first draft): fewest outside parts, but security code that only the autopilot and its reviewers would know — John preferred the familiar framework.
  - **Express 5:** 65 packages and a history of body-limit and ReDoS bugs in its parts (body-parser GHSA-v422-hmwv-36x6, GHSA-27r3-jxmh-p828; path-to-regexp GHSA-9wv6-86v2-598j, GHSA-j3q9-mxjg-w52f); no cookie reading without another package.
  - **Hono:** one npm maintainer, and repeated body-limit and cookie bugs (GHSA-9vqf-7f2p-gf9v, GHSA-26pp-8wgv-hjvm and others).
- **Upkeep:** Fastify's advisories are watched like every dependency (npm audit in the gate, Dependabot); a Fastify major version gets its own decision entry.
- Sources: https://fastify.dev/docs/latest/Reference/Server/ ; https://nodejs.org/api/http.html ; the npm advisory bulk endpoint (GitHub Advisory Database) for fastify, @fastify/cookie, find-my-way, express, body-parser, path-to-regexp, hono and @hono/node-server; OWASP ASVS 5.0 V3; `npm view` and trial installs, all read 2026-11-23.

## D-052 — Passwords with scrypt now and Argon2id later, two-step sign-in required for all staff (TOTP and recovery codes), sessions stored in PostgreSQL (2026-11-23, autopilot T-023)
Everything here uses `node:crypto` (`scrypt`, `randomBytes`, `createHmac`, `createHash`, `timingSafeEqual`, AES-256-GCM). No new dependency is needed. Checked against OWASP ASVS 5.0 V6 (Authentication), V7 (Session Management) and V3.3 (cookies).

**Passwords**
- **scrypt from `node:crypto` for now, N=2^14, r=8, p=5 (16 MiB).** This is one of OWASP's equal-strength scrypt settings, and the one that uses the least memory per sign-in, which matters on shared hosting (D-046). It took about 0.2 s in the sandbox, against 0.5 s and 128 MiB for N=2^17, p=1.
  - The salt is 16 random bytes and the key is 32 bytes.
  - Hashing always uses the async `crypto.scrypt` (the libuv thread pool), never `scryptSync`, and only a few hashes run at once, so a burst of sign-ins can't starve the server.
  - Each hash is stored as one PHC-format string with the algorithm and its settings (`$scrypt$ln=14,r=8,p=5$<salt>$<hash>`). When the settings or the algorithm change, a password is re-hashed at the next sign-in. Hashes are compared with `timingSafeEqual`.
- **Argon2id later.** OWASP prefers Argon2id (m=19456 KiB, t=2, p=1), and `crypto.argon2()` exists only from Node 24.7.0 and needs OpenSSL 3.2 or later. Oculus still supports Node 22 (D-006), and the build sandbox runs 22.23.5, where it is missing, so the gate couldn't test it. When the `engines` floor is raised to 24.7 or later (Node 22's support ends in April 2027), a decision entry switches new hashes to Argon2id, and the PHC format moves each user over at sign-in.
- **Password rules (ASVS 5.0 6.2):**
  - Length is at least 8 characters (6.2.1), with 15 recommended on the form. At least 64 characters are allowed (6.2.9); the cap is 1,024 bytes, which keeps request size bounded.
  - There are no composition rules (6.2.5), no forced rotation (6.2.10) and no hints or secret questions (6.4.2).
  - The password is hashed exactly as received, with no trimming, case changes or truncation (6.2.8).
  - A new password is checked against a bundled list of at least the 3,000 most common passwords (6.2.4) and a list of context words such as "oculus", "dickinson", "historical" and the organization's name (6.1.2, 6.2.11). The list's own license must pass D-002.
  - A check against breached passwords (6.2.12, for example the Have I Been Pwned range API) would be an outbound request. It is left as a later, off-by-default option with its own security review.
- **Sign-in throttling (ASVS 6.1.1, 6.3.1, 6.3.8):**
  - Failures are counted in PostgreSQL (no Redis needed) per account and per client address. The client address comes from the socket unless a trusted proxy is configured (D-051).
  - Each counter brings a growing delay and then a temporary block, never a permanent lockout, so nobody can lock a colleague out by guessing.
  - A wrong user name gets the same reply and the same timing as a wrong password: it is checked against a dummy hash.
  - The rules are written down, as 6.1.1 asks.
- **Rejected:**
  - The npm `argon2` package: a native add-on with prebuilt binaries, a poor fit for shared hosts, and a new dependency where Node will soon do the job.
  - bcrypt: legacy only, and it ignores everything past 72 bytes.
  - PBKDF2.
  - A pepper: an extra secret in the environment that, if lost, makes every password fail. OWASP calls it defence in depth only.

**Two-step sign-in**
- **TOTP per RFC 6238, built with `node:crypto` alone.** It uses HMAC-SHA-1, which every authenticator app supports, with 6 digits and 30-second steps. One step either side is accepted for clock drift, using the server's clock only (ASVS 6.5.5, 6.5.8).
  - The secret is 20 random bytes (160 bits, RFC 4226's recommended length). It is shown as RFC 4648 base32 text and as an `otpauth://` link.
  - The last accepted time step is stored per user, so a code is never accepted twice, even within its window (RFC 6238 §5.2, ASVS 6.5.1).
  - Code attempts are throttled like passwords.
- **The TOTP secret is encrypted at rest** with AES-256-GCM under a key from an environment variable (`OCULUS_SECRET_KEY`, never in the repository). It can't be hashed, because the server must read it to check codes. If that key is lost, two-step sign-in stops working but nothing else does. People then use recovery codes, or a system manager resets their two-step sign-in (D-019).
- **Recovery codes:** 10 single-use codes, each 120 random bits (24 Crockford base32 characters in groups of 4). They are shown once and stored as SHA-256 hashes. ASVS 6.5.2 allows a plain hash at 112 bits or more, so checking a code is not ten scrypt runs. Making a new set replaces the old set, and each use is logged.
- **QR code:** the setup screen needs an encoder to show the `otpauth://` link as a QR code. Choosing one (for example `uqr`, MIT, no dependencies) is T-038's own dependency decision. Without one, the screen shows the key as text.
- **WebAuthn (passkeys) later, not now.** It needs CBOR and COSE parsing of authenticator data, which means either a library or a lot of hand-written parsing, and ASVS asks for phishing-resistant factors only at Level 3 (6.3.3). Factors are stored in their own table, keyed by type, so WebAuthn can be added later without a schema rewrite.
- **Required for every staff account (John, 2026-11-23; ASVS 5.0 6.3.3 Level 2).** A new account sets up two-step sign-in at its first sign-in, before it can do anything else; it can't be turned off, only reset (new secret, new recovery codes) by the person or a system manager. This replaces the plan's "optional, admins can require it" (§3).
- Resetting two-step sign-in, changing a password and changing the sign-in email all need the password again, and the second factor if it is on (ASVS 7.5.1). Afterwards the person is offered "sign out everywhere else" (7.4.3).

**Sessions: server-side in PostgreSQL**
- **The session token:**
  - The token is 32 random bytes from `randomBytes` (256 bits; ASVS 7.2.3 asks for 128). Only its SHA-256 hash is stored, so a database leak gives no usable sessions.
  - It is a new token at every sign-in and at any change of role or privilege (7.2.4).
  - Each session row holds the user, the one organization the session is working in (D-019), the creation and last-seen times, and the sites unlocked in it (T-019d).
- **The cookie:** `__Host-oculus_session`, with `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` and no `Domain` (ASVS 3.3.1–3.3.4), written only through T-022's cookie function.
  - The admin should be served from its own hostname, separate from the public sites (ASVS 3.5.4), so the session cookie is never sent to a public page. T-050 and T-051 set that up.
- **CSRF:** a token for each session, required on every change, together with T-022's Origin check.
- **Time limits:**
  - **4 hours idle (John, 2026-11-23)** and 12 hours absolute by default. John chose 4 hours so long cataloguing sessions aren't interrupted; it is longer than NIST SP 800-63B's 30-minute AAL2 figure, which is acceptable here because two-step sign-in is required for everyone. System managers can change both within bounds in System settings, and T-037 documents them as ASVS 7.1.1 asks.
  - There is no limit on parallel sessions, but a person can see their sessions and end any of them (7.1.2, 7.5.2), and a system manager can end anyone's (7.4.5). Deactivating an account or resetting a password ends all of its sessions (7.4.2, T-039).
  - Expired rows are deleted by a cleanup command any scheduler can run (D-035). An expired session is refused even if the cleanup never runs.
- **Rejected: signed tokens (JWT or signed cookies).** Sign-out, sign-out everywhere, deactivation and role changes would all need a revocation list in the database anyway (ASVS 7.4.1). A signing key would have to be managed and rotated, and the history of JWT algorithm-confusion bugs (for example GHSA-f67f-6cw9-8mq4 in Hono) shows the risk. PostgreSQL is already required, so stored sessions cost nothing extra.

**Site passwords (T-019d)**
- **Stored:** a site's password is hashed exactly like a user's password, as a PHC string on the site row. Only a system manager can set it, after entering their own password again. It is never shown or emailed.
  - Because many staff share it, its minimum is 15 characters (ASVS 6.2.1's recommended length), and it is checked against the same common-password and context-word lists.
  - The row keeps a version number. Changing the password raises the version, which ends every existing unlock.
- **Unlocking:** after sign-in, entering the right site password records an unlock (site and password version) on the server-side session row, never in a separate cookie, and issues a new session token. The unlock ends with the session or when the password changes. The service layer checks for the unlock on every request for that site, not only in the admin screens.
- **Rate limiting:** the same PostgreSQL throttle as sign-in, counted per user per site and per site overall, with growing delays and a temporary block (never a permanent lockout). Every failure is written to the change log, and the form is an 8 KiB form post with the CSRF token and the Origin check.
- Sources:
  - OWASP Password Storage Cheat Sheet, Session Management Cheat Sheet and Multifactor Authentication Cheat Sheet (github.com/OWASP/CheatSheetSeries); OWASP ASVS 5.0 chapters V3, V6 and V7 (github.com/OWASP/ASVS, 5.0/en). These were read 2026-11-23.
  - Node.js `crypto` docs (doc/api/crypto.md: `argon2` added in v24.7.0 and needs OpenSSL 3.2; `scrypt`'s `maxmem`) and the CHANGELOG_V24 entries for argon2, also read 2026-11-23.
  - RFC 6238 and RFC 4226. Their text could not be fetched in this run: the sandbox proxy blocked rfc-editor.org and ietf.org. The time step, the one-step drift window, the no-reuse rule (§5.2) and the 160-bit key length are as the RFCs state them, and T-038 should re-read them before building.

## D-053 — Record type edits and deletions list the records they strand (2026-11-23, autopilot T-013a)
`recordTypeChanges(oldType, newType, existing?)` and `recordTypeDeletion(type, existing?)` (record-type-changes.ts) are the record type counterpart of D-023 and D-031, with the same frozen `{ changes, needsConfirmation, recordsChecked }` and changes carrying `recordIds` (at most `MAX_LISTED_RECORDS`) and `recordCount`. The codes:
- `key_changed`: records naming the old key in `recordTypeKey` stop passing `checkRecordType` until moved; a new key another type has is refused (`key_taken`).
- `key_adopts_records`: records already naming the new key (left from a deleted type) are taken over; `mismatchRecordIds` are those of another kind (listed up to the cap, all counted in `mismatchCount`). Always needs confirmation; reported without `existing` in case there are any.
- `kind_changed`: the type's records whose kind isn't the new one (they fail with `wrong_kind`).
- `type_deleted`: the records naming the type.
- `unverified`: `recordTypeChanges` without `existing`. The old type is then only the caller's word (stale, or claiming the new kind already), so the edit always needs confirmation, even when the two versions look the same (found in review).

Each needs confirmation when it affects records, and always when `existing` isn't given. Label, description and default template edits aren't reported: the type never decides a record's template or what it publishes (D-037). The new type's default template isn't checked here; `validateRecordType` does that.
- **`existing` is `{ recordTypes, records }`, both required**; the old type must be in the list exactly (`type_not_listed`), so with `existing` a caller can't hide a kind change by claiming the old kind; without it, the edit always needs confirmation (`unverified`). An empty list means none.
- **One organization (D-030), checked first:** the new type's `organizationId` is compared with the old type's before its shape is checked, so another organization's malformed type gets only `mixed_organizations`; both lists are read slot by slot once, as own data properties, and their organization checked before any entry is validated or any key looked up, so another organization's list, valid or not, gets no message naming its keys. Any invalid entry, duplicate type key or record ID, hole, getter or Proxy refuses the whole check; `recordTypeKey` and `description` are read as own properties, so a polluted `Object.prototype` adds nothing. Lists are capped at `MAX_RECORD_TYPES` and `MAX_RECORD_SET`, refused before any slot is read.
- **Rejected:** checking the new default template here (that needs the template registry and is `validateRecordType`'s job); reporting label or default template changes (they strand nothing); a `recordTypeCreation` for a new type adopting left-over records (a type changes no publication, so this is only data hygiene; the rename case covers the common path).
- **Not covered:** `templateChanges` doesn't yet take `recordTypes` (a template edit that drops a kind a type's default needs is found by `recordTypeTemplateIssues`); records are not moved to a renamed key here, the caller does that.


## D-054 — Public output always needs the records and templates as they are now (2026-11-23, autopilot security S-010)
Supersedes the "rejected: making it required" parts of D-020 and D-021. `publicOutput` now requires `records` (the current set, a list or a lookup from `indexRecords`) and `templateFor` (a registry from `indexTemplates` or a lookup), for every view. Without `records` it refuses with `records_unknown` (path `["records"]`), without `templateFor` with `templates_unknown` (path `["templateFor"]`), both at once when both are missing, before anything else about the record is checked; the messages are fixed text. With them, every view goes through D-021's ancestry check (`record_changed`) and D-020's template check (`template_changed`), and a digital asset's deed check always finds what it represents in `records`.
- **Why always, not only for a kept view:** nothing in a view says whether it was made a moment ago or kept from earlier: it is an object held in memory, the same either way. The optional path published a value whose field had since been made staff, or inherited from a parent the record had since left, whenever a caller forgot the options. Failing closed is the rule elsewhere at this boundary (`identifiers_unknown`, D-038; `accessions_unknown`, D-043). The cost is small: a caller that builds the view and publishes it in one step already holds both, because `effectiveRecord` takes the same records and template lookup, and passing them again only repeats a cheap comparison.
- **`currentTemplate` is removed** (passing it is `invalid_options`). It compared only the record's own template, so with `templateFor` required it checked nothing `templateFor` doesn't; `ancestor_templates_unchecked` goes with it.
- **Rejected:** recognising a "fresh" view by remembering which records and lookup it was built from and skipping the check when the same ones are passed (a caller holding a stale snapshot would pass exactly the index the view was built from, and a lookup function can change what it returns); making views expire after a time (D-021: age doesn't say whether anything changed); leaving `publicOutput` optional and requiring the check only in the service layer (the boundary module is where the guarantee belongs, and the service layer doesn't exist yet).
- **Index once:** a `records` list is validated and indexed once per call, and the ancestry check, the represented-record deed check and the link deed check all read that one index (so a `templateFor` that changes the list can't change what later checks see); callers publishing many records should pass one lookup from `indexRecords` made at publish time. The ancestry and template checks run before the deed checks, so records it can't use are `invalid_options`. One indexing path in `effective.ts` (`lookupOf`: a lookup from `indexRecords` as it is, or a list indexed once) serves both this index and `recordSet`, which `makeRecordLinkChecker` and `indexAccessions` use for the set's organization (D-055).
- **Limits:** `publicOutput` can only compare the view with what it is given: that `records` and `templateFor` are the catalog as it is now is the caller's job. The service layer (T-032) and publishing (T-034) must load them at publish time, in the same read as the publish state, never from a cache. And a public site must never render a `publicView` (kept or fresh) directly: only `publicOutput`'s result goes out (T-050).
- **Tests:** `public-output.kept.attacks.test.ts` keeps a view, then makes a field staff, changes a parent's template, moves the record, and deletes the record or its parent; published without the current data each is refused and nothing private appears. Existing tests that built and published in one step now pass the records and templates the view was made from (`nowOf` in the fixtures).

## D-055 — Narrowed link kinds in template changes, and a staff report of stale link labels (2026-11-23, autopilot T-015a)
- **`record_kind_removed`.** `templateChanges` takes a fourth argument, `options`, whose `linkChecker` is the organization's `makeRecordLinkChecker`. When a `record_link` field's `recordKinds` narrows (no `recordKinds` counts as all six), the change lists the records linking to a kind the field no longer allows, with `removedCodes` naming the kinds dropped, and needs confirmation when any record is affected or none were given. Without the checker every record holding a link under the key is listed, since any may be affected. A link the checker can't resolve to a kind (a record it doesn't hold, such as a deleted one or one added after the checker was made, an ID used twice, an invalid record) is counted too: its kind is unknown, so it may be affected (fail closed, from the review). A place field always links to places, so it can't narrow; `record_link` to `place` is `kind_changed`. The checker must be one `makeRecordLinkChecker` made (a Proxy of one or a hand-made function is `not_a_link_checker`) for this template's organization (`wrong_organization_checker`; one that belongs to no organization, made from an empty set with none given, is `no_organization_checker`; both checked before any record is read); options that are a Proxy, not a plain object or hold a getter are `invalid_options`. No message names a kind's record, title or label.
- **`findStaleLinkLabels(organizationId, records, templates, options?)`** (link-label-report.ts), for Data Cleaning: the `record_link` and place values whose label differs from the linked record's current title (after NFC, trimming and collapsing white space; case counts), with the label and title quoted. **Staff only**: titles may be private. The caller names its organization; records of another organization (decided from every entry of the set, valid or not, so a set of another organization's invalid records is refused too), a set mixing organizations or another organization's template registry refuse the whole report, naming nothing, and a template a lookup gives for another organization skips that record. Titles come only from the records given, so a link to an ID outside them is only counted (`unknownTargets`). Only own values are read. Entries and skipped records are capped by `maxEntries` (default 500, at most 10,000) with full counts.
- **The checker's organization (review).** `makeRecordLinkChecker` took its organization from valid records only, so a set of another organization's invalid records made a checker with none, which `templateChanges` accepted and which counted nothing. Now the organization is the set's, read from every entry valid or not (as `indexRecords` already requires), and `makeRecordLinkChecker(records, organizationId?)` may be told whose records these must be (another organization's: `wrong_organization`; an empty set then makes that organization's checker). A checker of no organization (an empty set with none given) refuses every value that names a record with `no_organization_checker` (a place holding only a name needs no checker and passes); `publicOutput` refuses it outright as `checkers.record_link` or `checkers.place` (as it does another organization's), `effectiveRecord` shows none of its place names, and `templateChanges` refuses it. `indexAccessions` reads the records' organization the same way (another organization's invalid records are `mixed_organizations`) and makes its checker for the register's organization, so a set with no valid records gives `unknown_record`.
- **Rejected:** a list of target records as the `templateChanges` option (the checker already holds a per-organization snapshot of kinds and is what callers pass elsewhere); leaving links the checker can't resolve uncounted (first version: an empty, partial or stale checker then reported nothing and needed no confirmation, failing open). Counting them closes that for records the checker doesn't know, but not for a record it knows under an old kind: a checker made before a linked record changed kind still answers with the old kind and can under-report. So callers must make the checker from the organization's current records at save time, in the same snapshot as the records given; the service layer (T-032) does this; scanning values by shape without templates (a left-over or a field of another kind could be read as a link); case-insensitive matching (a case change in a title is a real difference staff may want to copy).

## D-056 — Structured access restrictions on accessions hold records back like an unsigned deed; "today" comes from the caller (2026-11-23, autopilot T-016a)
Extends D-043.
- **Shape.** An accession may have `accessRestriction`, one of `{ kind: "closed_until", until }` (`until` an EDTF day `YYYY-MM-DD`: the first day the records may be published, as the mockup's "Nothing from this accession will be published before then") or `{ kind: "staff_and_researchers" }` (never on the public site). One per accession, as the mockup offers one choice. The free-text `restrictions` stay notes in the donor's words and hold nothing; the mockup's "Other condition" is notes only. Malformed parts are refused (`invalid_restriction`, `invalid_date`, `unknown_property`) without quoting them (an unknown key is reported once at `accessRestriction` itself, never by name); only own data properties are read, both when checking and when the register judges restrictions, so nothing on `Object.prototype` can add, complete or end a restriction.
- **"Today" is given, never read.** `indexAccessions` requires `today`, the organization's calendar day in its own time zone, `YYYY-MM-DD` (`invalid_today` otherwise, including a `Date`, a number or an ISO instant). Core never reads the clock or converts an instant to a day, so a time zone edge is the caller's to get right (T-034 works it out from the organization's time zone). The register keeps it as `heldAsOf`. A `closed_until` restriction is in force while `today < until`, compared as days; `staff_and_researchers` always is. Precedent: `overdueLoans(book, today)` and `overdueReturns(log, today)`.
- **The hold is the deed hold.** An accession holds when its deed is `missing`/`sent` or its restriction is in force on `today`; the same traversal then holds what it produced, the units filed below, and the digital assets representing any of them. `accession-holds.ts` gains `holdReasons(id)` (`deed`, `restriction`) beside `isHeld`, so `effective.ts` and `public-output.ts` still never see an accession, a restriction's kind or its date. The publish check reports `deed_not_signed`, `access_restricted` or both, naming no accession, restriction or date. Links to a restricted record go out exactly as links to a deed-held one (through `isHeld`). New query `restrictionHoldsOn`; `recordsHeldBack` covers both reasons.
- **Freshness.** A register kept past its day still holds a restriction that has since ended (errs on holding). A register given a day later than the real one lets records out early; core can't detect that, so T-034 must build the register at publish time with the real day, and should rebuild published pages when a `closed_until` date passes (a follow-up, not a leak).
- **Rejected:** `today` as a `publicOutput`/`effectivePublishIssues` option (two more places to forget it, and a register would answer differently per call); reading the clock in core (untestable, and the server's UTC day is wrong for Texas evenings); an optional `today` that holds every `closed_until` when left out (silently "closed forever" hides a caller bug); restriction holds as a separate check from deed holds (two traversals that could drift apart); a list of restrictions per accession (the mockup offers one choice; more can come later as a schema change); a "researchers" role check here (reading-room access is the service layer's, T-041).

## D-057 — `packages/db` details: the migrations table, the lock, the sql tag's values, type parsers, test databases (2026-11-23, autopilot T-024)
How T-024 built D-049 and D-050.
- **Environment variables.** `npm run db:migrate` reads `OCULUS_DATABASE_URL` and never prints it (it may hold a password; put passwords in `~/.pgpass` or `PGPASSWORD`). **The migrating role** must own the database or at least hold `CREATE` on the `public` schema: since PostgreSQL 15, `public` is owned by `pg_database_owner` and ordinary roles can no longer create in it, and the bookkeeping table lives in `public`. It also needs **two connections at once** (the lock's and the files', below): a role or database `CONNECTION LIMIT` of 1, or a server at `max_connections`, stops the run before any file with `connection_failed`, whose message names the cause (SQLSTATE `53300`, too many connections). Tests read `OCULUS_TEST_DATABASE_URL` (D-049).
- **The empty schema.** `0001_migrations_table.sql` creates only `public.oculus_migrations (name text PRIMARY KEY, sha256 text, applied_at timestamptz)`, with checks on the name and hash formats. The runner treats it like every other file: it runs the file and inserts its row in the same transaction, so the table's own shape can change later through migrations. The runner always names it with its schema (`to_regclass('public.oculus_migrations')`, the `SELECT` and the `INSERT`), so a fresh database has nothing applied and no `search_path` can point it at another table.
- **Files.** Every entry in `packages/db/migrations` must be a file named `NNNN_lower_case_name.sql` (anything else, including a README or `.SQL`, is refused rather than skipped), non-empty and valid UTF-8; two files with the same number are refused. Gaps in numbering are allowed. The SHA-256 is of the file's bytes, so `.gitattributes` keeps migrations at LF line endings on every checkout.
- **Refusals,** checked under the lock before anything runs: an applied file missing or renamed (`missing`), edited by even one byte (`edited`), a pending file sorting before the last applied one (`out_of_order`), a server below 15 (`server_too_old`; above 19 only warns). A failing file rolls back completely and later files don't run; the codes are listed below, with `lock_lost`, `transaction_ended`, `commit_unknown`, `applied_not_recorded` and `connection_failed`.
- **The lock, on two connections.** The runner opens two connections. The **lock connection** (`application_name` `oculus-migrate-lock`) checks the server version, takes a session-level `pg_advisory_lock(0x6f63756c7573)` ("oculus"), holds it for the whole run and never runs a migration file. The **file connection** (`oculus-migrate`) reads what was applied and runs every file. A transaction-level lock would be released between files. Advisory locks belong to the session that took them, so nothing a file does on its own connection can release the runner's lock: `pg_advisory_unlock_all()` and `pg_advisory_unlock(<key>)` release nothing there, and `pg_advisory_xact_lock(<key>)` or `pg_advisory_lock_shared(<key>)` in a file wait behind the runner's own lock (the `pg_try_` forms return false), as tests show. The lock waits up to `lockTimeoutMs` (default 60 s, through `lock_timeout`, which in a test is shown to cover advisory locks) and then refuses (`lock_timeout`). A role, database or server `statement_timeout` shorter than that still ends the wait; that is reported as `lock_timeout` too, naming the `statement_timeout` (a test sets it with `ALTER DATABASE`). From PostgreSQL 17 a `transaction_timeout` does the same (it applies to a single statement's implicit transaction, and ends the session rather than the statement): the runner reads it with `current_setting('transaction_timeout', true)` (null before 17), and SQLSTATE `25P04` during the wait is reported as `lock_timeout` naming it (a test on 17 and newer; on older servers it checks the setting doesn't exist). The lock connection sits idle while each file runs, so it sets `idle_session_timeout` and `idle_in_transaction_session_timeout` to 0 for itself (session-level `set_config`) before waiting, and `statement_timeout` (and, only where the setting exists, `transaction_timeout`) to 0 once it holds the lock; otherwise a role or database `idle_session_timeout` shorter than a file would end it and lose the lock (a test: `ALTER DATABASE … SET idle_session_timeout = '1s'` and a 2-second file). `lock_timeout` stays set, so its own checks can't wait forever. A second runner that waits finds nothing left to do; a test with a file that tries to swap the lock shows the second runner starts only after the first finishes. At the end the file connection is closed first, then the lock is released. Closing a connection doesn't wait for its server process: after a network drop the server may still be running a file's statement until it notices, so a second run could start while it finishes. The primary key on `oculus_migrations.name` is the final protection: the same file can't be recorded twice.
- **One transaction per file, checked.** A file is recorded, or reported as plain `failed`, only when the runner can prove the file never left the runner's own transaction; anything else is `transaction_ended`. The exact rules:
  - **Before the file:** `BEGIN`, then the transaction is given an ID (`pg_catalog.pg_current_xact_id()`), then `SAVEPOINT oculus_migration`. The file runs as one simple-protocol script.
  - **"Still in the runner's transaction"** means all three: the server's last ReadyForQuery said "in a transaction block" (`T`); `pg_catalog.pg_current_xact_id_if_assigned()` equals the ID read before the file (IDs are never reused, so a file that ended the transaction in any way, `PREPARE TRANSACTION` included, can't be in it again, and then no other transaction can have committed in between); and `pg_catalog.pg_xact_status` of that ID is `in progress`. `pg_xact_status` alone is not enough: after `PREPARE TRANSACTION` the ID is still `in progress`, in a prepared transaction.
  - **After a file that succeeded:** the block must still be `T`; then, inside the transaction, the session is reset (`RESET ALL`, `RESET ROLE`, `RESET SESSION AUTHORIZATION`, `DISCARD TEMP`, `DEALLOCATE ALL`) so a file's settings, temporary tables and prepared statements can't touch the runner's own statements; then "still in the runner's transaction" must hold (this also catches `PREPARE TRANSACTION`, which ends the runner's transaction ID; prepared transactions of other applications in the same database are not the file's and don't matter); then the runner must still hold its advisory lock (below). Then the bookkeeping `INSERT`; then `SET CONSTRAINTS ALL IMMEDIATE`, which runs the file's deferred constraints and triggers now instead of at `COMMIT` (one failing is `failed`, naming the file); then the file's row (name and hash) must still be in `public.oculus_migrations`, else `transaction_ended` (a trigger in the file deleted or changed it; the transaction is rolled back, so the file is not applied without its row); then the lock must still be held. Only then `COMMIT`. After it the file's row (name and hash) is read once more on the file connection: a deferred trigger can still run at the `COMMIT`, because one fired by `SET CONSTRAINTS ALL IMMEDIATE` can run `SET CONSTRAINTS ALL DEFERRED` and queue another (say by inserting into a table with a deferred trigger), which then deletes or changes the row after the check before the `COMMIT`. If the row is missing or different (or can't be read), the run stops with `applied_not_recorded`: the file was applied but its record is missing, and a person must check the database and record it by hand (the message gives its SHA-256); a test shows this and that later files don't run. The check before the `COMMIT` stays, so the ordinary case is still rolled back. Then the lock is checked once more, and if it was lost the run stops with `lock_lost`, saying the file was applied and recorded.
  - **At the runner's `COMMIT`:** deferred constraints have usually already run, but a trigger can defer them again (as above); if the `COMMIT` fails on the server, the transaction ends aborted (`pg_xact_status` says `aborted`): reported as `failed`, naming the file ("failed at COMMIT"), with nothing applied or recorded (a test: a deferred trigger re-defers constraints and inserts a row whose deferred foreign key fails at the runner's `COMMIT`). If the server can't be asked afterwards (the connection was lost during `COMMIT`), the outcome is unknown: `commit_unknown`, and the message says a person must check whether the file is recorded in `public.oculus_migrations` and its changes are there. (A test drops the connection at `COMMIT` through a socket proxy.)
  - **After a file that failed:** a statement that fails inside the runner's transaction leaves the block failed (`E`). So if the session is not in a failed block (it is outside any block, or in one that still runs queries), the file ended the runner's transaction: `transaction_ended`. In a failed block the runner runs `ROLLBACK TO SAVEPOINT oculus_migration`, which works only inside the runner's own transaction (unless a file made a savepoint of that name itself, which the next check catches); if it fails, `transaction_ended`. Then "still in the runner's transaction" must hold, else `transaction_ended`. Then the runner rolls back, and `pg_xact_status` of its ID must be `aborted`, else `transaction_ended`. Only a file that passes all of this is reported as `failed`, and nothing of it stays.
  - **So these are `transaction_ended`:** `COMMIT`, `END`, `COMMIT AND CHAIN` and `ROLLBACK` in the file, with or without a new `BEGIN`/`START TRANSACTION` after, whether the file then succeeds or fails (for example `ROLLBACK; CREATE TABLE ra (id int); COMMIT; SELECT * FROM nowhere;`, which leaves `ra` committed). A file that rolls back the runner's transaction and commits nothing of its own is reported the same way, because the runner can't tell it apart from one that did. `PREPARE TRANSACTION` is `transaction_ended`, and the message names the gid of the prepared transaction whose transaction ID (`pg_prepared_xacts.transaction`) is the runner's own, and says to resolve it with `COMMIT PREPARED` or `ROLLBACK PREPARED`; another application's prepared transaction is never named. A file that releases the runner's savepoint (`RELEASE SAVEPOINT oculus_migration`) and then fails is reported as `transaction_ended` too: the runner's `ROLLBACK TO SAVEPOINT` then fails, so it can't prove it is still in its own transaction, although in fact the runner's `ROLLBACK` undoes the whole file (a test shows nothing stays). A file that releases the savepoint and succeeds is checked like any other and recorded. If the runner can't ask (the connection is gone), it is `transaction_ended` too. The message always says the file is not recorded and a person must check the database, including `pg_prepared_xacts` for a prepared transaction the file left (the runner names one only when its transaction ID is the runner's own; if the connection was lost it can't look).
  - **After every file** the session is reset again; if that fails after the file committed, the run stops with a message saying the file was applied and recorded.
  - The runner names its table, functions and casts with their schemas (`public.oculus_migrations`, `pg_catalog.*`). Statements that can't run in a transaction (`CREATE INDEX CONCURRENTLY`) are not supported; if one is ever needed, it gets its own decision.
- **Checking the lock.** A file can still end the lock connection (`pg_terminate_backend`, as a role allowed to signal it). So before each file, before each file's bookkeeping `INSERT`, again just before its `COMMIT` (after its deferred triggers ran), after the `COMMIT`, and after a file fails, the runner asks the lock connection itself: it must answer, still be the backend (`pid`) that took the lock, and `pg_catalog.pg_lock_status()` (the function behind `pg_locks`) must show that `pid` holding the advisory lock `granted` in mode `ExclusiveLock` in its own database (`database` compared with `datid` from `pg_catalog.pg_stat_get_activity(pid)`, `classid` and `objid` the key's high and low 32 bits, `objsubid = 1`). The check reads only these shared-memory functions and takes no catalog table locks beyond parsing, so a file holding a lock on a catalog (`LOCK pg_catalog.pg_database`, tested) can't make it wait and report a false `lock_lost`. If the lock is lost before the `COMMIT`, the file is rolled back and the run stops (`lock_lost`; after a failed file the message says it failed too); after the `COMMIT`, the message says the file was applied and recorded. A file can itself cause a loss at the end of its transaction, with a deferred trigger that ends the lock connection: that is why deferred triggers run (`SET CONSTRAINTS ALL IMMEDIATE`) before the last check, and a test shows such a file in last place is `lock_lost`, not a silent success. A lock lost in the instant between the last check and the `COMMIT` (the network, an administrator) is reported after the `COMMIT`; a second runner could by then have started, and would wait on the file's locks or find the file applied, and the primary key on `oculus_migrations.name` stops a second record of the same file. The earlier check of `pg_locks` on the file's own connection was dropped: a file could fool it (unlock, then take the key again as a transaction or shared lock).
- **Recording failures.** If the bookkeeping `INSERT` fails, the message blames the first migration ("must create public.oculus_migrations") only when the table doesn't exist (SQLSTATE `42P01`); any other cause is reported as itself.
- **The `sql` tag's values.** Strings, finite numbers, bigints, booleans, null, valid Dates, `Uint8Array` (bytea) and arrays of these (up to 6 deep, no holes), copied when the query is made. Refused: `undefined`, NaN and infinities, plain objects (JSON is `${JSON.stringify(v)}::jsonb`), objects with `toPostgres`, functions, symbols, fragments inside arrays, more than 65,535 parameters. Fragments made by `sql` (or `joinSql(fragments, separator)`) are spliced in with their parameters renumbered; a fragment is recognised by a private-field check, not `instanceof`, so a forged object is just a refused value. There is no identifier or raw helper. Two placeholders may not touch (`${a}${b}`, or `joinSql` with an empty separator, would give `$1$2`), and a placeholder may not touch the text around it: an identifier character, digit or `$` just before it (`col${x}`, `$${x}`) or just after it (`${x}0` would read `$10`) is refused when the query is made.
- **Lint.** Outside `packages/db`, importing `pg`, `pg-*`, `pgpass`, `postgres`, `postgres-*` or `@types/pg` is refused, including `import()`, `require()` and `import x = require()`. Outside `packages/db/src/client.ts`, any `.query(` call is refused; `sql(...)`, `sql.call`, `sql.apply` and `sql.bind` are refused everywhere. This covers `.ts`, `.mts`, `.cts`, `.tsx` (all parsed as TypeScript by `eslint.config.js`) and JavaScript files, tested through the real config, and `client["query"](...)`. Lint is a guardrail for mistakes; the run-time checks in `sql.ts` and `client.ts` are the real guard. `client.ts` itself sends only `sql` values, always with the extended protocol (`queryMode: "extended"`; pg would otherwise send a query with no values by the simple protocol, which runs several statements); its two internal exceptions are the runner's whole-file script (simple protocol, from `packages/db/migrations` only) and `createDatabase` / `dropDatabase`, which accept only names matching `^[a-z][a-z0-9_]{0,62}$`. These are not exported from the package.
- **Type parsers,** per connection, never pg's global ones: `int8`, `numeric`, `date`, `timestamp`, `timestamptz`, `interval` and their arrays come back as the server's text. Every session sets `TimeZone=UTC`, `DateStyle=ISO,YMD` and `IntervalStyle=iso_8601`, so that text is the same on every server (`2026-11-23 12:00:00+00`, `P1DT2H`).
- **Test databases.** Each test file creates its own databases (`oculus_test_` + 16 random hex digits, from `template0`, UTF-8) and drops them `WITH (FORCE)` afterwards. Database tests set up inside each test rather than in `beforeAll`, so with no server every test fails on its own instead of being reported as skipped. Cloning a migrated template database waits until migrations take long enough to matter.
- **The gate's throwaway server** (`scripts/test-database.mjs`): `initdb --no-sync --no-locale -E UTF8 -U postgres -A trust`; the server settings go on `pg_ctl -o` (`-h ''` so no TCP, `-k <dir>` with socket permissions `0700`, `-F` for fsync off, `synchronous_commit` and `full_page_writes` off), and the directory path must be shell-safe because pg_ctl hands `-o` to a shell. Nothing is written into the data directory by root. `initdb` and `pg_ctl` get only a fixed `PATH=/usr/bin:/bin` and a C locale, never the caller's environment, and `runuser` is called by its full path. Two commands still use the caller's `PATH`: `pg_config --bindir` (only to find the binaries when `PG_BIN` is not set) and, under uid 0, `id -u postgres` / `id -g postgres` (to chown the directory). The server also gets `max_prepared_transactions=10`, so the runner's `PREPARE TRANSACTION` test runs. `PG_BIN` must hold both `initdb` and `pg_ctl`. The server runs only for the test step. Stopping tries `-m fast`, then `-m immediate`; if it is still running, its directory is left and reported, never deleted under a live server. Gate steps run as async child process groups, so SIGINT, SIGTERM or SIGHUP stop the running step and then the server at once. About 1 second in the sandbox.
- **CI** runs the gate against `postgres:15` and `postgres:19` (19 is published: the official-images library lists `19.0, 19, latest`, read 2026-11-23), `POSTGRES_HOST_AUTH_METHOD: trust`, a `pg_isready` health check, port 5432 on `localhost`, as GitHub's service-container guide shows. A step before the gate sets `max_prepared_transactions = 10` with `ALTER SYSTEM` and restarts the service container (a service container can't be given server options), waits up to 60 s for `pg_isready` (if the server isn't back by then the step fails with a clear error and the container's last log lines), and checks the setting took; without it the prepared-transaction test fails rather than skipping. The matrix jobs are `gate-postgres`; a final job named `gate` needs them and passes only if all passed, so a single required check named `gate` keeps working. The images are not pinned to digests: docker-library's repo-info lists them, but no digest could be checked against the registry from the sandbox (Docker Hub was blocked), so pinning waits for a run that can check one.
- **Rejected:** the runner creating its table in code (its shape could then only change in code); `pg_try_advisory_lock` in a loop (busy waiting); the lock on the same connection as the files (a file can release it and take the key again in another form, which no check can tell apart); treating every prepared transaction made during a file as the file's (another application's would be blamed); pg's global type parsers (they change every `pg` user in the process); timestamps as JavaScript Dates (local-time shifts, lost microseconds); refusing gaps in numbering (no safety gained); skipping unknown files in the migrations directory (a misnamed migration would silently never run); an identifier helper in the tag (no query needs one yet).
- Sources: https://www.postgresql.org/docs/15/runtime-config-client.html (`lock_timeout`), https://www.postgresql.org/docs/15/explicit-locking.html (advisory locks), https://www.postgresql.org/docs/17/runtime-config-client.html (`transaction_timeout`), https://www.postgresql.org/docs/17/errcodes-appendix.html (`25P04`), https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers, https://github.com/docker-library/official-images/blob/master/library/postgres (all read 2026-11-23).

## D-058 — The HTTP layer's own choices on top of D-051 (2026-11-23, autopilot T-022a)
`packages/api` builds the server with `buildServer(options)`. Choices D-051 left open, revised after the independent review:
- **A narrow route API.** Application code passes `OculusRoute`s (method, path, `form`, `credentials`, handler) and never gets the Fastify instance, request or reply. Handlers get:
  - an `OculusRequest`: a frozen copy of the method, path, parameters, query, parsed body (deep-frozen), client address, host, scheme, the well-formed Oculus cookies and seven ordinary headers (`Accept`, `Accept-Language`, `Content-Type`, `If-Match`, `If-Modified-Since`, `If-None-Match`, `User-Agent`). Never the Fastify request: from it `request.server` reaches the Fastify instance and the listening `http.Server` (`close()`, `prependListener`), and `request.raw.socket._httpMessage` the raw response. Host and scheme are included because absolute links (OAI-PMH, IIIF) need them; like the address they come from the trusted proxy only.
  - an `OculusReply` (status, checked headers, content type, the cookie writer): no `hijack`, no `raw`, no `Set-Cookie`, and every method throws once the handler has returned.
  - a `signal` (AbortSignal) that fires when the handler timeout has sent its 503 or the client has gone away; from then on every reply method throws, so a late handler can't change anything, and a handler with side effects (writes, outbound requests) should pass the signal on and stop. It is driven by the response closing, not by Fastify's `request.signal`, which also fires as soon as a request body has been read.
  So no route can add parsers, hooks or error handlers, raise its body limit or timeout, reach the socket or server, or write cookies around the writer. As a second line, onRoute refuses any route option outside the few the API uses, any prefix, and any body limit other than 8 KiB on credentials routes; route config is frozen; and the instance is ready (Fastify then refuses changes) before anything else can reach it.
- **Whatever a handler throws never reaches Fastify.** The route wrapper catches every throw and rejection and puts a fresh `Refusal` in its place: rebuilt from the thrown Refusal's own status and code if both are data properties and valid, otherwise a plain 500 `internal_error`. Nothing is read from the thrown value outside a try/catch and only own data properties are read, so no getter it carries is called; a Proxy's traps (`getPrototypeOf`, `getOwnPropertyDescriptor`) do run, inside the try/catch. If even the fresh 500 can't be built (a setter added to `Refusal.prototype`), a frozen 500 built at start-up is used, so the rebuild never throws; a Refusal's fields are defined, never assigned, so such a setter doesn't run anyway. Fastify, its default error handler (which copies `error.headers` onto the reply and sends the message: CORS, a `Refresh` open redirect, `Strict-Transport-Security: max-age=0`, framing headers, CR LF errors), diagnostics_channel subscribers and pino only ever see the fresh value: frozen, data properties only, `stack` included. The log gets one fixed-shape record per failure (`failure`: status, code, and the thrown value's name, message and V8 stack, as plain strings, read from own data properties, or from V8's own stack getter only when every prototype of the value is a built-in Error prototype and its own `name` and `message` are data: formatting the stack reads `name` and `message` and would run a getter there, so a subclass or anything else gets no stack in the log), never the thrown object. A handler that wants a 4xx throws a `Refusal`; any other thrown value, even one with a `statusCode`, is a 500.
- **A failure after the reply is sent is logged by Oculus, not Fastify.** When a handler rejects or returns after its timeout's 503 has gone out (or the client has left), the wrapper checks the signal and `reply.sent`, logs the same fixed-shape `failure` record with the method and path, and hands Fastify nothing: Fastify would have logged `{ err }` (pino's error serializer writes to the error and throws on a frozen Refusal), then sent that TypeError and logged `FST_ERR_REP_ALREADY_SENT`, whose message holds the full URL, query string included. `reply.sent` is checked again before the final `send`.
- **No log line holds a query string or an error object.** Besides the `req` serializer (method and path), the logger's `err` serializer returns a fixed `{ type: "omitted" }` without looking at the error, and a pino `logMethod` hook rebuilds every call (Fastify's and Oculus's): a merging object keeps only `req`, `res`, `failure`, `responseTime` and `statusCode` (an `Error` or `err` becomes the fixed value, so its message never becomes the log message), the message has anything from `?` to the next space removed (Fastify writes `request.url` into "Reply was already sent … in "/x?q=…"" and "Route GET:/x?q=… not found"), and printf-style arguments are dropped.
- **5xx log redaction policy.** The `failure` record holds the thrown value's name (100 characters), message (500) and stack (4,000) as the handler made them: whatever a handler puts in an error message (a query value, part of a record) reaches the server log, so handlers must not put secrets or personal data in error messages. The log never holds the request's query string, headers, cookies, address or body. Shipping and keeping logs is part of deployment (D-035).
- **The error handler can't throw.** It reads errors only through `errorReply` (own data properties, never throws) and is wrapped in a try/catch whose fallback writes a fixed `{"error":"internal_error"}` 500 with the security headers straight to the response (or closes the connection if the reply has started), so Fastify's own default and fallback error handlers are never reached, even when the logger's stream throws.
- **A `Refusal` is 400 to 599 with a code like `not_found`** (`^[a-z][a-z0-9_]{0,63}$`); the constructor throws otherwise (a 1xx desyncs the connection, a status outside 100–999 makes Node throw, a 2xx or 3xx isn't an error), and the rebuild checks both again.
- **Handlers return plain data, a string or nothing.** Plain objects (or null-prototype ones) and arrays of strings, finite numbers, booleans and null are copied as they are checked (so a Proxy can't change them afterwards) and sent as JSON; a string is sent as it is. A Web `Response`, a stream, a Buffer, a Date, a class instance, a function, a getter, a cycle, nesting deeper than 256, an array longer than 100,000 items, more than 1,000,000 values in all (an array's `length` is read with one descriptor, and an object's `Reflect.ownKeys` counted against what is left of the budget, before any entry is read, so a 3,000,000-item array or a million-key object is refused without building a descriptor per entry), or more than 16 MiB of text (strings and keys, in UTF-8; a text result too) is a 500 `internal_error`. Values are counted at every visit, so an object shared from many places (whose copy would double at every level) can't run the server out of time or memory: Fastify copies a `Response`'s headers after the onSend checks, so a `Response` could send any `Set-Cookie` or a false `Content-Length` (response desync). Files and images (Phase 3) will need their own decision. With this, HEAD on a GET route always answers the GET reply's status and headers with no body.
- **Response headers: an allowlist.** Names must be RFC 9110 tokens and values free of control characters other than tab (Node's own rule), so Node's own header errors (whose text names the header) never run. A handler may write only these, each with a value of a fixed form, and everything else is refused (`X-Accel-Redirect`, `X-Sendfile`, `Set-Cookie`, framing, CORS, `Refresh`, caching headers (`Cache-Control`, `Expires`, `Pragma`, `Surrogate-Control`), `Link`, `Alt-Svc`, `NEL`, `Report-To`, `WWW-Authenticate`, `Content-Disposition`, custom `X-` headers and anything new):
  - every value at most 1,024 characters;
  - `Content-Type` only through `type()`: `type/subtype` with token parameters (no quoted strings), never active content (`text/html`, `image/svg+xml`, `application/xhtml+xml`) and no charset but `utf-8`, until server-built public pages get their own decision (D-034);
  - `Content-Language`: comma-separated language tags;
  - `ETag`: a strong or weak entity tag (RFC 9110 §8.8.3);
  - `Last-Modified`: an IMF-fixdate naming a real moment (the right weekday, no 30 February or hour 25);
  - `Vary`: comma-separated header names, never `*`;
  - `Location`: a same-origin path only (`/x`, not `//host` or `/\host`);
  - `Retry-After`: at most 86,400 seconds, or a real IMF-fixdate no more than a day ahead.
  `Cache-Control` is not on the list: every reply gets `no-store` and a handler can't weaken it; caching of public responses is a decision for later. `Link` is not on it either: no current route needs it, and `rel=preconnect`/`preload` reach other hosts; OAI-PMH or IIIF paging links, if needed, will add `Link` with same-origin targets and named `rel` values. Every reply, error replies, the router's own errors (`frameworkErrors`: a URL it can't decode such as `/items/%C0%AF`, a parameter longer than 100 characters; these skip onSend, so the headers are set there) and Node-level parse errors included, carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; form-action 'none'; base-uri 'none'` and `Cache-Control: no-store`; handlers can't change them.
- **An error reply drops everything the handler set** (headers, cookies, status, `Location`) before `{ "error" }` is sent.
- **`@fastify/cookie` is dropped (a change to D-051).** Its `setCookie` parses every request cookie into `request.cookies`, its parser keeps the first of two copies, and its serializer only loads when the plugin is registered. Oculus reads its own names from the raw header and writes its fixed `Set-Cookie` text itself; names, values and the Cookie header must be `typeof "string"` before any other check (an object's `toString` could pass the check and then write something else); just before sending, every `Set-Cookie` must be one the writer issued for that reply and pass a browser-style attribute check (names without case, each attribute once, only `Path=/`, `HttpOnly`, `Secure`, `SameSite=Lax|Strict`, `Max-Age`).
- **Duplicate Oculus cookies refuse the request (trade-off).** Whoever can plant a second copy (a sibling subdomain can't set a `__Host-` cookie, but a case variant or a script on the same origin can) can make that browser's requests fail with 400 until the copy is cleared. The alternative, picking one copy, lets a planted cookie win (session fixation). Refusing is the safer failure.
- **Error replies are `{ "error": "<code>" }` and nothing else**, with `Cache-Control: no-store`, including requests Node itself can't parse (`clientErrorHandler`: 400, 408 or 431). Codes: `bad_path`, `cross_origin`, `duplicate_cookie`, `forbidden_key`, `repeated_key`, `repeated_field`, `too_deep`, `bad_number`, `bad_body`, `unsupported_media_type`, `payload_too_large`, `not_found`, `method_not_allowed`, a generic code per status for other 4xx, and `internal_error` or `unavailable`. The request log holds the method and path only.
- **Bodies, stricter than D-051 asked:** valid UTF-8 without a byte order mark; JSON nested at most 64 deep, no key twice in one object (compared after unescaping), no number too large for a double, no `__proto__`, `constructor` or `prototype` key (as `@oculus/core`); forms decoded strictly (bad `%` sequences and bad UTF-8 refused), no field twice; Content-Type whitespace exactly as RFC 9110 §8.3.1 (spaces or tabs around `;`, none around `=`); two `Content-Type` headers refused.
- **Paths, stricter than D-051 asked:** also refuse `%2E`, percent-encoded letters, digits, `-`, `_` and `~` (`/item%73`), double encoding, control characters, `//` and anything that isn't an origin-form path. An empty `:param` (`/items/` reaching `/items/:id`) is answered 404 before the handler.
- **405 needs a route table of our own,** because Fastify answers a wrong method with 404 and doesn't expose its router. `checkRoute` reads each field of an application route once and returns a frozen copy, and only the copy is registered (a `method` getter can't say GET to the check and TRACE to Fastify); onRoute also refuses any method other than GET, POST, PUT, PATCH, DELETE and the HEAD Fastify adds for GET. Paths use only static segments, whole-segment `:name` parameters and a final `*`, with no prefixes; other find-my-way syntax stops the server from starting.
- **Same origin from configuration, not from `Host`:** `OCULUS_ORIGINS` (required) lists the install's bare origins, https only except on localhost. A change passes when its `Origin` is listed and names the host the request was sent to (so one Oculus site can't post to another), or when it has no `Origin` and says `Sec-Fetch-Site: same-origin`; any disagreeing signal refuses.
- **`OCULUS_TRUSTED_PROXY`** takes IP addresses, CIDR ranges and `loopback`, comma-separated. A range may be no wider than /16 (IPv4) or /32 (IPv6) unless it lies inside 10/8, 172.16/12, 192.168/16, 127/8, fc00::/7 or ::1. IPv6 ranges inside a block that carries IPv4 addresses (::ffff:0:0/96, ::/96, 64:ff9b::/96, 2002::/16) get the IPv4 rule for the IPv4 range inside them, and a range wider than such a block (`::/32`) is refused, so no IPv6 spelling trusts all of IPv4. Zone ids (`fe80::1%eth0`), `true`, `*`, hop counts and names stop the server from starting.
- **Cookie `Max-Age` is at most 400 days** (the cap browsers apply, RFC 6265bis §5.6.2), the same limit in the writer and in the check before sending.
- **Timeouts:** idle socket 30 s, whole request 30 s, headers 10 s (checked every second), keep-alive 5 s, handler 30 s (then 503, the request view's `signal` fires and the reply stops working; the handler itself can't be stopped from outside, so it should watch the signal). Two limits of the design: Fastify's handler timer starts when the request is routed, before the hooks run and the body is read, so a slow upload uses up the handler's time; and the signal is driven by the response's `close` event, so it fires when the 503 has been flushed to the client (a slow reader delays it), not the instant the timer runs out. Node's defaults are none, 300 s and 60 s; Fastify's keep-alive is 72 s. Options can only shorten them. Large uploads (Phase 3) will need their own decision.
- **Not covered:** handlers run in the same process and the same JavaScript realm, so code that imports Node or Fastify itself (`node:http`, `process`, a module-level reference to the server) or changes shared built-ins (`Error.prototype`, `Object.defineProperty`, `Error.prepareStackTrace`, `Refusal[Symbol.hasInstance]`, `JSON.stringify`) is outside what the API can stop: every guarantee here is against the values a handler returns, throws or passes, not against code that patches the globals the HTTP layer itself uses. Review catches that.
- **Left for later decisions:**
  - `return503OnClosing`: while the server is closing Fastify answers new requests with its own 503 (its own body, none of the default headers, written before any hook). Turning it off lets requests run against a server that is shutting down (and its database pool); keeping it means a short window of replies without nosniff or the CSP. ## D-060 — The first catalog schema: composite keys with `organization_id`, versioned JSON for templates and record types, core validating both ways (2026-11-23, autopilot T-025)
`packages/db/migrations/0002_catalog.sql` creates `organizations`, `templates` and `template_versions`, `record_types` and `record_type_versions`, and `records`; `packages/db/src/catalog.ts` reads and writes them.
- **Separation is in the keys (D-019).** Every table but `organizations` has `organization_id NOT NULL`. Templates and record types are keyed `(organization_id, key)`, so two organizations can use the same key. Records are keyed `(organization_id, id)`, with no key on `id` alone: two organizations can hold the same record ID, and one organization's insert is never refused because of another's row, so it learns nothing about the other's IDs (the service layer still makes every ID as a random version 4 UUID; a person never chooses one). Every foreign key between catalog rows is composite and names the organization on both sides: a record's template, record type, parent and represented record, a record type's default template, a version's template or type. So no row can point at another organization's, whatever the application sends.
- **What identifies a row never changes.** A `BEFORE UPDATE` trigger on every catalog table (`catalog_keep_identity`) refuses any change to `organization_id` and to the columns that identify the row: an organization's `id`; a template's or record type's `key`; a version's `key` and `version`; a record's `id`. It raises SQLSTATE `23000` with the constraint `<table>_<column>_fixed`. The foreign keys alone weren't enough: a row nothing points at (a lone record, a template identity with no versions, any version row, whose key the other organization may also use) could be moved to another organization with one `UPDATE`. Tests try each with direct SQL. *Rejected:* single-column foreign keys plus application checks (a forgotten filter would link across organizations silently); row-level security as the only guard (it depends on the session role and settings, and doesn't stop the owner; it may come later as a second line for the public role, D-034); relying on the foreign keys to stop moves (they stop only rows that point or are pointed at).
- **Templates and record types: an identity row plus one row per version.** `templates (organization_id, key)` is what records and record types point at; `template_versions (organization_id, key, version, definition jsonb)` holds every version as the JSON `validateTemplate` accepted, and the highest version is current (records follow the current version, D-029). Record type versions also keep `kind` and `default_template_key` as columns, so the default template is a foreign key. Checks tie the JSON's `key`, `organizationId`, `kind` and `defaultTemplateKey` to the row's columns. `insertRecordTypeVersion` takes no template from the caller: it reads the current version of the type's default template from the database, checks the type against it, and inserts only if that version is still the current one with the same JSON, tested in the insert statement itself; otherwise it stores nothing and returns `template_changed`. (A version committed at the very moment the statement starts can still slip past; `readRecordType` checks against the current template on every read, so such a type reads as issues, never as valid.) A new version is one statement (`INSERT … ON CONFLICT DO NOTHING` for the identity, then `max(version) + 1`); two saves of one key at once can't take the same number, the second fails on the primary key. *Rejected:* a `current_version` column on the identity row (a second source of truth, and a circular foreign key); one table with `(organization_id, key, version)` (records could then only point at a version, which D-029 rules out). Who may write versions and that history is append-only is T-029's (database roles).
- **Records.** Columns for what every kind has (`kind`, `template_key NOT NULL`, `record_type_key`, `title`, `fields jsonb`, `created_at`, `updated_at`) and for what some kinds have (`level`, `parent_id`; `media_type`, `represents_id`; `agent_type`; `latitude`, `longitude`), with checks that each kind has exactly its own. `template_key` is NOT NULL as D-029 planned: there are no stored keyless records to migrate, so `insertRecord` refuses one (`no_template_key`). Timestamps are `timestamptz` holding whole milliseconds (a check), read back with `to_char` in core's `2026-11-20T16:05:00.000Z` form, so they round-trip exactly. *Rejected:* the whole record as one JSONB document (no foreign keys or checks on parent, template or kind); a table per kind (the arrangement and links point at any kind).
- **Checks back up core, never go beyond it.** Kinds, levels, agent types, the media type pattern, key and title rules, UUID version 4, `jsonb` objects, coordinates in range, no self-parent or self-representation (named constraints), `updated_at >= created_at`. Each is implied by core's validators, so nothing core accepts is refused. One edge: core accepts years 0000 and earlier than PostgreSQL's range, which a `timestamptz` refuses; `createRecord` stamps the current time, so only a hand-made record could hit it. **Left to the service layer (T-032), with core's checks:** cycles in the arrangement (a unit filed under its own descendant), the parent being an archival unit at a higher level, a record type of the record's kind, a template that applies to the record's kind, and a record's fields against its template (that needs the organization's identifier types and records). SQL can't see these without triggers, and core already has them (`validateArrangement`, `checkRecordType`, `checkRecordAgainstTemplate`). **Links inside `fields`** (`record_link` values) are JSON, with no foreign key: checking that each names a record of the same organization (`checkRecordAgainstTemplate` with the organization's `makeRecordLinkChecker`) and refusing to delete a record others link to are the service layer's too. `insertRecord` checks the record's shape only, so its callers must run that check first. **The service layer also** makes record IDs, and never passes a database error's text to a person: `pg`'s messages name tables, constraints and values, so it maps them to its own.
- **Nothing cascades.** Deleting an organization, a template or a record that another row points at through a column (a parent, a represented record, a template, a record type) is refused. A record linked to only from another record's `fields` is not protected by the database (above).
- **No size check on `fields` or `definition`.** A `CHECK (pg_column_size(...) <= n)` was considered and left out: `pg_column_size` measures the stored, possibly compressed, size, so whether a value fits would depend on how well it compresses, and the checks never go beyond core. Size is bounded before the database: the API refuses bodies over its limit (1 MiB by default, D-051), and core limits field counts and text lengths.
- **Core validates both ways.** Inserts validate with core and store the validated copy, or return the issues and touch nothing. Reads take the organization, rebuild the core value from the row and validate it again (a template with `validateTemplate`, a record type with `validateRecordType` against the current version of its default template, a record with `validateRecord`), and compare its organization and key or ID with the row; a row changed by hand comes out as issues. Database errors are thrown as `pg` reports them.
- **What doesn't round-trip exactly.** JSON is stored as `jsonb`, which keeps the data, not the text: object keys come back sorted (shortest first, then by bytes), not in the order written, and `-0` comes back as `0` (`JSON.stringify` already writes it as `0`). Nothing in Oculus may depend on key order or on `-0`. Numbers in `jsonb` are `numeric`, so a number `JSON.stringify` wrote comes back as the same JavaScript number; `latitude` and `longitude` are `double precision`, which come back exactly only while the server's `extra_float_digits` is above 0 (the default, 1, since PostgreSQL 12 gives the shortest text that reads back as the same number). A server or role configured with 0 or less would round coordinates; don't.
- **`@oculus/db` depends on `@oculus/core`.** Type checking and lint read core's sources (`paths` in `packages/db/tsconfig.json`, whose `rootDir` is `packages/`); the build narrows `rootDir` to `src` and reads core's built types, and core builds first because workspaces build in name order. `npm run db:migrate` builds core itself before building `@oculus/db`, so it works on a fresh clone; `scripts/db-migrate-build.test.mjs` runs it in a copy of the two packages with nothing built. Vitest aliases `@oculus/core` to its sources, since the gate runs the tests before the build.
- Sources: https://www.postgresql.org/docs/15/ddl-constraints.html (check constraints, composite foreign keys, `MATCH SIMPLE` skipping rows with a null column), https://www.postgresql.org/docs/15/queries-with.html (data-modifying statements in `WITH`), https://www.postgresql.org/docs/15/functions-datetime.html (`date_trunc`, `AT TIME ZONE`), https://www.postgresql.org/docs/15/functions-formatting.html (`to_char`), https://www.postgresql.org/docs/15/plpgsql-trigger.html and https://www.postgresql.org/docs/15/plpgsql-errors-and-messages.html (`TG_ARGV`, `RAISE … USING ERRCODE, CONSTRAINT`), https://www.postgresql.org/docs/15/datatype-json.html (`jsonb` key order and duplicates), https://www.postgresql.org/docs/15/runtime-config-client.html (`extra_float_digits`); read 2026-11-23.

- **Hardening (second review):** `catalog_keep_identity` runs with `search_path = pg_catalog, pg_temp`, so an overload created elsewhere (for example `public.to_jsonb(public.records)`) can't replace its checks; its triggers are named `zzzz_*` so they fire after any other BEFORE UPDATE trigger. The guarantee holds for roles that don't own the tables: the owner (the migrating role) can still disable triggers, truncate or add rules, and a role with DELETE and INSERT can "move" a record as a delete plus a new row. T-029 gives the app a non-owner role without UPDATE or DELETE on the version tables and without cross-organization access.

## D-061 — Identifier storage: types as one validated JSON row each, a holding per number carrying its type's rule, unique indexes per rule, a locked counter for auto-numbers (2026-11-23, autopilot T-026)
`packages/db/migrations/0003_identifiers.sql` creates `identifier_types`, `identifier_holdings`, `record_identifiers`, `former_identifiers` and `identifier_counters`; `packages/db/src/identifiers.ts` reads and writes them. Everything follows D-060: `organization_id` in every key and composite foreign key, `catalog_keep_identity` (`zzzz_*` triggers) on every new table, core validating before writing and after reading, nothing cascading on delete.
- **Identifier types: one row per `(organization_id, key)`, the JSON `validateIdentifierType` accepted, edited in place** (`updateIdentifierType`), with `uniqueness` also a column (checks tie the JSON's `key`, `organizationId` and `uniqueness` to the row). Not versioned like templates: stored numbers must point at their type's *current* rule with a foreign key, so a rule change reaches every value in the same statement, and pointing at "the current version" is what D-060 rejected (`current_version` column). Records never follow a type's version the way they follow a template's, and the history of type edits belongs in the change log (T-029). New types go through `validateNewIdentifierType`, at most `MAX_IDENTIFIER_TYPES` per organization (counted under a no-key lock on the organization row); the key never changes (identity trigger), so a rename is a new type, as D-031 already treats it.
- **A holding per number.** `identifier_holdings (organization_id, record_id, type_key, key, uniqueness, current)` has one row per `(type, identifierKey)` a record holds or held, current or former or both (a reinstated number, two spellings of one former number). `uniqueness` is never what the writer sends: a `BEFORE INSERT OR UPDATE` trigger (`zzzz_identifier_holdings_take_rule`, fixed `search_path`) copies it from `identifier_types`, and the composite foreign key `(organization_id, type_key, uniqueness)` with `ON UPDATE CASCADE` keeps it in step when the type's rule changes. A holding of a type that doesn't exist has a null rule and counts for nothing, as core's `ruleOf` (a former number of a deleted or imported type, D-009); a current one can't (`identifier_holdings_current_has_type`). When a type is created later under that key, an `AFTER INSERT` trigger on `identifier_types` (`zzzz_identifier_types_adopt_holdings`, fixed `search_path`) fills in the rule of the waiting holdings (D-031 `key_adopts_values`), so a type inserted by direct SQL adopts them too; a clash refuses the insert.
- **Types and holdings of one key are never written at the same moment.** Each `(organization_id, type key)` has a transaction-level advisory lock, **bucketed**: `identifier_type_lock_bucket(type_key)` is a hash of the key mod 64, and `identifier_type_lock_key` hashes the organization and that bucket, so a transaction holds at most 64 of these locks per organization whatever it writes (a job spanning many organizations in one transaction holds 64 for each and can still fill the table: such jobs commit per organization). A record's former numbers may name up to 500 unknown type keys, so a lock per key let one save take 500 locks and a few such saves fill the server's shared lock table (`53200`, out of shared memory), failing other organizations' writes too; keys sharing a bucket only wait for each other. The holdings' trigger takes the lock shared before it reads the rule, and a trigger on `identifier_types` takes it exclusive on every insert, update and delete, so direct SQL writers are covered too. Without it, a save that read "no such type" (null rule) while the type was being created, and the creation's adopting update that couldn't see the uncommitted holding, each missed the other, and the number stayed outside both unique indexes for good (an `all_time` number given twice). With it, whichever comes second waits for the first to commit and then sees it: the trigger's own statements each take a new snapshot. Saves take shared locks, so they never wait for each other here. Where one call needs several buckets, `identifier_type_locks(organization, keys, exclusive)` takes each bucket once **in bucket order** (the same order in every organization): a save takes its buckets shared that way before writing holdings (the trigger then finds them held), and an allocation takes its types' buckets exclusive that way. The type rows' own locks come first (a save reads them `FOR SHARE`; an update or delete has locked the row before its trigger runs), so the order is type rows, then key locks in bucket order — except for a type created after a save read the types, where a concurrent rule change can deadlock with the save's foreign-key check (the database refuses one, which gets `retry`). A holding still may have no type (former numbers, D-009) and then has a null rule; only holdings of keys with no type do.
- **Read Committed only.** All of the above needs each statement to take a new snapshot, which only Read Committed does: under Repeatable Read or Serializable a statement reads the transaction's first snapshot, so the adopting update and the allocation's read could miss what committed while they waited for a lock, and the null-rule race returns. So the guarantee doesn't depend on the caller: `Database.transaction` begins `BEGIN ISOLATION LEVEL READ COMMITTED` whatever the server's `default_transaction_isolation`; every function here checks `transaction_isolation` inside its savepoint and otherwise refuses with `read_committed_required` without writing; and the database refuses too (`identifier_require_read_committed`, SQLSTATE `OC061`, called by the holdings' and types' triggers and by `identifier_type_locks`), so a direct writer in another isolation level, or a statement outside a transaction on a database defaulting to Repeatable Read, is refused rather than racing. Tests set the level with `SET TRANSACTION` and with `ALTER DATABASE … SET default_transaction_isolation = 'repeatable read'`.
- **The rules are two partial unique indexes** on `(organization_id, type_key, key)`: `WHERE uniqueness = 'current' AND current` and `WHERE uniqueness = 'all_time'`. Because there is one holding per record per number, a record may hold its own number as current and former, while two records never share one under the rule. Tightening a rule over values that already clash fails in the cascade (`uniqueness_clash`); adopting former numbers that clash fails the new type (`adopted_values_clash`). Two organizations can hold the same number under every rule. The index waits on an uncommitted holding of the same number, so of two saves at the same moment the second waits and is refused if the first commits.
- **The values themselves** are in `record_identifiers` (current: order, the primary mark, at most one primary per record by a partial unique index, the foreign key to a holding with `current = true`) and `former_identifiers` (order, `retired_at` in whole milliseconds, note). Each stores `key` = core's `identifierKey(value)` beside the value as typed. The database can't compute the key, so `readRecordIdentifiers` checks every stored key against `identifierKey(value)` and refuses a mismatch as `key_outdated`: a row changed by hand, or keys from an older `identifierKey`. As D-024 says, changing `identifierKey` is a migration that recomputes every key (and the unique indexes then re-check them). Otherwise stored sets are **read leniently, as D-031 reads them**: every shape and safety rule applies, but a current value that no longer fits a format changed after it was saved (an edit D-031 allows with confirmation) is returned, not refused, with a `format_mismatch` issue at its path in the result's `issues` (`StoredRecordIdentifiers`); a save of it is still refused until it is fixed. The record, its current and former values and the organization's types are read in one statement, so from one moment.
- **Saving replaces a record's whole set** (`saveRecordIdentifiers`): types read `FOR SHARE` (they can't change under the save), `validateRecordIdentifiers` against them, the record row locked `FOR NO KEY UPDATE` (one save per record at a time, without blocking foreign key checks); then the record's value rows are deleted, its holdings written in **one statement in a fixed order** (type key, then comparison key, byte order: an `INSERT … ORDER BY … ON CONFLICT` on the holding's key that only flips `current` on a holding it keeps), only then the holdings it lets go of deleted, and the value rows inserted. A save waiting on another's number (an uncommitted holding of it) has then written only numbers before it in that order and deleted none, so two saves can't wait for each other: two records swapping numbers at the same moment each meet the other's number still held and are both refused (`not_unique`), where delete-then-insert deadlocked. A deadlock, a serialization failure or a full lock table (`53200`) that still happens (direct writers, allocations below, a server short of lock memory) rolls back to the savepoint and returns `retry` from every function here, never the raw error; the trigger's `OC061` returns `read_committed_required`. Every write runs in a savepoint inside the caller's transaction, and these functions throw outside one (a `SAVEPOINT` outside a transaction fails); if rolling back to the savepoint fails as well, the error thrown keeps the first one as its `cause`. A refusal by a rule index rolls back to the savepoint and returns `not_unique` at the value's own path, naming only the caller's own value and its type's label; the caller's transaction stays usable. Without the savepoint, an error would abort the caller's transaction and its `COMMIT` would silently roll back. Other database errors are thrown as before (D-060); a type changed in the instant between the check and the write gives `types_changed`. Callers (T-032) check `droppedIdentifiers` first: a number left out of a save is gone, and under `all_time` free again.
- **Auto-numbers** (`allocateIdentifier(tx, organizationId, typeKey, { year })`): the counter row `identifier_counters (organization_id, type_key, series)`, series the year for year-based numbering and `''` for prefix numbering, is created if missing and locked `FOR UPDATE` until the transaction ends, after the type's key lock (its bucket's), taken exclusive: the allocation waits for every save of the type's numbers that hasn't committed, and saves of the type wait for the allocating transaction. Without it the allocator could give out a number someone is typing in an uncommitted save (the save would then be refused `not_unique`, or under uniqueness `none` both would keep it); with it, the typed number is seen and the next one given out. After the lock (so the statement sees whatever an earlier holder committed) every value of the type, current and former, is read and handed to core's `nextIdentifier` together with the counter's `last_value` as if a record held it; the result is stored as the new `last_value`. So it is exactly core's rule (highest held + 1, former numbers counted, gaps not filled) and never lower than the last number given out: a number allocated in one transaction and saved in another (or never) is still never given out again. Allocating and saving in one transaction holds the lock until commit; a rolled-back transaction gives its number back. Tests run ten allocations at once on a type with no uniqueness rule, where only the lock keeps numbers apart. **Several types in one transaction go through one `allocateIdentifiers(tx, organizationId, [{ typeKey, year }, …])` call**, which takes the types' key locks in bucket order and then the counters in a fixed order (type key, then series, byte order) whatever the order asked, and returns the numbers in the order asked: two transactions allocating two types one call at a time in opposite orders can each wait for the other, and the database then refuses one, which gets `retry`. Because keys share buckets, any transaction that allocates (exclusive) and also saves (shared) can deadlock with another doing the same for a type in a colliding bucket — likely for imports naming many legacy former types; the database refuses one, which gets `retry`, and the caller retries the whole transaction. Saves alone never deadlock on these locks, since they take them shared. `53200` (out of shared memory) is also mapped to `retry`, but retrying inside the same transaction can't help: the message tells the caller to roll back and start again.
- **Separation tests** try, with direct SQL: a holding or value pointing at another organization's record or holding, a current number of a type only another organization has, a counter for another organization's type, moving any new row to another organization or changing its record, key, position or series, forging a holding's rule to dodge the indexes, and deleting a type, record or holding in use.
- **Rejected:** versioned identifier types (above); an exclusion constraint (`EXCLUDE … record_id WITH <>`) on one value table, which needs the `btree_gist` extension; a constraint trigger that searches for clashes (not safe against two saves at once without extra locks); the rule written by the application (a direct writer could store `none` and dodge the index); a `SEQUENCE` per type (it can't follow core's "highest held + 1" with imported and former numbers, and year series restart); allocating without a counter, relying on the unique index (a type with uniqueness `none` but auto-numbering could get duplicates, and the loser of a race would fail its save instead of getting the next number); a real foreign key from every holding to its type instead of the key lock (former numbers of a type that doesn't exist must be storable, D-009); advisory locks per number instead of the fixed write order (a save may touch over a thousand numbers, which the shared lock table can't take for many saves at once), and for the same reason a lock per type key (up to 500 per save); `REPEATABLE READ` for reads (a reader inside the caller's Read Committed transaction can't change its isolation); accepting any isolation level and relying on callers to use Read Committed (one `ALTER DATABASE` would silently reopen the race); doing the adoption in `insertIdentifierType` only (a type inserted by direct SQL never adopted).
- **Not covered here:** template `identifier` fields naming held numbers (D-038), type-change reports and confirmation (D-031), deleting a type, and staff search by number (T-028, which can use `identifier_holdings_lookup`) belong to the service layer and later tasks.

## D-062 — Terms and term usages: one table of stored terms per organization, a term key from core's rules, a usage index the data-access layer rebuilds per record (2026-11-23, autopilot T-027)
`packages/db/migrations/0004_vocabularies.sql` creates `terms`, `record_term_index` and `record_terms`; `packages/db/src/vocabularies.ts` reads and writes them. Everything follows D-060 and D-061: `organization_id` in every key and composite foreign key, `catalog_keep_identity` (`zzzz_*` triggers) on every new table, core validating before writing and after reading, writes in a savepoint of the caller's transaction with clean refusals, nothing cascading on delete.
- **Stored terms: one table for local and authority terms.** `terms (organization_id, id, vocabulary, uri, label, term_key)`, keyed `(organization_id, id)` with a random version 4 UUID made when the term is first saved, and unique on `(organization_id, term_key)`, so an organization stores each term once and two organizations can store the same one. Both kinds are core's `ControlledTerm` (`validateControlledTerm`); a local term is one with no vocabulary or `local` and no URI (a check, `terms_local_without_uri`, backs D-014 up), so a second table would only split one shape in two. `saveTerm` inserts (no `id`) or replaces the term with that ID (a local term renamed, a URI added); the ID never changes, the term and its key can. Saving a term never rewrites the records that use it (they hold their own copy, D-010): renaming or merging across records is Data Cleaning's, a later task. Until T-019b2 gives stored terms an `organizationId` in core, the organization is the row's column, which every read and write filters by. *Rejected:* separate local and authority tables (same shape, one key); keying stored terms by label (a rename would be a new identity).
- **The term key** is what says two values are one term, for the unique stored copy and for counting: a term with a URI is its vocabulary plus `termUriKey(uri)` (so http and https copies of one Nomenclature address meet, and a record holding an old label for an LCSH heading still counts under the heading); any other is its vocabulary (none = `local`) plus its exact label. Spellings that differ are different terms: suggesting they may be one is `findNearDuplicateTerms`'s job, never the key's. That includes labels that differ only invisibly, such as a composed and a decomposed accent (NFC `Café` and NFD `Cafe` + combining acute): they are two terms by design, because core compares and stores labels exactly (`validateControlledTerm` keeps the label as given) and a key that normalised would merge two stored rows whose labels core calls different, so the stored copy shown for the merged term would depend on which was saved first. Data Cleaning finds them: `findNearDuplicateTerms` pairs them as `same_label`. *Rejected:* NFC in the key alone (diverges from core; if labels should be NFC, core's validator is where to say so, for every place a label is stored). Stored as the SHA-256 of that text in hex (64 characters), because a URL with non-ASCII characters percent-encodes to many times its length and a btree entry is limited to about 2.7 kB; the database can't compute it (`termUriKey` parses a WHATWG URL), so reads recompute it from the row and a mismatch reads as `row_mismatch`. Changing the key rule is a migration, as D-024 says for `identifierKey`.
- **The usage index is maintained by the data-access layer, not a trigger on `records`.** Which fields hold terms is in the record's template (the `controlled_term` fields of its current version), and the key needs core; a PL/pgSQL trigger would have to re-implement template reading, term validation and URL parsing in SQL, two copies of the rules that could drift. `refreshRecordTerms(tx, organizationId, recordId)` locks the record (`FOR NO KEY UPDATE`, so two refreshes never interleave), reads it and its template as stored (never what the caller holds), validates every value of every `controlled_term` field with `validateControlledTerm` (values it refuses are left out and returned in `skipped`; a list or a single value is indexed whatever the field says, since fitting the field is `checkRecordAgainstTemplate`'s at save time), and replaces the record's rows in `record_terms` (one per field and term key, with the term as the record holds it, so stale labels can be listed by staff tools; no field visibility is kept, see the counts below). The service layer (T-032) calls it in the transaction that saves the record. **A refused refresh removes old usages:** when the record or its template no longer validates (or names no template, or its template is gone), the record's usages and its index row are deleted and the issues returned, so the counts never show what the record used to hold, and `recordsWithStaleTerms` lists it until a refresh succeeds. **Lock order:** `refreshRecordTerms` locks the record, then writes the index; `clearRecordTerms` locks the record `FOR UPDATE` first too (as deleting it will), then deletes the index, so a clear and a concurrent save-and-refresh of the same record wait for each other instead of deadlocking (an orchestrated two-connection test). Both turn a deadlock (`40P01`) or serialization failure (`40001`) into a clean `retry` issue: roll back and run the whole transaction again. **The cost of not using a trigger** is that a write which forgets the refresh leaves the index stale, so `record_term_index` keeps what each record's usages were built from: its template key and version and an md5 of its `fields` as `jsonb` text (a change detector, not a security check). `recordsWithStaleTerms` lists records with no index row or one whose fields, template or template version changed since, by record ID in pages (`limit`, `after` the last ID): a record whose refresh keeps being refused stays stale, so a job working through the list passes `after` and reaches the records beyond a page of ones it can't fix (tested with a good stale record after a full page of permanently stale ones). It reads every record of the organization, so it is a maintenance check, never part of a count. `record_terms` points at the index row, which points at the record and the template version, all by `organization_id`.
- **Counts and lists read the index only, and are STAFF-ONLY.** `termUsageCounts` gives, per term key, how many distinct records use it (a record using a term in two fields counts once), in every field of every record, published or not, plus every stored term with 0 if unused (for Data Cleaning); with `fieldKey`, only usages in that field and no unused terms. It has no public option: any option but `fieldKey`, `limit` and `after` is refused (`unknown_option`), so a caller asking for a public scope is told no rather than given staff counts. **Public Subjects counts are never worked out from `record_terms`.** They come from what is published: `publicOutput` or the public views of published records, or a separate index built from those at publish time (T-034, T-050). *Rejected (second review):* a `public_fields` scope over `record_terms.visibility`. It could not follow core's visibility rules: a value that doesn't fit its field (which core's public view withholds) was still counted, the visibility was the field's when the record was last indexed (stale after a template edit until a refresh), and terms the organization stored but no public field used were listed with 0. Two copies of the public rules would drift, so the column is dropped too: staff filtering by visibility is not needed, and keeping it would invite public use. **Nothing typed in a record is shown as a term's name or address:** a stored term is shown by the organization's stored copy; a term not stored by its key, vocabulary and (if it has one) its canonical URI, `canonicalTermUri`: the scheme of one counted usage followed by `termUriKey`, i.e. rebuilt from the parsed parts the key is made of (scheme and host lower case, dot segments resolved, default port, user name, password and trailing slashes dropped), checked against the key. Two URIs with one key differ there at most in scheme. (Before this, the smallest raw URI any usage held was shown, so `http://nomenclature.info/nom/AAA-secret-note/../1`, typed in a staff field and with the same key as `https://nomenclature.info/nom/1`, was shown as the term's URI; and earlier still, the smallest label any record held, so a staff note typed as an LCSH heading's label could be shown as the heading's name.) *Rejected:* a label from a public field only (still possibly from an unpublished record; staff find the records with `recordsUsingTerm`). `termUsageCounts` and `readTerms` page by term key (`limit`, `after` the last key), a stable order however counts change; ranking by count or sorting by label is the caller's. `recordsUsingTerm` lists records by ID with the fields they use the term in, in pages (`limit`, `after`). All take at most `MAX_TERM_LIST_LIMIT` (10,000) and say when there were more. The index `(organization_id, term_key, record_id)` serves the counts and lists.
- **Deleting.** Nothing cascades: an indexed record can't be deleted until `clearRecordTerms` removes its usages and index row, in the same transaction (it locks the record first, see the lock order above).
- **Separation tests** try, with direct SQL: an index row for another organization's record or built from another organization's template version, a usage on another organization's record, a term of an organization that doesn't exist (all refused by composite foreign keys), and moving any row of the three tables or changing what identifies it (refused by the identity triggers). Two organizations storing and using the same term are counted apart, and one organization's calls never find, refresh, clear or rename the other's rows.
- **Not covered here:** inherited values (counted only on the record that holds them; Subjects counts of inherited access points would need the arrangement), `place` values with GNIS URIs (not `controlled_term`), deleting stored terms and rewriting records (Data Cleaning), and an organization on stored terms in core (T-019b2).
- Sources: https://www.postgresql.org/docs/15/ddl-constraints.html, https://www.postgresql.org/docs/15/btree-implementation.html (index entry size limit), https://www.postgresql.org/docs/15/datatype-json.html (`jsonb` text output is canonical), https://www.postgresql.org/docs/15/functions-string.html (`md5`), https://www.postgresql.org/docs/15/sql-select.html (`FOR UPDATE`, `FOR NO KEY UPDATE`), https://www.postgresql.org/docs/15/explicit-locking.html (row-level lock conflicts, deadlocks), https://www.postgresql.org/docs/15/transaction-iso.html (`40001` under repeatable read), https://www.postgresql.org/docs/15/errcodes-appendix.html (`40P01`, `40001`), https://unicode.org/reports/tr15/ (NFC and NFD), https://url.spec.whatwg.org/ (percent-encoding of non-ASCII path characters); read 2026-11-23.

## D-063 — Record versions: an append-only table the database keeps in step with every record write, opaque actor IDs until users exist, grants for a non-owner app role (2026-11-23, autopilot T-029)
`packages/db/migrations/0005_record_versions.sql` adds `records.version` and `record_versions`; `packages/db/src/record-versions.ts` reads them and `catalog.ts` writes them. Follows D-060–D-062: `organization_id` in every key, triggers with a fixed `search_path` named `zzzz_*`, writes in a savepoint of the caller's transaction (outside one they throw), clean refusals, core validating both ways.
- **One row per write.** `record_versions (organization_id, record_id, version, record jsonb, actor, recorded_at, changed_fields text[], reason)`, keyed `(organization_id, record_id, version)`. `record` is the whole record as `validateRecord` accepted it. `insertRecord(tx, record, { actor, reason? })` writes the row and version 1; the new `updateRecord(tx, record, { expectedVersion, actor, reason? })` writes the row and the next version, or stores nothing and returns `version_conflict` if the record is no longer at `expectedVersion` (`UPDATE … WHERE version = expected`: of two edits from one version the second waits on the row lock and then finds the new version, and a write that meets the version triggers out of step gets it too), `unknown_record`, `created_at_changed`, `kind_changed`, `updated_before` or `retry` (deadlock, serialization failure). `insertRecord` refuses a deleted record's ID as `id_used_before`. **A record's kind never changes** (`catalog_keep_identity` on `records` now also fixes `kind`, constraint `records_kind_fixed`): a unit with children can't become an object, nor a represented record change kind. **Its template may change, only through `updateRecord`**, after the caller has checked the record against the new template (T-032), as for any save. **`updatedAt` never goes backwards** (`records_updated_at_backwards`; equal is allowed); it is the writer's value, so history is ordered by version number and the database's `recorded_at`, never by `updatedAt`. `readStoredRecord` gives the record with its version number; `readVersions` (oldest first, paged by `after`/`limit`) and `readVersion` (one, or the latest) validate every snapshot again and check its organization and ID. T-031 adds "what changed since" to the conflict; T-030 compares and restores.
- **The database keeps records and versions in step, for every writer.** `records.version` starts at 1 and every UPDATE must add exactly 1 (`zzzz_records_version_step`). A version row is accepted only when the record row (locked `FOR NO KEY UPDATE`) already carries its number, the number follows the last stored one, and its snapshot equals the row (`record_snapshot(records)`, the same object `recordFromRow` builds; `SET extra_float_digits = 1` so coordinates compare whatever the session's setting) (`zzzz_record_versions_check`). A deferred constraint trigger (`zzzz_records_have_version`) refuses the COMMIT of a record insert or update whose current version isn't stored as the row now is **by this same transaction**: each version row keeps `written_in`, the top-level transaction ID (`pg_current_xact_id()`, the same inside a savepoint), set by the trigger, and the check compares it. So a record wound back to an older stored version (content and number both matching) still can't commit without a new version of its own. So no gap, no duplicate, no record write without its version and no version without its write, whatever the isolation level (under Repeatable Read a racing update fails `40001`, mapped to `retry`). **When** (`recorded_at`, the database clock, whole milliseconds) and **which fields changed** (core's property names and `fields.<key>`, sorted; every one for version 1; never `id`, `organizationId`, `createdAt`, `updatedAt`) are filled in by the trigger, never taken from the writer. Errors are SQLSTATE `23000` with constraints `records_version_step`, `records_id_used_before`, `records_kind_fixed`, `records_updated_at_backwards`, `records_have_version`, `record_versions_with_record_write`, `record_versions_next_number`, `record_versions_snapshot_matches`, `record_versions_append_only`.
- **Append-only.** Row triggers refuse UPDATE and DELETE and a statement trigger refuses TRUNCATE on `record_versions` (`record_versions_append_only`); `REVOKE ALL … FROM PUBLIC`. The owner (the migrating role) can still disable triggers, so **the app must never connect as the owner**.
- **Who: an opaque actor ID until T-036.** `user:` and a lowercase version 4 UUID, or `system:` and a lower-case name (`system:import`, `system:migration_0005`), checked by `validateRecordChange`/`isActorId` and a CHECK. Nothing checks a user exists yet: T-036 adds a users table and ties `user:` IDs to it (a `user_id` column with a foreign key, or a trigger), and T-032 must pass the signed-in person's ID, never one a request names. **Why:** optional, 1–2000 characters, no spaces or line breaks at the ends, no control characters but line breaks.
- **History outlives the record, and its ID is never reused.** Versions have no foreign key to `records`, so deleting a record keeps its history. `zzzz_records_version_step` refuses inserting a record whose ID has versions but no live row (`records_id_used_before`; a live duplicate is still refused by the primary key), so a deleted record can't be re-created to wind its history back (found by the independent review: delete, then insert version 1's content, committed with no new version). **Deleting a record isn't versioned yet, so the app role gets no DELETE on `records`: record deletion is unavailable to the app until T-032 adds tombstones.** That needs a schema change: an `action` column on `record_versions` (`'save'` or `'delete'`), a deletion version allowed only as a record's last version and written in the same transaction as the DELETE (who, when, why), and every later write of that ID refused.
- **Roles are not created by the migration.** `CREATE ROLE` needs `CREATEROLE`, which a shared host (D-035, D-046) may not give, and roles are cluster-wide. The app role's grants, for T-032 and T-051 to apply (tested in the throwaway database with a non-owner login role):
  ```sql
  GRANT USAGE ON SCHEMA public TO oculus_app;
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO oculus_app;
  GRANT INSERT, UPDATE ON public.records TO oculus_app;
  GRANT INSERT, UPDATE, DELETE ON public.organizations, public.templates, public.record_types,
    public.identifier_types, public.identifier_holdings, public.record_identifiers,
    public.former_identifiers, public.identifier_counters, public.terms, public.record_term_index,
    public.record_terms TO oculus_app;
  GRANT INSERT ON public.template_versions, public.record_type_versions, public.record_versions TO oculus_app;
  ```
  The app role then gets `42501` for DELETE on `records`, for UPDATE, DELETE and TRUNCATE of any version table, for `ALTER TABLE … DISABLE TRIGGER`, `DROP TRIGGER` and `SET session_replication_role`. T-032 narrows these further (which role may write at all). Template and record type versions get the same INSERT-only grant here but no append-only trigger yet (their identity triggers already fix keys and numbers).
- **Migrating existing rows.** Rows stored before 0005 get version 1 by `system:migration_0005` (no deployed database has any).
- **Tests changed:** direct SQL writes in older tests that simulate a hand edit now add 1 to `version` and store the row's version (`writeRecordDirectly` in the fixtures), because the database refuses them otherwise; `insertRecord` calls run in a transaction with an actor.
- **Rejected:** versions written by a trigger on `records` (the snapshot would be built in SQL, never validated by core, and the trigger couldn't know who or why); trusting the writer's `changed_fields` and time; a foreign key from versions to records (history would block deletes or vanish with them); `ON DELETE CASCADE`; a sequence for version numbers (gaps on rollback); creating roles in the migration (fails on hosts without `CREATEROLE`).
- Sources: https://www.postgresql.org/docs/16/sql-createtrigger.html (constraint triggers, `DEFERRABLE INITIALLY DEFERRED`, TRUNCATE triggers, firing order by name), https://www.postgresql.org/docs/16/sql-createfunction.html (`SET` clauses), https://www.postgresql.org/docs/16/ddl-priv.html and https://www.postgresql.org/docs/16/sql-grant.html (privileges, owner-only `ALTER TABLE`), https://www.postgresql.org/docs/16/runtime-config-client.html (`extra_float_digits`, `session_replication_role` superuser-only), https://www.postgresql.org/docs/16/transaction-iso.html (re-checking a locked row's `WHERE` under Read Committed); read 2026-11-23.

## D-064 — Backups: one file of pg_dump's custom archive plus a manifest, restored only into a database exactly as CREATE DATABASE made it, by a role that is not a superuser, and checked afterwards (2026-11-23, autopilot T-052)
`npm run db:backup -- <new file>` and `npm run db:restore -- [--allow-superuser] [--no-privileges] <file>` (`packages/db/src/backup.ts`, `backup-connection.ts`, `backup-catalog.ts`, `backup-cleanup.ts`, `backup-cli.ts`). Both read the database only from `OCULUS_DATABASE_URL`; a relative path is taken from where npm was run (`INIT_CWD`), else the current directory; exit 0 done, 1 refused, failed or stopped, 2 usage, 3 restored but stopped before the check finished. They are plain commands any scheduler can run (D-035); where copies go is T-051's. `*.oculus-backup`, `*.dump` and `*.partial` are in `.gitignore`.
- **The file.** `[pg_dump --format=custom archive][manifest JSON][8-byte big-endian manifest length][SHA-256 of the manifest][ASCII "OCULUS-BACKUP-01"]`. The manifest (`format`, `formatVersion` 2 (format 1, from before the `objects.revokes` list, is refused with a message saying it comes from an earlier version of Oculus), `createdAt`, `serverVersion`, `serverVersionNum`, `pgDumpVersion`, `migrations` [name, sha256], `tables` [`schema.table`, `rows`, `rowsHash`], `objects` [`sequences`, `functions`, `triggers`, `policies`, `grants`, each a sorted list of lines], `dump` [bytes, sha256]) is checked exactly on restore (unknown fields refused). The trailer goes after the archive so pg_dump streams straight into the file with no second copy; restore reads the archive once to check its size and SHA-256 before anything touches the target, then streams it to pg_restore's stdin, hashing it again and holding back the last 1 MiB chunk until that second hash matches (tested with an archive of several chunks) (if the file changed in between, pg_restore never gets the archive's end, so it can't reach COMMIT, and is killed). No copy of the data is ever written.
- **One snapshot.** The backup opens a `REPEATABLE READ, READ ONLY` transaction, sets `statement_timeout`, `idle_in_transaction_session_timeout` and (17+) `transaction_timeout` to 0 for it (`set_config(..., true)`: it sits idle while pg_dump runs, and a role or database timeout must not end it), reads `public.oculus_migrations`, every table's count and row hash and the objects, exports the snapshot (`pg_export_snapshot()`) and runs `pg_dump --snapshot`, so the manifest describes exactly what the archive holds even while the app writes. pg_dump can't import a snapshot from another database. Once pg_dump has finished, a lost exporting session no longer matters (pg_dump held its own copy of the snapshot), so its `COMMIT` failing doesn't fail the backup. A database without `public.oculus_migrations` is refused (`not_oculus`).
- **Found, not listed.** Every ordinary or partitioned table outside `pg_*` and `information_schema` is counted, so later tables (T-029's versions) are covered with no change. Each table is named by `format('%I.%I')` from the catalog inside `query_to_xml`, so no identifier is ever built in JavaScript (D-050). `rowsHash` is the sum of the first 64 bits of each row's SHA-256, the row being `ROW(oculus_backup_row.*)::text` (a qualified star is the whole row even if a column has the alias's name), in the UTC/ISO session settings of D-057: order-independent, a check against lost or changed rows, not a signature. `objects`: revocations (see `--no-privileges` below), sequence names (not values: sequences aren't transactional, so a value read beside the snapshot could differ from pg_dump's under writes), functions (signature, kind and a SHA-256 of body, result, language, volatility, security definer and settings), triggers (table, name, enabled state, SHA-256 of the definition), row security on/forced per table and each policy (command, permissive, roles, SHA-256 of its expressions), and grants on tables, schemas and functions (grantee and privilege; grants to an object's owner and grantors are left out because `--no-owner` changes owners), all outside extensions.
- **Written atomically, never over anything.** The destination must not exist. pg_dump streams into `.<name>.<random>.partial` in the same directory (ignored by git) (created `wx`, mode 0600, `chmod` 0600 whatever the umask), which is synced, hard-linked to the destination (a link fails if the name exists) and unlinked, and the directory synced (if it can't be, the backup still stands and a warning says so). A file system without hard links is refused (`write_failed`) rather than check-then-rename. If the temporary name can't be unlinked after the link, the backup is complete and a warning names the file to delete. On any failure or stop the partial file is removed.
- **One connection for the driver and the tools.** The URL is parsed once, as libpq reads a URI (user, password, host, port, database from the URL, then query keywords, a later one winning, `%`-decoded), and given to the driver field by field (never as the URL, which node-pg reads differently: it ignores `?dbname=`, so the checks and pg_restore could reach different databases) and to the tools as a libpq service file `[oculus_backup]` with `--dbname=service=oculus_backup`, and the password, if any, as a libpq password file (`*:*:*:*:` and the password with `:` and `\` escaped) named by `PGPASSFILE`: libpq refuses service-file lines over about 1,020 bytes ("line too long in service file", seen with 16), while the password file takes 2,000-character passwords: a test backs up and restores, as two roles with such passwords (one containing `:` and `\\`), against a throwaway scram-sha-256 server it starts itself (`scripts/test-database.mjs` takes a `password` for that; CI installs the server package, without a cluster, so `initdb` is there). Both files are mode 0600 in a `mkdtemp` 0700 directory, deleted afterwards. Any other value that would make a service-file line over 1,000 bytes is refused up front. Host, user and database must be named and a single host given. Only keywords both can be given the same meaning are accepted: `host`, `port`, `dbname`, `user`, `password`, `sslmode`, `sslrootcert`, `sslcert`, `sslkey`, `connect_timeout`, and `application_name` (replaced by `oculus-backup` / `oculus-restore`); anything else (`hostaddr`, `options`, `target_session_attrs`, `service`, `passfile`, `sslpassword`, node-pg's `ssl=true`) is refused, as are values a service file can't hold exactly (line breaks, leading or trailing spaces), with messages that show no value.
- **TLS, the same for both.** A Unix socket: none. `localhost`, `127.0.0.1` or `::1` with no `sslmode`, `disable`, `allow` or `prefer`: none. Any other host is always verified: no `sslmode`, `prefer`, `require` and `verify-full` all become `verify-full` (libpq's `require` doesn't check the certificate, node-pg's does; we take the stricter); `verify-ca` needs `sslrootcert` naming a file (libpq refuses `verify-ca` with `sslrootcert=system`; the driver then checks the chain but not the name); `disable` and `allow` are refused (the password would cross the network in the clear). With `sslrootcert` both trust that file; without it both trust the system's CAs (`sslrootcert=system`, an explicit choice too, means OpenSSL's default store for libpq, which needs tools 16 or newer, else a refusal asks for `sslrootcert`, and Node's built-in CAs for the driver: two slightly different lists, both public CAs). `sslcert` and `sslkey` go together to both. libpq's default client certificate in `~/.postgresql` could still be offered when none is named; it can't change which server is reached.
- **Environment.** The tools get the caller's environment minus every `OCULUS_` variable and every `PG*` variable, plus `PGSERVICEFILE` and, when the URL has a password, our `PGPASSFILE`; when it has none, the caller's `PGPASSWORD` and `PGPASSFILE` stay (the driver reads them too); `--no-password`, so a scheduled run never waits at a prompt. Everything the commands print passes through a filter hiding the URL and its password, if 4 characters or longer (shorter ones would mangle numbers in messages; nothing prints a password anyway). A test runs both commands with wrapper tools that record their arguments, environment and the service file's permissions.
- **Processes.** Each tool runs as `sh -c <watchdog> oculus-tool <tool> <args>` (arguments never interpreted by the shell) in its own process group, with the watchdog's fd 0 a lifeline pipe from Node that is never written and fd 3 the tool's stdin (the archive for pg_restore, empty for pg_dump). The watchdog starts the tool and a watcher that reads the lifeline: when Node dies by any means the pipe closes and the watcher sends the whole group SIGTERM, then SIGKILL 5 seconds later, so a tool that ignores SIGTERM, and anything it started, still ends (tested by SIGKILLing the parent of a tool that ignores SIGTERM); an unfinished pg_restore rolls back. The watchdog survives SIGTERM, SIGINT and SIGHUP (passing them on) and waits for the tool, so Node sees its real end; Node sends SIGKILL to the group 5 seconds after its own SIGTERM, and at once if the watchdog is killed, so no tool keeps the pipes open. `backup` and `restore` take an `AbortSignal`, checked between steps and between archive chunks; the commands abort it on SIGINT, SIGTERM or SIGHUP.
- **Nothing left behind.** The private directory (service and password files), the partial backup and every running tool group are registered while they exist (`backup-cleanup.ts`) and removed or SIGKILLed by a synchronous `process.on("exit")` handler if the ordinary path didn't, so a second signal (`process.exit` at once) and the forced exit after the grace period (30 s; `OCULUS_STOP_GRACE_MS` shortens it for tests) leave nothing: tests run the command as a real process with tools that ignore SIGTERM and SIGINT, double Ctrl-C it and let the grace period run out, and find no tool, partial file or private file. Only SIGKILL of Node itself skips the handler; the watchdog then still ends the tools, and only the private 0700 directory can remain.
- **A stop after COMMIT.** If pg_restore ends badly or is stopped, restore first waits (up to 20 s, inside the command's 30-second grace period so the answer comes before a forced exit) until pg_restore's session (`application_name` `oculus-restore`) has left `pg_stat_activity`, so its transaction has ended on the server either way, then looks at the target before saying anything: still as CREATE DATABASE made it means nothing was restored (`interrupted` or `restore_failed`); otherwise pg_restore had committed, and the database is verified as usual. A good result is reported done (exit 0) with a note that the stop came after the commit; a stop that comes during that check doesn't interrupt it, since it is what says whether the restore is good.
- **Stopping the command while the restore is being checked.** Once pg_restore has committed, a stop can't undo the restore, so the command lets the check finish: a first SIGINT, SIGTERM or SIGHUP prints that the check is finishing and starts no grace period (one already running from a stop before the commit is cancelled). **So after the commit a single SIGTERM waits for the check with no time limit**; a supervisor (systemd's `TimeoutStopSec`, a scheduler's kill timeout) should follow with SIGKILL after its own timeout, which leaves a restored but unchecked database (the watchdog still ends the tools). A second signal exits at once with code 3 and says the database was restored but NOT checked, and must not be used until a restore is checked. One Ctrl-C can arrive as two signals a few milliseconds apart (the terminal signals the whole process group, and npm or a service manager with `KillMode=control-group` passes its own on), so signals within 1 s of the first (`SAME_STOP_MS`) are the same stop, before and after the commit; only a later one counts as a second. Once the command has finished, signals are ignored, so none can replace its exit code. Tests run the command as a real process, with a pg_restore wrapper that, after committing, leaves a session locking `public.oculus_migrations` for 4 s so the check waits, and a 50 ms grace period: one signal during the check ends with exit 0 and "Done"; two signals 2 ms apart do too, printing one notice; two 1.5 s apart end with exit 3.
- **Run it directly, or through npm with one shell exec'd away.** npm runs a script through a shell; without `exec` a signal to npm or that shell can leave node running as an orphan. So both the root scripts (`npm run db:backup -- <file>` from the repository root: `tsc` builds `packages/core` and `packages/db`, then `exec node packages/db/dist/backup-cli.js backup`) and the `packages/db` scripts end in `exec node …`: what npm starts is node itself, one npm deep. Tests start each through npm, check npm's only child is node, send SIGTERM (to npm from the root, to node from the package), and find node, the tool and the partial file gone. npm passes the exit code (including 3) through. Schedulers should still build once per release (`npm run build`) and run `node packages/db/dist/backup-cli.js backup <file>` (or `restore <file>`) directly, with `OCULUS_DATABASE_URL` in the environment: no npm, no build at every run, exact signals and exit codes.
- **The tools.** `PG_BIN` (holding `pg_dump`, or `pg_restore`), else `pg_config --bindir`. pg_dump must be at least the server's major and pg_restore at least the dump's and the target server's; otherwise a refusal says which version to point `PG_BIN` at. CI runs `apt-get update`, installs `postgresql-client-<major>` from the PostgreSQL apt repository for each matrix server and sets `PG_BIN`. POSIX only (`/bin/sh`).
- **Restore, in this order:** the file (trailer, manifest hash and shape, archive size); the migrations against the code's files (every backed-up migration must be a code file with the same SHA-256, and no code file the backup lacks may sort before its last; all differences are listed, `migrations_differ`; code files after the backup's last are allowed and reported as pending, to be applied with `db:migrate`, since restoring an older backup into newer code is the normal upgrade path); pg_restore's version; the archive read through once and its SHA-256 checked (nothing written). Then, on one session that turns off its own `statement_timeout` and idle timeouts: the server's version (15+); **the role is a plain role** (`superuser` otherwise, unless `--allow-superuser`, which prints a warning naming the reasons: a backup's SQL would run with the role's powers). An allowlist, not a list of dangerous roles: `SESSION_USER` and `CURRENT_USER` must be the same role; it may have no attribute beyond LOGIN and INHERIT/NOINHERIT (no SUPERUSER, CREATEROLE, CREATEDB, REPLICATION, BYPASSRLS); and it may be a member of no role at all (no `pg_auth_members` row with it as member, so nothing to inherit or `SET ROLE` to, directly or through other roles). CREATEDB is refused too: it can't reach superuser, but a restoring role needs none, and the database is made by an administrator first. No `pg_*` role is allowed as harmless: none is needed to restore, and each (`pg_signal_backend`, `pg_create_subscription`, `pg_read_all_data`, ...) lends something a backup's SQL shouldn't have. Owning the database (through `pg_database_owner`) is not a membership row. **Nor may anything be granted to the role directly**: no ACL entry naming it (other than as an object's owner) on server parameters (`pg_parameter_acl`, e.g. `GRANT ALTER SYSTEM ON PARAMETER`), tablespaces, databases other than the target, or, in the target, on `pg_catalog` and `information_schema` functions, tables and views, types and the schemas themselves, languages, large objects, foreign-data wrappers or foreign servers (the target holds nothing else yet; tests refuse `GRANT ALTER SYSTEM ON PARAMETER archive_command` and `GRANT EXECUTE ON FUNCTION pg_catalog.pg_read_file(text)`). The refusal says how: an administrator runs `CREATE ROLE oculus_restore LOGIN PASSWORD '…'; GRANT oculus_restore TO <admin role>; CREATE DATABASE oculus OWNER oculus_restore TEMPLATE template0;`, then the restore uses `oculus_restore`. On PostgreSQL 16 and newer, and on managed hosts where the administrator isn't a superuser, the administrator must be a member of a role to make it a database's owner; that grant gives the administrator `oculus_restore`'s rights, not the reverse, so `oculus_restore` stays plain. **The archive's SQL runs as this role,** so it could change the role's own password or settings: the check afterwards compares the role's own settings (`pg_db_role_setting` for the role, in every database) and runs the plain-role check again, reporting any change; a password change can't be seen, which is one more reason to use a dedicated role only for restoring. Tests refuse a role granted `postgres`, `pg_execute_server_program`, `pg_signal_backend`, `pg_create_subscription` (16 and newer) or a NOLOGIN role with CREATEROLE, and roles with CREATEROLE, CREATEDB, REPLICATION or BYPASSRLS; a plain owner restores, as in every other test; the migration runner's advisory lock (`pg_try_advisory_lock`, held to the end, so `db:migrate` can't fill the target meanwhile: `target_busy`); and the target is **exactly as CREATE DATABASE made it** (an allowlist, below); then pg_restore starts at once. A restore never creates, drops or overwrites a database.
- **"As CREATE DATABASE made it":** no object created after initdb (OID 16384 and up) in any catalog of objects — schemas, relations, functions, types, constraints, collations, conversions, operators, operator classes and families, access methods, casts, transforms, text search configurations, dictionaries, parsers and templates, extended statistics, languages, extensions, foreign-data wrappers, foreign servers — leaving out other sessions' temporary schemas and their contents; no default privileges, publications, event triggers or large objects; no subscriptions in this database; no settings for this database (`pg_db_role_setting`, for any role); and a public schema that is OID 2200, owned by `pg_database_owner`, with exactly `{pg_database_owner=UC/pg_database_owner,=U/pg_database_owner}` and the comment "standard public schema". Each is tested. **The remaining gap:** the check and pg_restore's first statement are separate sessions, so an object created by someone else in the instant between them is not seen; pg_restore then fails on a conflict (rolling everything back) or the check afterwards reports the difference. Holding the migration lock keeps `db:migrate` out; nothing else should be connected to a brand-new database. Database-level properties outside the catalogs listed (the database's own ACL, security labels) are not checked: they don't change what is restored.
- **Then** `pg_restore --no-owner --single-transaction --exit-on-error --no-password`, reading the archive from stdin: any error rolls the whole restore back. Privileges are kept; roles are cluster-wide and not in the dump, so a role the backup grants to must exist on the target or the restore fails cleanly. For disaster recovery on another cluster without those roles, `--no-privileges` passes `pg_restore --no-privileges`: no GRANT is restored, and no REVOKE or default privileges either, which would leave objects open to PUBLIC that the backup had closed. So the manifest lists such revocations (`objects.revokes`: functions and types without EXECUTE or USAGE for PUBLIC, the public schema without USAGE for PUBLIC, and every default-privileges entry), and `--no-privileges` is refused (`privileges_needed`, naming them) when there are any; otherwise grants aren't compared afterwards and must be set up again. Policies still name their roles, which must exist.
- **Then it verifies:** `public.oculus_migrations` equals the manifest's list; the same tables exist, each with the manifest's count and row hash; and every object list matches line for line, except grants to the restoring role on both sides (with `--no-owner` it owns everything, and an owner's rights are not grants: a backup granting the restoring role `SELECT` restores and verifies; grantees are written with `quote_ident` so the line can be read back), and grants and revocations entirely with `--no-privileges`. It also requires that the target has no database or role-in-database settings (`pg_db_role_setting`) afterwards: a restore never makes them, so any that appear are reported (tested with a pg_restore wrapper that adds one). A mismatch is `verify_failed`, listing each difference: pg_restore has already committed, so the message says not to use the database but drop it and restore again. (Checking inside pg_restore's transaction would mean replacing pg_restore with a script through psql; rejected as more moving parts for a case that only a damaged or edited manifest can cause, since the archive's SHA-256 is already checked.)
- **Not an authenticity check.** The SHA-256s catch damage, not a deliberate edit: anyone who can write the file can rewrite the manifest consistently, and a pg_dump archive runs SQL as the restoring role, which is why restore refuses a role with superuser powers by default. Keep backups where only the operator can write them; signing waits for `OCULUS_SECRET_KEY` (D-052) or T-051's off-site copies if wanted.
- **Rejected:** copying the archive out to a file for pg_restore (a second plaintext copy of every record on disk); checking only `rolsuper` (membership of a superuser role or a file-access role gives the same powers); a list of dangerous roles to refuse (any role or attribute not thought of would pass, so the restoring role must be plain instead); a password in the service file (libpq's line limit); a separate manifest file next to the dump (two files can't be published atomically, and one can be lost); the manifest at the front (needs the archive's hash before it is written, so a second full copy); pg_dump's directory format (many files, no atomic publish); `pg_dumpall` (needs superuser, and roles and other databases aren't Oculus's); the URL in `--dbname` or `PGPASSWORD` set from it (`ps` shows argv; the service file keeps the password off both); giving the driver the URL itself (node-pg and libpq read some keywords differently); `pg-connection-string` (node-pg's reading, not libpq's); a denylist of objects for the empty check (anything not thought of would pass); check-then-rename where hard links are missing (a race could overwrite a file); counting outside the dump's snapshot (counts and archive could disagree under writes); sequence values in the manifest (not transactional); restoring into a database that isn't empty, or dropping one first (never overwrite data).
- Sources: https://www.postgresql.org/docs/15/app-pgdump.html (`--snapshot`, custom format, version compatibility), https://www.postgresql.org/docs/15/app-pgrestore.html (`--single-transaction`, `--exit-on-error`, `--no-owner`), https://www.postgresql.org/docs/15/functions-admin.html (`pg_export_snapshot`), https://www.postgresql.org/docs/15/libpq-pgservice.html and https://www.postgresql.org/docs/15/libpq-connect.html (service files, URI format, keywords), https://www.postgresql.org/docs/15/functions-xml.html (`query_to_xml`), https://www.postgresql.org/download/linux/ubuntu/ (the apt repository) (not re-fetched in this run; every behaviour relied on — service files with a password, an unknown keyword refused naming only the file and line, `pg_export_snapshot` in a read-only transaction, `--snapshot`, restoring into a fresh database — was checked against the sandbox's PostgreSQL 16.15 and its tests). The CI step's apt commands are from the download page and are untested here (no CI from the sandbox).

## D-065 — Comparing and restoring record versions, and what an edit conflict returns: a pure compare in core, restore as a new checked version of the record row only, the conflict's changed names beside its issues, an arrangement lock and loop guard (2026-11-23, autopilot T-030, T-031)
`packages/core/src/record-compare.ts` compares; `packages/db/src/record-versions.ts` (`compareVersions`), `catalog.ts` (`updateRecord`'s `conflict`) and `record-restore.ts` (`restoreVersion`) use it; `packages/db/migrations/0006_arrangement_guard.sql` guards the arrangement. Follows D-063.
- **Compare is pure and lives in core.** `compareRecords(before, after)` validates both copies, refuses two records (`different_records`) or two organizations (`mixed_organizations`), and lists `{ name, change: added | removed | changed, before?, after? }`, sorted, with names as the database's `changed_fields` (D-063): core property names and `fields.<key>`, never `id`, `organizationId`, `createdAt` or `updatedAt`. So comparing version N−1 with N gives exactly N's `changedFields` (tested). Values are compared as JSON data (`sameJson`), so `jsonb`'s sorted keys compare equal. Title, kind, template, record type and parent changes are entries like any other (`title`, `kind`, `templateKey`, `recordTypeKey`, `parentId`); no separate flags, which the screens can derive. `compareVersions(db, org, record, from, to)` reads both versions in one statement, organization-scoped (another organization's record has no versions: `unknown_version`). Everything returned holds staff values: staff-only, never public output. *Rejected:* comparing in SQL (the History tab also compares a draft with a version, which isn't stored); comparing by `JSON.stringify` (key order).
- **An edit conflict returns what changed, by name only, beside its issues.** `updateRecord` now returns `RecordUpdateResult`: on `version_conflict` the failure also has `conflict: { expectedVersion, currentVersion, differences? }`, where `differences` lists `{ name, change }` only, from the version the edit started from to the current one, read after the refusal in the caller's transaction (so a save that waited on another's uncommitted update sees it once committed). **Never values** (independent review): anyone who can submit an edit gets a conflict, with any `expectedVersion` they like, so values there would let an editor read every old version, staff fields and removed values included. Values come only from an explicit `compareVersions` call, which T-041/T-043 must guard with the permission to read the record's history. `differences` is absent when the expected version is later than the current one (never stored) or a version no longer validates. Other refusals carry no `conflict`. The type is still assignable to `Validated<RecordVersion>`. **`updateRecord` trusts the input record's `organizationId`**: T-032 must set it from the signed-in session, never from a request (said in its doc comment). Which of the person's own edits overlap is the editor's (T-046), with `compareRecords` on its draft. *Rejected:* encoding the differences in issues (an `Issue` has path, code and message only); locks or a merge (the version number is the lock).
- **Restore writes a new version, never rewinds.** `restoreVersion(tx, org, record, N, { expectedVersion, actor, reason? })` builds the record from version N's snapshot with `updatedAt` = max(stored, now), and writes it through `updateRecord` with the reason `restored version N` (and `: ` and the person's reason, if given). History keeps every version; a restore can itself be restored over. Refused, storing nothing: `unknown_record`, `unknown_version`, `version_conflict` with its `conflict` (the person was looking at an older version), `no_changes` (version N is the record as it is now), `read_committed_required` (any other isolation level), `missing_reference` (a parent, represented record, template or type deleted between the checks and the write: the foreign key's 23503, mapped only for a restore; other writers still throw it, D-060), `unknown_property`/`invalid_option` (only `expectedVersion`, `actor`, `reason`; options only `now`, `confirmMadePublic`).
- **Today's checks run first, and failures are reported, not saved.** The old content is checked as a save would be now: the current version of its template (`checkRecordAgainstTemplate`, with the rights checker by default, the identifier checker from today's identifier types, and the record link and place checkers built from the records it links to as they are now, so a link to a record since gone, or to another organization's, is `unknown_record`); `identifierFieldIssues` against the record's identifiers as they are now; its record type as it is now; for archival units whose parent or level differs from the stored row, a parent that exists, is an archival unit it can be filed under, isn't itself or a descendant (`loop`) and keeps the tree within `MAX_ARRANGEMENT_DEPTH`, and children that still fit a changed level; for digital assets, a represented record that still exists. Every problem is returned at its path in the record, all of them (a check that can't run, such as the identifier checker when the types don't read, is reported and the others still run); nothing is stored. The descendants' depth is walked only as far as the room left under the new parent and at most `MAX_DESCENDANTS_WALKED` (100 000) rows (`too_many_descendants` beyond).
- **Restoring into a field public today needs confirmation** (independent review). A value stored while its field was staff-only, removed, and the field then made public never went through the made-public confirmation (no record held a value then). So every restored value that lands in a field public today and differs from the record's current value is listed (`public_field_restored`), and the restore waits for `confirmMadePublic` naming **exactly** those field keys, as the person saw them: a list that changed since (another field made public, another value) is refused and shown again. The title is not in the rule: core's public views always carry it (`PublicRecord.title`), so an old title was never staff-only.
- **A restore's refusal quotes no values** (second review). Core's messages may quote a value (`"X" is not a … this field allows`, an old number that doesn't fit a format, an unknown type key), and a refusal must not become a way to read old versions. Every issue from core's checks and from reading the stored rows keeps its code and path and gets fixed text (a short table by code, a generic sentence otherwise), as S-007 did for `publicOutput`. Restore reveals an old version's content once it succeeds (it becomes the record), so **restore requires the permission to read the record's history as well as to edit it** (T-032, T-041, T-043). *Rejected:* comparing with the field's visibility when the old version was written (template history would have to be matched to every version; the simplest rule is safe and the list is short). Publish-time rules (`rightsPublishIssues`, deeds and restrictions, D-043, D-056) are not restore's: restoring doesn't publish, and T-034 runs them at publishing.
- **Restore covers the record row only, not identifiers.** Versions hold the record row (D-063); identifier sets live in their own tables (D-061), aren't versioned, and keep their own history as former numbers. So restore never changes a record's current or former numbers, and can't break uniqueness. An old identifier field naming a number the record no longer holds is reported (`identifier_not_held`); the person puts the number back through the identifier save, which runs the uniqueness rules, then restores. *Rejected:* restoring identifiers too (they aren't in the snapshot; reconstructing them from former numbers would guess, and could take a number another record now holds); versioning identifier sets now (a schema change T-030 doesn't need).
- **Locking.** The record row is locked `FOR NO KEY UPDATE` first, inside a savepoint, so the record and its identifiers (`saveRecordIdentifiers` takes the same lock) can't change between the checks and the write. Templates, types and other records aren't locked: a change committing in that instant can slip past the template checks, as for any save until T-032's service layer re-checks in its transaction.
- **The arrangement: one lock per organization, and a guard in the database** (independent review: two restores at once, A under B and B under A, each saw no loop and both committed). Migration 0006: `arrangement_lock(organization)` takes an exclusive transaction-level advisory lock (two-int key space, classid 65, so it never meets the identifier or migration locks); a non-deferred `AFTER INSERT`/`AFTER UPDATE OF parent_id, level` row trigger (`zzzz_records_arrangement_*`) takes it whenever a unit gets a parent or its parent or level changes, then walks up from the unit through the rows as now committed, refusing a loop (`records_arrangement_loop`) and more than 63 ancestors (`records_arrangement_too_deep`); and when the parent changes, it walks down the unit's own subtree only as far as the room left under the new parent, stopping at the first unit past it, and refuses the move if any descendant would sit deeper than 64 (second review: walking up alone let a deep subtree be moved under a deep chain). Both are core's rules (`validateArrangement`), so the check never goes beyond core (D-060). **Levels are not checked by the database** (a unit under its parent, children under a changed level): they stay the writer's check, after taking the lock. The second of two such writers waits for the first to finish and its walk, a new statement under Read Committed, sees the first's change. So no writer, direct SQL included, can make a loop. Not deferred, so the refusal is the statement's, inside the writer's savepoint, and `updateRecord`/`insertRecord` return it as `loop`/`too_deep`; under Repeatable Read or Serializable the trigger refuses (`OC061` with its own message, `arrangement_require_read_committed`; mapped to `read_committed_required`), as identifiers do (D-061). `restoreVersion` decides up front, from the version and the row as read, whether the restore changes the parent or level, and then takes the lock **before** the record row's lock (if the row changed in between, its version no longer matches and the restore is a `version_conflict`), so its own checks see a settled tree and report `loop` cleanly. **Deadlocks:** a writer that holds the lock (it moved a unit) and then waits for another record's row, while that row's holder waits for the lock, deadlocks; PostgreSQL refuses one, which gets `retry` (inside a savepoint) or fails at that statement, and the caller retries the whole transaction. Any transaction that moves units and then writes other records can meet this. **Long imports hold the lock** from their first arrangement write to COMMIT, stopping every other arrangement change in the organization: commit per batch. Levels against the parent and children, and descendants' depth, stay the writer's checks (restore here, T-032's service). *Rejected:* `FOR SHARE` on the new parent's ancestor chain (moving any of them takes the same organization lock, so it adds nothing, and it would deadlock with `FOR NO KEY UPDATE` writers); a deferred constraint trigger (both commits' checks can run before either is visible, so it needs the lock anyway, and its refusal would come at COMMIT, outside any savepoint); a lock per tree (the tree's top changes as units move).
- **Restore is a save.** The service layer must wrap it like any save (T-032): the same permissions, `refreshRecordTerms` after it, the change log, and for a published record T-034's publish re-check.
- **For T-032 and T-043:** the actor must be the signed-in person (D-063); compare and restore are staff-only and need the record's read and edit permissions (T-041); the API returns `conflict` with a 409.

## D-066 — Staff search: a generated, folded tsvector on records, pure-SQL accent folding, identifier lookup through the stored key, staff only (2026-11-23, autopilot T-028)
`packages/db/migrations/0007_staff_search.sql` adds `records.search_document` and `public.search_fold`; `packages/db/src/search.ts` has `searchRecords(db, org, query, { limit, after })`. Follows D-050 (the query is always a `sql` parameter, parsed by `websearch_to_tsquery`), D-060 (the organization in every `WHERE`) and D-061 (the identifier key).
- **STAFF ONLY.** The document holds every record's title and every string of its fields: staff-only fields, unpublished and withdrawn records, donor and accession notes. **The public search (Phase 4) must build its own index from the published public views of published records (`publicOutput`) and must never read `records.search_document`, call `searchRecords`, or use either to pick, count, rank or order public results** — a hit, a count or a rank on a staff-only word reveals it. The public sites' read-only role (D-034) gets no `SELECT` on `public.records`. `searchRecords` has no scope option; an unknown option (`public: true`) is refused (`unknown_option`), never ignored. Said in the migration, the module header and the function's comment.
- **A stored generated column, not a trigger or a table the data-access layer writes.** `search_document tsvector GENERATED ALWAYS AS (public.record_search_document(title, fields)) STORED`, with a GIN index. The database recomputes it on every insert and update by any writer (`updateRecord`, `restoreVersion`, direct SQL), and no writer can set it (SQLSTATE `428C9`, tested), so it is never out of step or forged. Identifier saves need no upkeep: lookup reads `identifier_holdings`, which the saves themselves write. *Rejected:* a column the data-access layer fills with core's folding (a direct writer, a restore or a forgotten call leaves it stale, and the query side would need the same JavaScript); a separate table kept by a trigger (needs write grants or `SECURITY DEFINER` for the app role, and could be forged by any role allowed to write it); `unaccent` (an extension a host may not install, D-035).
- **Accent folding in pure SQL, the same function for document and query.** `public.search_fold(text)` (IMMUTABLE, fixed `search_path`): `normalize(…, NFKD)` (accents split off; full-width, ligature and superscript forms become plain letters); combining marks of the general diacritic blocks removed (U+0300–036F, 1AB0–1AFF, 1DC0–1DFF, 20D0–20FF, FE20–FE2F); `ß ẞ → ss`, `Æ æ → ae`, `Œ œ → oe`, `Þ þ → th`, and `Ø ø Ł ł Đ đ Ð ð Ħ ħ Ŧ ŧ ı` to their plain letters; Greek and Cyrillic capitals lowered by a fixed `translate` table (final `ς` → `σ`), then `lower()`. So Latin, Greek and Cyrillic fold the same on every server, including the gate's `--no-locale` one where `lower()` only folds ASCII; case in other scripts follows the database's locale, the same way for the document and the query. The 'simple' configuration: no stemming and no stop words (records are in many languages; a stemmer for one would mangle the others). Deliberately generous, like `identifierKey`: `й` meets `и`, `ø` meets `o`. **Accent-insensitive means Latin, Greek and Cyrillic only.** Marks outside those blocks are kept: Hebrew points (niqqud), Arabic vowel marks (harakat) and Indic vowel signs stay in the document and the query, so vocalized and unvocalized Hebrew or Arabic text do not match each other (`שָׁלוֹם` does not find `שלום`, tested). Folding them would be a fold change and a rebuild (below). *Rejected:* core's `identifierKey` for text (it keeps accents and removes spaces); folding in JavaScript only (the database could not fold the document itself).
- **UTF-8 only.** `normalize()` works only in a UTF-8 database, so the migration refuses any other encoding with a clear message rather than leaving every record write failing. Oculus databases are UTF-8 (the gate's server is created `-E UTF8`; T-051 must create production's the same way).
- **What is indexed.** The title (first 2,000 characters, weight A) and every JSON string anywhere in `fields`, in `jsonb_path_query`'s fixed order (weight C): text, term labels and URIs, identifier values, dates as typed, link labels and IDs. Object keys are not. Only the first 100,000 characters of the folded field text: a tsvector is limited to 1 MB, and core allows a record 1,000,000 characters of text, so without the cap a large record would be refused by the database. A test stores nine fields of nearly 100,000 UTF-16 units of distinct 4-byte-character words (about 0.53 MB of tsvector) and shows words past the cap aren't found. Words over 2,047 bytes are skipped by PostgreSQL. Raising the cap or changing the fold is a migration that replaces the function and then calls `public.rebuild_search_documents()` (an edited IMMUTABLE function alone would leave stored documents folded the old way).
- **Write cost and the 1 MB limit.** The stored tsvector widens every record row (TOASTed when large) and is recomputed, with its GIN entries, on every record write, including writes that change neither title nor fields. PostgreSQL limits a tsvector's lexemes and positions together to under 1 MB (1,048,576 bytes). The densest text found is hyphenated pairs of distinct 4-byte letters (`X-Y` indexes `x-y`, `x` and `y`, three words for four characters): at the 100,000-character field cap plus a full title that comes to about 765,000 bytes (the whole value about 1.07 MB with its 4-byte word entries, which don't count), so the margin is only about 20–27% (the review estimated about 20%; tested, the test asserting the figure stays between 700,000 and 800,000 bytes). **Any raise of the 100,000-character or 2,000-character cap must redo that calculation and the worst-case test**, or the largest records core accepts would be refused by the database on save.
- **Rebuilding the stored documents.** The documents are computed when a record is written, so they keep whatever `normalize()` (PostgreSQL's Unicode tables, which a major version may update) and `lower()` (the C library's or ICU's rules for the database's locale, for scripts other than Latin, Greek and Cyrillic) did at that time. After a PostgreSQL major upgrade by `pg_upgrade`, a C library or ICU upgrade, or a locale change, and in any migration that changes the fold, run, as the role that owns `public.records` (the migrations' role), in a quiet moment: `psql "$OCULUS_DATABASE_URL" -c 'SELECT public.rebuild_search_documents()'`. It drops and re-adds the generated column and its GIN index in one transaction under an `ACCESS EXCLUSIVE` lock on `records` (no reads or writes until it commits; time grows with the table): the only way to recompute a stored generated column without updating every record, which the version triggers refuse (D-063) and which would put a false edit in every record's history. No row trigger fires; record versions and `record_versions` are untouched (tested, with a stand-in fold change). It runs with the caller's rights, so for any role but the table's owner it fails (`must be owner`, SQLSTATE `42501`) and changes nothing (tested with a role holding the app's `UPDATE` grant); `EXECUTE` is not revoked from `PUBLIC`, since a revocation would stop backups restoring with `--no-privileges` (D-064). Migration 0007 builds the column with the same function, so there is one definition. A restore from a backup (D-064) needs nothing: generated columns are not dumped and are computed as rows are restored.
- **Identifiers through the stored key.** The whole query (after cleaning) goes through core's `identifierKey` and is matched against `identifier_holdings.key` (index `identifier_holdings_lookup`), current and former numbers of every type, including former numbers of types that no longer exist. So `ｄｈｓ－０００１`, an en dash or a Cyrillic look-alike find `DHS-0001`, and an old number finds the record that held it; digits and letters stay apart (`0` is not `O`), and dashes are kept, as `identifierKey` decides (D-009). A number dropped from a record no longer finds it.
- **Queries.** Text, at most 500 UTF-16 units (`query_too_long`, checked before any other work), not empty after cleaning (`empty_query`); control characters (NUL can't be sent to PostgreSQL) and unpaired surrogates count as spaces. The query is folded by the same SQL function and parsed by `websearch_to_tsquery('pg_catalog.simple', …)` as a parameter: quotes for phrases, `or`, `-` to exclude; tsquery operators, quotes and SQL in the text are just words (tested). **A query that a record with none of its words would match finds nothing by text** (`querytree` = `T`): an exclusion alone (`-chair`, `-a -b`) and any exclusion OR'd with the rest (`chair or -table`, `"a b" or -c`). Such a query means "every record without the excluded word", which the index can't find without scanning every record of the organization, so it is not run, and the OR'd words find nothing either: `chair or -table` does not return the chair. An exclusion ANDed with words (`chair -table`, `chair or lamp -table`) runs as usual. The identifier lookup runs for every query. Tested. A later screen (T-046) may tell the person why such a query found nothing.
- **Order and paging.** Identifier matches first, then `ts_rank` (title words weigh 1.0, field words 0.2) descending, then record ID. The rank is kept as `ts_rank × 1,000,000` rounded to a whole number, so keyset paging compares exactly (a `real` printed under a session's `extra_float_digits` could skip or repeat a row between pages); `rank` in a hit is that number ÷ 1,000,000 (0 for a number-only hit). The rank key and record ID leave the query as text (so the cursor carries them exactly), but the final `ORDER BY` names the underlying columns (`hits.grp, hits.rank_key DESC, hits.id`): a bare name would sort the text output column, putting a 6-digit rank after 5-digit ones and skipping hits between pages while the keyset `WHERE` compares them as numbers (found by review; tested with ranks of different lengths and a walk one hit a page). `next` is an opaque cursor (`group.rankKey.recordId`), checked strictly on the way back (`invalid_cursor`). Default 50 hits a page, at most 200. A hit is `{ recordId, title, rank, matchedBy }`, `matchedBy` being `identifier` and/or `text`.
- **Organizations apart.** The organization is in every `WHERE` (holdings, records, the join), so the same title, words or number in two organizations each find only their own, and a cursor from one organization reveals nothing of another (tested). The GIN index is shared by all organizations; the filter is never optional.
- **Cost grows with the organization (and the whole table).** `ts_rank` is computed for every matching record of the organization on every page, since ranking can't use the index, and the GIN index has no organization column, so the index scan finds matches in every organization before the filter. A common word therefore costs in proportion to how many records hold it: the review measured about 260–540 ms per page at 50,000 records. Fine for staff use behind a login today; **whatever exposes search over HTTP (T-043) must set a `statement_timeout` for the search query (or the request) and/or cap the matches ranked**, and should be measured again then. *Not done now:* a composite index with the organization (needs `btree_gin`, an extension, D-035) or a match cap (changes results silently).
- **Not here:** permissions (T-041: who may search staff records), the API and screens (T-043, T-046), filters by kind, template or field (later, as `WHERE` conditions beside the same document), and the public search (Phase 4, above).
- Sources: https://www.postgresql.org/docs/16/textsearch-controls.html (`websearch_to_tsquery`, `ts_rank`, weights), https://www.postgresql.org/docs/16/textsearch-limitations.html (1 MB tsvector, 2 KB lexeme, 256 positions per lexeme, position 16,383), https://www.postgresql.org/docs/16/textsearch-features.html (`setweight`, `querytree`), https://www.postgresql.org/docs/16/functions-string.html (`normalize`, UTF-8 only), https://www.postgresql.org/docs/16/ddl-generated-columns.html (immutable expressions, not writable), https://www.postgresql.org/docs/16/functions-json.html (`jsonb_path_query`), https://www.postgresql.org/docs/16/textsearch-dictionaries.html (the `simple` dictionary lowercases and has no stop words by default), https://www.postgresql.org/docs/16/sql-altertable.html (dropping and adding a column, `ACCESS EXCLUSIVE`, table rewrite), https://www.postgresql.org/docs/16/pgupgrade.html (stored data is kept as is), https://www.postgresql.org/docs/16/locale.html and https://www.postgresql.org/docs/16/collation.html (`lower()` follows the locale's C library or ICU rules); read 2026-11-23.

## D-067 — The service layer: one writer with its own database role, every save checked under locks in one transaction, deletion as a tombstone version (2026-11-23, autopilot T-032)
`packages/service` (`createService`) is the only code that writes records and their related rows: identifiers, term usages, versions and the arrangement. `packages/db/migrations/0008_record_deletion.sql` adds tombstones and definition locks. `record-checks.ts` holds today's checks, now shared with restore. `record-delete.ts` deletes, and `roles.ts` grants the writer role. Follows D-060 to D-065. (Numbered 0008 because branch `autopilot/T-028` holds 0007; the runner allows gaps. D-066 is T-028's.)
- **One role writes.** Migrations still create no roles (D-063). The deployment (T-051) creates one login role and, as the owner, runs `grantWriterRole(tx, role)`: USAGE on `public`, SELECT on every table, and exactly `WRITER_PRIVILEGES`, which is what the data-access code uses and no more: INSERT and DELETE on `records` (plus UPDATE); INSERT only on `templates`, `record_types` and every version table; INSERT and UPDATE on `organizations` (UPDATE only because the code row-locks it, which needs UPDATE), `identifier_types` (a real write as well as a lock: `updateIdentifierType` changes a type's definition and uniqueness rule), `identifier_counters` and `terms`; INSERT, UPDATE and DELETE on `identifier_holdings` and `record_term_index` (both use `ON CONFLICT … DO UPDATE`); INSERT and DELETE on `record_identifiers`, `former_identifiers` and `record_terms`. Nothing can delete organizations, templates, record types, identifier types, counters or terms. No table grants anything to PUBLIC, and any other role gets at most SELECT. `grantWriterRole` only adds privileges; it never revokes what a role already holds. So `checkConnection()` (`checkWriterConnection`) checks the connection against an **allowlist**: the writer must be a plain role holding exactly the writer's grants. It checks both the role in effect and the login (`session_user`, since a session can `SET ROLE` back to the role it logged in as).
  - *Why an allowlist.* Two review rounds each found another way past a denylist of dangerous roles and privileges, and `has_*_privilege` hid several of them. Those functions count only inherited privileges, so a member with INHERIT FALSE, NOINHERIT or ADMIN only (which can re-grant itself) could `SET ROLE` into a role holding TRIGGER, `SET session_replication_role` or CREATE. They also don't see column grants: `UPDATE (definition)` on `template_versions` rewrote stored history. And membership in `pg_create_subscription` plus CREATE on the database let a subscription's apply worker, which runs in replica mode, insert a record with no version.
  - The roles must have none of SUPERUSER, CREATEROLE, BYPASSRLS or REPLICATION.
  - They must be a member of **no role at all**: any `pg_auth_members` row, whatever its INHERIT, SET or ADMIN option (PostgreSQL 16 added those columns; only `member` is read, so 15 works too). That alone closes every inherited path, `pg_create_subscription`, the server-file and server-program roles and `pg_signal_backend` (which could end other sessions: denial of service only, but refused with the rest). The second review's separate checks of superuser membership and the server roles are therefore dropped as redundant.
  - They must own nothing in `public`, not `public` itself and not the database.
  - Privileges are read from the catalogs' ACLs (`aclexplode`), for grants to the role itself or to PUBLIC:
    - table and sequence privileges in `public` must be a subset of SELECT plus `WRITER_PRIVILEGES`, and PUBLIC gets none;
    - there must be no column privilege at all (`pg_attribute.attacl`);
    - there must be no default privileges (`pg_default_acl`), apart from PUBLIC's built-in EXECUTE on functions and USAGE on types, which a revoke-only row repeats;
    - there must be no CREATE on the database or on `public`;
    - there must be no SET or ALTER SYSTEM on any parameter (`pg_parameter_acl`, PostgreSQL 15 and later, the oldest supported).
  - **No GRANT OPTION** (fourth review): even on its own privileges, a grant option would let it hand them to other roles. The ACL's grantable bit is read, so a grant option is reported as `extra_privilege`.
  - **Nothing it owns and no other privileges, anywhere in the database** (`pg_shdepend`, this database's rows and shared ones). It must own no object at all (`owns_object`). That covers subscriptions: in the fourth review, a subscription the writer owned outlived the revoked grants that made it, and `ALTER SUBSCRIPTION … SET (run_as_owner = true)` re-pointed it so its apply worker, which runs in replica mode, inserted unversioned records. It also covers schemas, large objects, foreign servers, publications and other databases. Its non-default privileges must be only on public's tables (their columns are the column check's), schema public and databases (`object_privilege`). Functions, types, other schemas, foreign data wrappers, servers, large objects and parameters are refused; default-privilege and parameter entries are reported here as well as by their own checks.
  - **No CREATE on any schema** (`schema_create`, to the role or PUBLIC). Triggers pin `search_path` and qualify every name, but owner sessions (migrations, backups) use the default search path, where an object planted in another schema could be picked up.
  - **Not in replica mode, and nothing that starts its sessions in replica mode** (fourth review). This session's `session_replication_role` must be `origin` (`replication_role`). Settings in `pg_db_role_setting` for the role in this database or in all databases must be only `ALLOWED_ROLE_SETTINGS`: `lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`, `idle_session_timeout`, `transaction_timeout` and `application_name`, so T-051 can still set time limits. No setting for every role, in this database (`ALTER DATABASE … SET`, `ALTER ROLE ALL IN DATABASE … SET`) or in all, may set `session_replication_role` (`role_setting`). Other roles' unrelated settings are left alone.
  - The role in effect must hold every one of the writer's grants.
  - Messages name at most five items and count the rest.
  - **The check runs only when `checkConnection` is called.** It is not periodic, and nothing in the database re-runs it. T-051 must call it at service startup and after every migration (a new table, a default privilege or a grant since the last check changes the answer), and should refuse to start the service when it reports anything. Tests cover each case: memberships with every option, `pg_create_subscription`, each attribute, parameters to the role and to PUBLIC, CREATE on the database and on the schema, each extra table and column privilege, default privileges, each missing grant, and an owner login that `SET ROLE`s to the writer.
- **Every guard trigger fires in replica mode** (0008, the root fix for the fourth review's replica-mode bypasses). `session_replication_role = replica` skips ordinary (ORIGIN) triggers, so a session started in replica mode could write records without versions, rewrite history or skip the arrangement guard. 0008 runs `ALTER TABLE … ENABLE ALWAYS TRIGGER` on every non-internal trigger on public's tables (0002 to 0008). **Any later migration that adds a guard trigger must `ENABLE ALWAYS` it too**, and tests that turn a trigger off and on must turn it on with `ENABLE ALWAYS TRIGGER`; a plain `ENABLE TRIGGER` resets it to ORIGIN, and a test checks every trigger is ALWAYS. Foreign keys are internal triggers that replica mode still skips, and only a superuser could change them, so the connection check above refuses replica mode as well. Backups are unaffected: `pg_dump` creates triggers in its post-data section, after the rows are loaded, and dumps the ALWAYS state with them, so restores load data without tripping the version check and come back with the same trigger states (the round-trip tests pass). Tests in replica mode, as the superuser: a record write without its version, a version update, a template version update and a delete without a tombstone are all still refused.
- **Tested on a database owned by a plain role**, as on shared hosting: migrated as that owner, the writer granted by it, and the check returns nothing for the writer and `owner` for the owner.
- **Template and record type versions are append-only too** (0008, third review). Triggers refuse UPDATE, DELETE and TRUNCATE (`template_versions_append_only`, `record_type_versions_append_only`) for every role that can't disable triggers, as for `record_versions` (D-063), so even a stray column grant can't rewrite a definition's history. Two older tests that simulated an owner's hand edit now turn the trigger off inside their transaction, as the record version tests already did.
  *Possible later step:* column-level `GRANT UPDATE (…)` on `organizations` and `identifier_types` instead of table-level UPDATE, so a lock doesn't also allow rewriting other columns. It would need `checkConnection` to allow exactly those column grants, which it now refuses, and the backup comparison (D-064) reads table-level ACLs only, so it was skipped.
- **What the writer can still do with direct SQL**, around the service: change an identifier type's uniqueness rule (`all_time` to `none`, say) or definition; delete a record's identifier holdings and then the record (with a valid tombstone), which frees its `all_time` numbers; write `fields` values the service would refuse, such as links to records that don't exist or to records being deleted (JSON has no foreign key); take the advisory locks below and hold them; `LOCK TABLE` any table it may write (which UPDATE or DELETE allows), stalling every organization until it ends. **What it can't do:** change or remove any version (no UPDATE, DELETE or TRUNCATE on version tables, plus triggers); write a record without its version, delete one without its tombstone, write anything after a tombstone, or reuse a deleted ID; TRUNCATE any table; disable, drop or alter triggers, tables or functions (owner only); `SET session_replication_role` (superuser, or a `GRANT SET ON PARAMETER`, which `checkConnection` refuses); create tables in `public`; move rows between organizations (identity triggers, composite foreign keys). So the service's code is the only trusted writer, and the writer role's password is as sensitive as the owner's for data integrity.
- **Any connecting role can stall saves.** `arrangement_lock`, `definition_lock` and PostgreSQL's own `pg_advisory_*` functions are executable by PUBLIC, and their keys are predictable (classid 65, 66 or 67 and a hash of the organization ID and key), so any role that can connect, even a read-only one, can take one exclusive and hold it, making an organization's arrangement writes or saves wait. That is denial of service, not a way to write. *Rejected for now:* REVOKE EXECUTE on the two wrappers from PUBLIC. It wouldn't help, since `pg_advisory_xact_lock` itself is PUBLIC and needs only the key; and a migration revoking from PUBLIC would add a revoke to every database, which the backup module (D-064) refuses to restore without privileges. **Rule:** only trusted roles may connect to an Oculus database at all. The deployment (T-051) gives login only to the owner (for migrations and backups), the writer and, later, any read role, and sets `lock_timeout`/`statement_timeout` for the writer, so a stalled save fails as `retry` or `timeout` instead of hanging.
- **The context carries the organization and the actor**, built by the caller from the signed-in session, never from a request (D-019, D-063). The service validates it (own data properties only; an unknown organization is `unknown_organization`). A draft or identifier set naming another organization is `wrong_organization` before anything is read. Every lookup uses the context's organization, so another organization's record gives exactly the same answer as one that doesn't exist (`unknown_record`, tested as equal results). Links, parents, scans, templates and record types resolve only within the organization.
- **Drafts, not records.** `createRecord(ctx, draft)` refuses an `id`, `createdAt` or `updatedAt`. The service makes the ID (random UUID v4) and stamps both times. `updateRecord(ctx, id, draft, { expectedVersion })` takes the ID, organization, kind and `createdAt` from the stored row (`kind_changed`, `wrong_record`), and sets `updatedAt` to max(stored, now). An unchanged draft writes nothing (`changed: false`). Drafts are copied as plain data first (`readPlainData`), so getters and proxies are refused. Unknown keys and options are refused.
- **One Read Committed transaction per operation**: the record, its version, its identifiers, the identifier-field check, `refreshRecordTerms` and the checks all commit together. Any refusal throws inside the transaction, so it rolls back entirely; for example, a number taken by another record leaves no record row or version behind.
- **Checks run under locks, so they stay true until COMMIT** (`recordCheckIssues`, also used by `restoreVersion` now, which closes D-065's "templates, types and other records are not locked"). The order is: the organization's `arrangement_lock`, whenever a unit is new with a parent or its parent or level changes, taken before the row (D-065; for an update this is decided from the row as committed, then confirmed by the version under the row lock); the record row `FOR NO KEY UPDATE`; linked, parent and represented records `FOR KEY SHARE` in ID order (a deletion's `FOR UPDATE` waits, and kinds never change); a shared `definition_lock` on the template and the record type; the identifier types `FOR SHARE`. New template and record type versions are INSERTs that row locks don't stop, so 0008 adds an advisory lock per (organization, key): exclusive in a trigger on every insert into `template_versions` and `record_type_versions`, shared in saves (two-int key space, classid 66 for templates and 67 for record types; 65 is the arrangement lock). Then come the checks: `checkRecordAgainstTemplate` with the identifier checker from today's types and the organization's record link checker, `checkRecordType`, the parent's level, loops, depth, and children against a changed level. After the writes, `identifierFieldIssues` runs against the numbers the record now holds; uniqueness is the database's unique indexes in the same transaction (D-061). Save messages are core's own (the person's input); restore keeps the fixed messages (D-065).
- **Identifiers.** They are saved with a create or an update, or on their own with `saveIdentifiers`. A number dropped from the record altogether (neither current nor former) is refused as `numbers_dropped` unless `confirmDropped` lists exactly those numbers, because under `all_time` it becomes free (D-061). Edits to a former number's note or date need no confirmation. Dropping a number an identifier field shows is refused even when confirmed.
- **Clean errors.** Refusals are `{ ok: false, issues, conflict? }` (T-031's names-only conflict). Deadlocks and serialization failures retry the whole transaction (`attempts`, default 3), then return `retry`. Thrown errors map by SQLSTATE to fixed text (`missing_reference`, `refused_by_database`, `not_permitted`, `read_committed_required`, `timeout`, `internal_error`), never the database's message. The raw error goes only to `onError` (for the server log), and a failure of the hook is ignored.
- **Deletion is a tombstone version.** `record_versions.action` is `'save'` or `'delete'`. A delete version holds the row exactly as it was, at the number after the row's version, with who, when and why. The database enforces this for every writer: a DELETE of a record needs this transaction's delete version (`records_delete_needs_version`; TRUNCATE is refused the same way); a delete version can't commit while the row exists (`record_versions_delete_done`, deferred); nothing is stored after it (`record_versions_after_delete`, independent review: a writer could otherwise store a delete version, push the row's version past it, save, then delete again); the row can't be updated once it is stored (`records_deleted`); and the ID is never reused (`records_id_used_before`). That trigger alone is not enough under Repeatable Read or Serializable, where a concurrent deletion's tombstone isn't in the inserting transaction's snapshot. There the version table's primary key (a second version 1 for the ID) and serialization failures are what stop reuse. `deleteRecord` locks the row `FOR UPDATE`, then refuses `has_children`, `represented` (scans), `linked_from` (`record_link`/place values anywhere in other records' `fields`, found by `jsonb_path_exists`) and `holds_identifiers`. The messages give counts, never IDs. It then clears term usages, writes the tombstone and deletes. A save linking to the record and the deletion serialise on the row lock: tested both ways with two connections. *Rejected:* a soft-delete flag (every query would need to filter it, and a forgotten filter leaks); deleting identifiers with the record (it would silently free `all_time` numbers).
- **T-018a and S-013 (loans).** Loans, accessions and moves are not stored yet (core only), so nothing here closes loans. The rule for when they are: closing a loan in by an accession, and deciding that a loan is over, happen only inside the service, from the register and loan book read in the same transaction under the record locks above, never from a register or book a caller hands in (the hole all three T-018a reviews found). That needs storage tasks for accessions, loans and moves first.
- **Left for later:** permissions (T-041; restore also needs the history permission, D-065; the deletion counts and the target kind in `wrong_record_kind` may tell a person about records they can't open); publish re-checks (T-034); an index of links instead of scanning the organization's `fields` on every deletion; keeping `all_time` numbers of deleted records reserved; allocation of auto-numbers through the service.
