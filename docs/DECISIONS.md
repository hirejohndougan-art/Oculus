# Decisions

Newest at the bottom. Each entry gives the choice, what was rejected, and why.

## D-001 — Public repository (2026-11-20, John)
Oculus is developed in a public GitHub repository. Nothing private goes in it: no secrets, no private data about real people, and no code from John's private repositories (see D-002).

## D-002 — MIT license; permissive dependencies only (2026-11-20, John)
The code is MIT-licensed, so any archive, museum or historical society can use it. Dependencies must be MIT, BSD, ISC, Apache-2.0 or similarly permissive. GPL, AGPL and LGPL are not allowed, because they would change the terms for anyone installing Oculus. Code from John's private repositories (Polybius, Blueprint and others) may be brought in only by an entry here written by John.

## D-003 — Built by autopilot, no human approval (2026-11-20, John)
Three scheduled sessions each night (build, upkeep, security) do one task each, check it against the gate, and merge to `main` themselves. This is the same model as John's Blueprint, Argus and FerroJS projects. John can switch to pull requests he approves by changing step j of AUTOPILOT.md and recording it here.

## D-004 — No AI inside the product (carried over from the Polybius project)
Oculus contains no hosted AI, no AI SDKs and no pretrained models. Suggestion features use classical retrieval: BM25 plus a curated synonym list. One exception: OCR may use an engine's trained text-recognition models (D-033).

## D-005 — Platform name and parts (2026-11-20, John)
The platform is **Oculus**. Its staff back end is called **Polybius** and its public sites are called **Hermes**. These are names for parts of one product, not separate products. **Superseded by D-018.**

## D-006 — Toolchain, Node version and the license allowlist (2026-11-20, autopilot T-001)
npm workspaces (`packages/*`), TypeScript 6.0 in strict mode (plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`), ESLint 10 with typescript-eslint's strict type-checked rules, Prettier 3 and Vitest 5. `.nvmrc` is Node 26, the Active LTS line ("Lithium", LTS from October 2026, supported to April 2029); `engines` allows Node 22 and later, because the build sandbox runs 22. - Vite is pinned to 7 as a dev dependency. Vitest 5 accepts Vite 6–8, but Vite 8 requires `lightningcss`, which is MPL-2.0. MPL is file-level copyleft, so it is treated as not allowed under D-002, even for dev tools. Vite 7 has it only as an optional peer, so it is not installed.

- Prettier checks code and config only; the hand-written Markdown docs and the generated mockup are excluded so the gate doesn't rewrite them.

## D-007 — Record kinds and the arrangement levels (2026-11-20, autopilot T-002)
Six record kinds: object, archival unit, digital asset, agent, place and event. An archival unit has a `level` (fonds, series, collection, file or item) and an optional `parentId`.
- **The levels follow how Polybius works today:** Fonds (whose records) › Series (what kind of records) › Collection (the group items are filed in, by topic or how the creator kept them) › File › Item. A unit can be filed under any higher level, so levels can be skipped: a collection can sit straight in a fonds, and an item straight in a collection. That keeps collections and series independent (PLATFORM_PLAN.md §1). Series and files can contain more of their own level (sub-series, sub-files), so the tree goes as deep as needed, up to a safety limit of 64.
- **A unit with no parent is allowed.** It's either a top-level fonds or collection, or something not filed yet (the "Needs Sorting" list).
- **Rejected: ISAD(G)'s level list as-is** (fonds, subfonds, series, subseries, file, item). It has no "collection" level between series and file, which is where Polybius files items today. Subfonds can be added later as a level if an organization needs it.
- **Rejected: collections as a separate many-to-many grouping outside the tree.** That would mean two ways to file the same item, which is harder to explain to volunteers and to show in a finding aid. A topical grouping that cuts across the tree can come later, as exhibits or tags.
- **Validation is strict.** Unknown properties, untrimmed titles, control characters, non-JSON field values and the keys `__proto__`, `constructor` and `prototype` are all reported. Nothing is fixed silently.

## D-008 — How dates are stored, bounded and sorted (2026-11-20, autopilot T-003)
Dates are stored as EDTF text (Library of Congress EDTF, 2019; ISO 8601-2). `parseEdtf` derives everything else from that text, so nothing derived is stored as the truth.
- **Supported:** levels 0 and 1 in full, and from level 2: qualifiers on single parts, X digits anywhere, sub-year groupings 25–41 and sets. **Rejected:** exponential years and significant digits (geological and astronomical time, not collections). Each part takes one qualifier and a date takes one trailing qualifier; that is stricter than some readings of the level 2 grammar, and can be loosened later without breaking stored data.
- **Bounds hold every possible day, and can be wider.** `earliest`/`latest` are for search and filtering, so leaving out a real possibility is worse than being wide. Seasons 21–24 don't name a hemisphere, so they cover both; winter covers December of the year before to February of the year after. `~` and `?` don't widen bounds: inventing a "± N years" range would be making things up.
- **Sort key** is `year*10000 + month*100 + day` of the earliest day (latest when the start is open). It's an exact integer up to year 999,999,999 and orders BCE years correctly. Dates whose year starts with X get no sort key and sort last, rather than as year 0.
- **Free text is converted only when the reading is safe.** Two-way forms ("1900s", "6/5/1920", "1920-25", "1901-05", "c1920", a leading dash, "'50s") are flagged, not guessed. Where EDTF can't say all the text said ("late 1920s" → `192X`, centuries), the result keeps the original words as a note.
- **Rejected: an EDTF package from npm** (such as edtf.js). The parser is small enough to own and test here, and owning it keeps the bounds, sorting and flag-don't-guess rules exactly as above. It can be compared against edtf.js in tests later if useful.

## D-009 — Typed identifiers: safe formats, comparison keys, uniqueness and numbering (2026-11-20, autopilot T-004)
Each identifier type has a key, a label, an optional format, a uniqueness rule (`none`, `current` or `all_time`) and optional auto-numbering: `year` (`2026.015`) or `prefix` (`DHS-0001`). A record has current identifiers, exactly one of them primary, and former ones. Former identifiers are history: they are never checked against today's format and may name a type that has since been removed.
- **Formats are a small language of our own, not regexes.** `#` is a digit, `@` an ASCII letter, `*` either, `{n}`/`{n,m}` repeats, `\` escapes. A format compiles to at most 200 single-character slots, and matching tracks every reachable slot at once, so it never backtracks. *Rejected:* compiling admin-written regexes (ReDoS) and regex "safety" checkers (incomplete).
- **Values are stored exactly as typed and compared by a key.** The key applies NFKC, maps Cyrillic, Greek and Armenian letters that look Latin and all dashes to `-`, folds case, and removes spaces and invisible characters. It errs towards calling identifiers the same. `0`/`O` and `1`/`l` stay distinct. *Rejected:* changing stored values, and the full Unicode TR39 confusables table (large; not read, so nothing claims to follow it).
- **The next number is the highest in use + 1,** counting former values, so retired numbers are never reused and gaps are not filled. Numbers the type's format could never produce are ignored. The caller supplies the year.

## D-010 — Field templates: field definitions, value shapes and the checker hook (2026-11-20, autopilot T-005)
A template is untrusted data: `{ key, label, description?, appliesTo: RecordKind[], fields }`, checked by `validateTemplate`, and checked again inside `checkRecordAgainstTemplate`, which fails closed with `invalid_template`. Each field definition holds `key`, `label`, `help?`, `kind`, `required`, `repeatable`, `visibility` (`public` or `staff`), `inherited`, `standards?` (`{standard, element, uri?}`) and kind-specific `options`, `vocabularies`, `identifierTypes` or `maxLength`. The flags and `visibility` must always be stated, with no defaults, so a field can never become public by being left out.
- **Value shapes:** text (one trimmed line), long_text, date (EDTF, checked with `parseEdtf`), list (one option value; several choices means a repeatable list), controlled_term `{label, uri?, vocabulary?}`, identifier `{type, value}`, link `{url, label?}`, rights `{uri, note?}`, place `{label, uri?, recordId?}`. A repeatable field stores a non-empty list. An empty value is left out, never stored as null, "" or []. URLs must be http or https with no user name, password or backslash; this checks what is stored and is not a guard against server-side requests.
- **Kind-specific checks plug in** through `options.checkers[kind]`, a function `(value, field, record) => FieldProblem[]`. A checker that throws or returns something malformed makes the value fail.
- **Hardening:** optional settings are read as own properties only; template keys and codes refuse `constructor` and `prototype`. Limits: 200 fields, 500 options per list, 10,000 options per template.
- **Rejected:** defaults for `visibility` and the other flags (a missing value could make a field public by mistake); `link` as a link to another record (a separate relationship feature, since publishing it could reveal unpublished records); requiring a vocabulary on every term (T-009 decides that).

## D-011 — How rights are stored and the publish rule (2026-11-20, autopilot T-007)
A record's rights are one canonical URI in the `uri` of the template field `rights`, stored as `{ uri, note? }` (D-010, D-015). Accepted values are the 12 rightsstatements.org 1.0 statements, the six Creative Commons 4.0 International licenses, CC0 1.0 and the Public Domain Mark 1.0. Either a statement or a CC tool meets the rule that a record needs rights before it can be published.
- **The rule covers the kinds that hold copyrightable content:** object, archival unit and digital asset. Agent, place and event records can be published without rights. A record whose kind is missing or unknown is checked anyway.
- **What the check reads:** only own, enumerable data properties of the exact frozen record being published. Getters, hidden properties and Proxies are reported as unreadable.
- **Canonical forms are the ones each issuer publishes.** rightsstatements.org uses `http://`, the `/vocab/` path and a trailing slash (its technical requirements v1.2.2 say `/page/` URLs "MUST NOT be used" in metadata). Creative Commons uses `https://creativecommons.org/licenses/by/4.0/`.
- **Variants are fixed only through `normalizeRightsUri`, which lists every change** (http/https, `/page/`, trailing slash, `deed`/`legalcode` endings, `www.`, a query or fragment, spaces). Stored values that aren't canonical are refused with `not_canonical`.
- **Rejected for now:** CC versions 1.0 to 3.0 and national ports (reported as `unsupported_version`; the full list couldn't be confirmed and none is current; add them if the Omeka migration needs them); CC's "Certification 1.0 US" (not a current tool); several rights values per record (`edm:rights` takes one).

## D-012 — Standards presets and the Dublin Core mapping (2026-11-20, autopilot T-006)
Three frozen starting templates built with the D-010 model: `dacs-archival-unit`, `spectrum-object` and `dublin-core-digital-asset`. Fields cite their source in `standards`: DACS element number and name (SAA, second edition, saa-ts-dacs.github.io version 2022.0.4; no URIs, because none are stable), Spectrum 5.1 unit of information names (where only the information group was confirmed, for rights and valuation, the element says "(information group)"), and DCMI terms with `http://purl.org/dc/terms/` URIs, on public fields only. The record's own `title` is DACS 2.3, Spectrum Title and dcterms `title`, so it is not a template field.
- **Privacy defaults: staff, and the organization opts in.** Anything that can name a private person or is internal starts as `staff`: donor and acquisition details, custodial and object history, where originals and copies are, storage and current location, appraisal, valuation and insurance, other numbers, credit line, sources, rights holders, and notes (including DACS 7.1). Public on purpose: conditions governing access (researchers need it; the help text forbids personal or donor-confidential reasons), the repository's name and location, and `rights` (D-011).
- **The Dublin Core mapping is separate data,** `{ template, entries: [{ field, term }] }`. `validateDublinCoreMapping(mapping, template)` checks it every time it is used: the template must be valid, every field must exist and be `public` (otherwise `staff_field`), and terms come from a closed list of 31 confirmed DCMI terms. `mappingForTemplate` re-targets a preset's mapping to a copied template. Unmapped fields are not published as Dublin Core.
- Rejected: dcterms cites in `standards` as the publishing source (a field switched to staff would keep its cite, and two sources could disagree); publishing credit lines, custodial history or rights holders by default (they often name donors or private owners); citing DACS 8.2 for rights (8.2 covers rights in the description itself; 4.4 is cited).

## D-013 — The effective record: how inheritance, own values and visibility combine (2026-11-20, autopilot T-008)
`effectiveRecord(id, records | indexRecords(...), templateFor, { checkers? })` returns a frozen, staff-side result: `{ id, kind, title, fields, entries, chain, notes, record }`. Each entry gives the value, `own`, the record it came from and the effective `visibility`.
- **Public output only ever comes from `publicView(effective)`,** which keeps only entries that are public and in the template, with no notes, no stored record and no ancestors.
- **Rights are checked with `effectivePublishIssues`,** which refuses rights that aren't public here (since D-015 requires a public `rights` field, today only a left-over `rights` key), then runs `rightsPublishIssues` on the public view. `rightsPublishIssues` itself refuses an effective record (`use_effective_publish_issues`).
- **Own value wins entirely;** a repeatable field's own list replaces the inherited one. *Rejected:* merging lists (an item couldn't drop an inherited value).
- **An empty stored value means "none"** and blocks inheritance from that record up. *Rejected:* treating it as absent (a cleared value could be published from an ancestor).
- **Only the record's own template decides whether a field inherits.** Going up, a unit whose template lacks the key is passed over; one with `inherited: false` stops the search; the nearest stored value decides. Every definition on the way must have the same kind and `repeatable`, and the value must pass the record's own template check and the caller's checkers (which see a frozen record; exactly the checked value is kept).
- **Visibility is the strictest along the chain.** Left-over keys are `staff`, never inherited and never public.
- **Any doubt fails the whole result:** a missing parent, a duplicate or unreadable ID, an invalid record, a loop, the wrong level, more than 64 levels, a bad template, or options that aren't plain. *Rejected:* partial results.
- **Snapshots:** `indexRecords` validates every record when built, so an index is one consistent frozen snapshot and must be rebuilt after edits; templates are validated afresh on every call. *Rejected:* lazy validation and caching templates by object identity (a shared object changed between calls turned staff into public in review).
- Notes may quote values and labels, so they are staff only.

## D-014 — Controlled terms: vocabularies, URI rules and near-duplicate detection (2026-11-20, autopilot T-009)
Terms keep the D-010 shape `{label, uri?, vocabulary?}`. Six vocabulary codes: `lcsh`, `lcnaf`, `lcgft`, `nomenclature`, `gnis` and `local`; a template's `vocabularies` may list only these. A term with no vocabulary is local, and templates accept it wherever the field allows `local` or lists no vocabularies. Local terms can't have a URI; for the others a URI is optional (built LCSH headings often have no authority record). The rules run by default in `checkRecordAgainstTemplate` (`controlledTermChecker`).
- **LC URIs** must be exactly the form id.loc.gov publishes, `http://id.loc.gov/authorities/{subjects|names|genreForms}/{LCCN}`, with the control number checked against LC's "The LCCN Namespace". Variants are refused (`not_canonical`); only `normalizeTermUri` fixes them, listing every change.
- **Nomenclature and GNIS URIs** are stored as given, because neither issuer's URI form could be confirmed (their sites couldn't be reached). Nomenclature must be a page on nomenclature.info; GNIS must not be on an LC or Nomenclature host. `termUriKey` compares URIs loosely without changing what is stored.
- **Near-duplicates** use classical methods only (D-004): `same_uri`, `same_label`, `same_words`, `abbreviation` (including spaced initials) and `similar_spelling` (edit distance 1, or 2 for keys of 10+ letters). Designators (numbers, letter-digit tokens, single letters, Roman numerals) must match; accents are removed only from Latin, Greek and Cyrillic letters; invalid or over-long terms are skipped and listed; work is budgeted and every limit reached is listed in `limitsReached`. It reports pairs and never merges anything. 50,000 hostile terms run in under 2 seconds.
- **Rejected:** requiring URIs for LC terms; inferring the vocabulary from the URI; normalizing Nomenclature or GNIS URIs when stored; all-pairs comparison; failing the whole check on one bad term; stripping every Unicode mark (merges words in Indic scripts); free-form vocabulary codes; synonym matching (needs a thesaurus).

## D-015 — Default field checkers, the rights field, and identifier values need a checker (2026-11-20, autopilot T-007a)
`field-checkers.ts` holds the ready-made checkers. `checkRightsValue` (rights) and `controlledTermChecker` (D-014) run by default in `checkRecordAgainstTemplate`. `makeIdentifierChecker(types)` validates the organization's identifier types once and returns a checker for the `identifier` kind.
- **A checker the caller gives replaces the default.** Leaving a kind out, giving `undefined`, or a checker on `Object.prototype` keeps the default, so a check can't be switched off by accident. To skip a check on purpose, pass `() => []`.
- **Identifier values without a checker are refused** with `unchecked`, never accepted. Uniqueness needs every record, so it stays with `checkNewIdentifier` and `uniquenessIssues` on the save path.
- **The stored rights value is `{ uri, note? }` in field `rights`.** The publish rule reads `fields.rights.uri` (own enumerable data properties only) and refuses a plain string, unknown properties and a bad note, so publishing doesn't depend on the template check having run.
- **The rights kind and the key `rights` go together:** at most one rights field per template, not repeatable, and always `public`.
- **Rights notes** (superseded by D-016: notes are not published and are left out of `publicView`). Keep them free of private details anyway.
- **Rejected:** an `identifierTypes` option on every check; letting identifier values pass unchecked; treating `undefined` as "off"; a bare URI string as the stored rights value; accepting both shapes; several or staff-only rights fields.

## D-016 — Public output: Dublin Core, JSON-LD and oai_dc (2026-11-20, autopilot T-010)
`publicOutput(view, mapping, { baseUrl, published, checkers?, currentTemplate?, templateFor? })` (`templateFor` added by D-020, `records` by D-021) returns `{ id, dublinCore, jsonLd, jsonLdText, oaiDcXml }` or issues. It never throws.
- **Input is only a real `publicView` result,** recognised by a WeakMap mark `effective.ts` sets beside each view, never by its shape. Output is refused unless all of these pass: `effectivePublishIssues`; `validateDublinCoreMapping` against the view's template; for objects, archival units and digital assets, a mapping of `rights` to `rights` or `license` (`rights_not_mapped`); `checkRecordAgainstTemplate` on the view's values (default checkers plus the caller's, which replace the defaults); and, if `currentTemplate` is given, that it matches the template the view was built with (`template_changed`). Views must be built at publish time.
- **Published records:** the caller lists published record IDs, and the record must be among them. A place's `recordId` becomes a link only if that record is listed; otherwise only its name goes out. Public values inherited from an unpublished ancestor may be published on a published child; the ancestor's title and ID never appear.
- **Values by kind:** text as text; a date as its EDTF text; a list choice as its option label (and, for a DCMI Type code under `type` on kinds with no type of their own, also `@type` and the DCMI Type URI); a controlled term or place as its label plus URI; an identifier as its value only; a link as its URL; rights as the URI only. URIs must be http(s), canonical (`new URL(v).href === v`), and contain no `<>"{}|\^`` or space, no bad `%` escape, and `[` `]` only around an IPv6 host.
- **Rights notes are not published,** and `publicView` leaves them out: a literal under `dcterms:rights` breaks its range. This supersedes D-015's "notes are public".
- **JSON-LD:** an inline context (`dcterms`, `dcmitype`, `rdfs`); `@id` is the base URL plus the record ID; `@type` by kind (PhysicalObject; Collection for archival units above item level; Event; `dcterms:Agent`; `dcterms:Location`). Each term is written by its DCMI range: literal-range terms get text; class-range terms get `{"@id"}` with a URI, otherwise `{"rdfs:label"}`; `type` gets a label node. `jsonLdText` is written by its own writer (no `JSON.stringify`), escapes `< > &` and U+2028/2029 for script elements, and is capped as it is written.
- **Dublin Core and oai_dc:** text only; `identifier` starts with the record URL and `type` with the DCMI Type URI; oai_dc writes refinements as their parent element and leaves out `rightsHolder` and `provenance`; characters outside XML 1.0 are refused; the caller encodes it as UTF-8.
- **Limits:** each form is capped at 5,000,000 characters as produced. Output objects have null prototypes.
- **Rejected:** `edm:rights` (Europeana-specific); choosing a type from `mediaType`; IRIs under literal terms (and, until D-042, under `dcterms:type`); linking unpublished records; a "simple dcterms" XML form (no schema).

## D-017 — EDTF qualifiers: two suffixes, and "?" after a free-text range (2026-11-21, autopilot T-003a)
Checked against the LoC EDTF specification (loc.gov/standards/datetime/edtf.html, 2019-02-04).
- **Two suffix qualifiers stay refused.** The spec's level 2 examples put at most one qualifier after the parts (`2004-06~-11`, `2004?-06-11`) and use prefixes for anything finer (`?2004-06-~11`, `2004-%06-11`). `2004?-06~-11` isn't among them, so D-008's strict reading stands. Since a suffix applies to its part and every part to its left, the error message gives the same meaning in prefixes (`%2004-~06-11`). Rejected: accepting it, which would let two spellings of one meaning into stored data. Loosening later won't break stored dates.
- **"?" after a free-text range is flagged, not guessed.** In EDTF a qualifier belongs to one interval end, but in free text "1920-1925?" can doubt the end year or the whole range. A qualifier in front ("probably 1920-1925", "ca. 1920-1925") still applies to both ends. A single date that reads as an interval ("19th century?") isn't a range and isn't flagged. Rejected: `?` on both ends (the old behaviour), which guessed.

## D-019 — One install, several organizations (2026-11-21, John)
One Oculus install can hold several organizations, each with its own catalog, ID number formats, rights settings, people and roles, and its own public site or sites. The case: the Dickinson Historical Society runs its own archives (IDs like `DS5C740001`) and also hosts the library on a separate site (IDs `DPL1`, `DPL2`, `DPL3` …). This replaces PLATFORM_PLAN.md decision 3 ("one organization with several public sites … not a hosted service for many organizations"). **Complete separation (John, same day):** treat each organization as if it were a completely separate copy of Oculus. Its records, templates, record types, ID number formats, vocabularies and terms, rights settings, people, roles, change log, files and public sites belong to it alone, and no search, report, API call or public page ever reads across. Staff choose which one they are working in from a switcher in the admin; a person who works for both (say a Society admin who also runs the library's site) has one sign-in with separate roles in each, and nothing they can do in one carries over to the other. Rejected: sharing templates, vocabularies or people lists between organizations, which would tie them together. **Also (John, same day):** the site selector sits in the sidebar under the Oculus name; a site can be password protected, so staff must enter its password before opening it even when they hold a role there; and there are **System settings** for the whole install (sites, who is a system admin and which sites each person can use, sign-in and security rules, password protection, email, backups and updates), separate from each site's own Site settings. **Users (John, same day):** system admins manage every user from one Users page covering all sites (invite, set a role per site or no access, make someone a system admin, reset passwords and two-step sign-in, deactivate). After signing in, a person sees only the sites they have a role on; with exactly one site they go straight to it. Site roles stay as T-041 defines them; a system admin can manage every site. How it's modelled is T-019.

## D-020 — Public output re-checks every template up the tree (2026-11-21, autopilot security S-001)
A public view now remembers each record on the way up with the template it was read with. `publicOutput` takes `templateFor` (the same lookup `effectiveRecord` takes) and asks it again for the record and every ancestor; any template that differs, is missing or invalid gives `template_changed`, and a lookup that throws gives `template_lookup_failed`. `currentTemplate` alone is refused for a record with parents (`ancestor_templates_unchecked`), because it checks only the record's own template and a parent's field made staff since would still publish the child's inherited value.
- **Rejected:** a map of record ID → template (callers already have the lookup); checking only the ancestors a value came from (a parent's `inherited` or visibility change can matter even where no value came from it); making `templateFor` required (it would break every caller for views built and published in one step, which is the documented use).
- **Not covered here:** the ancestry itself is the one the view was built with; the `records` option (D-021) checks it against the current records.

## D-021 — Public output can re-check the ancestry against the current records (2026-11-21, autopilot security S-001a)
Extends D-020. `publicOutput` takes an optional `records` (the current set: a list or a lookup from `indexRecords`, as `effectiveRecord` takes). When given, the record's ancestry is found again in it, the same way `effectiveRecord` finds it, and output is refused (`record_changed`, path `["records", <record ID>]`, never a title or value) unless it is the same records, in the same order, with the same stored content as the view was built from, compared as validated data with sorted keys. A record removed, a parent missing or invalid, a value changed or emptied, a move to another parent or a level change all refuse. `templateFor` is then asked with the current records. A `records` that isn't a list or an index is `invalid_options`.
- **Building the view at publish time stays the rule.** Only `records` and `templateFor` together catch every change to a kept view; either alone (and `currentTemplate`) is still allowed and catches only its own kind of change.
- **Rejected:** comparing only the fields a value came from (a parent's new value, emptied value or new parent changes what the child inherits even where nothing came from it before); making kept views expire (a time limit doesn't say whether anything changed); making `records` required (it would break every caller that builds and publishes in one step).


## D-022 — Identifier types are staff only unless marked public (2026-11-21, autopilot security S-006)
An identifier type takes `public?: boolean`; left out or `false`, it is staff only. A donor file number in a public `identifier` field with no `identifierTypes` restriction used to be published as a bare value (D-016); now it can't be.
- **Refused at the template check.** The checker from `makeIdentifierChecker` reports `private_identifier_type` (at the value's `type`) for a staff type's value in any field that isn't `visibility: "staff"`, so the admin catches it when the record is saved and nothing private is published or quietly left out. Staff fields take any type. The flag is read as an own property, so a polluted `Object.prototype` can't make a type public.
- **The effective record and public view** (D-013). The identifier checker in `effectiveRecord`'s `checkers` says which types are public. Checkers judge an inherited value by its effective visibility, not the receiving field's: a staff-type number inherited as staff (staff anywhere along the way) stays in the effective record for staff. One inherited public-to-public is left out with a `not_valid_here` note, like any value that doesn't fit, not refused. A record's own value in a public field (own values aren't checked there) whose type, or any of whose types, isn't public is kept but marked `staff` with a `private_identifier_type` note. With no identifier checker from `makeIdentifierChecker`, every public identifier value is marked staff with `identifier_types_unknown` (fail closed). Either note makes `effectivePublishIssues` refuse publishing, so an own private number is never silently dropped. The public view holds an identifier as `{ value }` only, never its type (D-016 publishes only the value).
- **Checked again at the boundary.** `publicOutput` already runs the template check with the caller's checkers. It also asks the `identifier` checker for the public types it was made with (a WeakMap beside each checker `makeIdentifierChecker` made, never its shape), and refuses an identifier value whose type (read from the effective record, since the view has none) isn't among them (`private_identifier_type`). A hand-written identifier checker can't say which types are public, so with one, any identifier value refuses the output (`unchecked`). This narrows D-015's "pass `() => []` to skip a check" for identifier values in public output only.
- **Presets** don't define identifier types. Object numbers, accession numbers and call numbers, which the presets put in public fields, are usually published, so organizations should mark those types public; the tests' sample types do.
- **Rejected:** public by default (one forgotten flag publishes private numbers); leaving a record's own staff values out of output silently (a public field that drops values hides a cataloguing mistake); keeping `type` in the public view (nothing public needs it); a new `identifierTypes` option on `publicOutput` (a second copy of the types that could disagree with the checker's); per-field allow lists alone (`identifierTypes` on the field is optional, so the gap stays open by default). Unifying `RecordIdentifiers` and identifier fields is still T-014.


## D-023 — Template changes are compared before saving; making a field public needs confirmation (2026-11-21, autopilot security S-002, T-005a)
`templateChanges(oldTemplate, newTemplate, records?)` (template-changes.ts) validates both versions of one template (same `key`, else `different_template`) and every record given, and returns a frozen `{ changes, needsConfirmation, recordsChecked }`. Each change has a `code`, the field `key`, `needsConfirmation`, a message, and the IDs of the records holding a value for that key (`recordIds`, at most 10,000 listed, with the full `recordCount`). The codes:
- `made_public`: staff → public, or a new public field whose key records still hold left-over values for (left-overs are staff, D-013). **Always needs confirmation; the caller must get a person's confirmation before saving a template with a `made_public` change** (T-047 shows it).
- **Without records, every new field is reported:** a new public field as `made_public` and every new field as `key_reused`, both needing confirmation, since its key may hold left-overs nobody can see.
- `kind_added`: `appliesTo` gains a record kind. It is reported whatever the count, because the caller's records usually can't include that kind yet (they used another template); `recordIds` lists any given. Records of that kind may hold values, including staff ones from their old template, under keys this template publishes, so it needs confirmation whenever the template has a public field.
- `key_reused`: a new field takes a key records hold left-over values for. `key_removed`: the values stay as left-overs; removing an inherited field always needs confirmation. `kind_changed`; `repeatable_changed` (true → false also lists `recordsWithSeveralValues`); `option_removed` (with `option`); `max_length_lowered`, `vocabulary_removed` and `identifier_type_removed` (with `removedCodes`; a term with no vocabulary counts as `local`), listing the records holding a value the new field refuses; `made_required`, listing the records without a value. These need confirmation when records are affected, or when no records were given.
- `record_kind_removed` (T-015a, see D-055): a `record_link` field's `recordKinds` narrows (`removedCodes` names the kinds dropped). With `options.linkChecker` (the organization's `makeRecordLinkChecker`), `recordIds` are the records linking to a kind no longer allowed; without it, every record holding a link under the key. Another organization's checker or any other function refuses the comparison.
- `inherited_changed` needs confirmation when a field starts being inherited; stopping is informational, as is `made_staff`.
- **Descendants on other templates are not in `recordIds`.** Making a field inherited or removing an inherited field changes what lower levels receive, and can lift the strictest-visibility-along-the-way restriction of D-013 for descendants using other templates; this function sees only the records given, so those changes always need confirmation instead.
- **Left-over keys are found only through the records**, so a caller saving a template must pass the records that use it; without them `recordsChecked` is false. **An empty list means "these are all the records" (there are none)**: a caller must pass nothing, never `[]`, when it doesn't know them.
- **Messages name keys and counts only**, never a stored value. Any invalid record, duplicate ID, Proxy or getter refuses the whole comparison: an unreadable record could hide a staff value. Work is linear in records × changed keys.
- **Rejected:** refusing key reuse outright (an admin may legitimately bring a field back; reporting it with the records is enough, and refusing would need a history of removed keys the template doesn't keep); confirming `made_public` only when records hold values (records not given, or added before the save, would slip through).
- **Not covered:** identifier type edits (T-005a's second part) and aligning `identifierTypes` codes with identifier type keys stay open; renaming a key is seen as `key_removed` plus a new field. A record moving to another template through the caller's `templateFor` lookup (records don't name their template yet, T-012) can turn its staff values public without any template change; this function doesn't see that.


## D-024 — Identifier keys split accents before mapping lookalikes; blank characters (2026-11-21, autopilot security S-003)
`identifierKey` (D-009) now removes spaces, invisible and blank characters first (so none can sit between a letter and its accent), applies NFKC then NFD, maps lookalike *base* letters, folds case and recomposes with NFKC. Precomposed Cyrillic and Greek letters such as `Ӧ`, `Ӓ`, `Ӑ`, `Ά`, `έ`, `ό` (which NFKC keeps whole) now meet their Latin twins `Ö`, `Ä`, `Ă`, `Á`, `é`, `ó`; the Greek tonos and the Latin acute are one mark after NFD. The mark is kept, so `Ӧ` meets `Ö` but not `O`, and `Č` and `C` stay different as before. Visible characters that draw nothing (U+2800 Braille blank, U+16FE4, U+1D159; `BLANK_CHARACTERS`) are dropped from the key like spaces, and refused in identifier values, prefixes and formats (`invisible_characters` / `bad_characters`) like invisible characters. The Hangul fillers were already both, being default-ignorable. The table also gains lookalikes with no Latin decomposition (`Ү`, `Ӕ`, `Ә`, `Ө`, `Ѵ`, `Ҫ`, `Ϳ` and their small forms); the Greek perispomeni (`ᾶ`) maps to a tilde, since most fonts draw it as one; the Ogham space mark, a space to `\s` but drawn as a dash, becomes `-`.
- **Cost:** normalization sorts each run of combining marks in quadratic time. The key first removes spaces and invisibles and decomposes (NFKD one character at a time, which needs no sorting; whole-text NFKD is unsafe because non-marks such as `ﾞ` decompose into marks), then measures runs of marks. Text with a run of more than 8 marks (`MAX_MARK_RUN`) gets a key with its marks sorted by code point instead of normalized, behind a U+FEFF marker. The path depends only on the decomposed runs, so canonically equivalent spellings (`Ö`+marks, `O`+diaeresis+marks, reordered marks) always take the same path and meet; the key is linear at any length. Identifier values, auto-number prefixes and formats with such a run are refused (`too_many_marks`; `bad_characters` for formats), so only queries and old data take that path.
- **Rejected:** listing every precomposed lookalike in the table (hundreds of entries, easy to miss one); treating blanks only as spaces (a value made of nothing but Braille blanks would pass the empty check) or only refusing them (values imported before the check still need to clash); a new issue code (the existing one says the same thing to the person); deciding the path on the raw text or its length (a second review showed equivalent spellings could then get different keys); a higher mark limit (no identifier needs more than two or three marks on a letter).
- **Stored format:** no comparison keys are stored yet. Once T-026 stores each value's `identifierKey` beside it, any change to the key is a migration: recompute every stored key and re-run the uniqueness check, because values that were different can become the same and the unique index would refuse them.

## D-025 — System managers and site managers (2026-11-21, John)
Two levels of management, refining D-019's system admins and site roles:
- **System managers** can do everything, across the whole install. They sign in, create and set up the sites, install plugins and themes, manage every user and which sites each person can use, and run System settings.
- **Site managers** manage only the sites assigned to them, one or more. On those sites they have full control (content, catalog, Design, Site settings and the site's people and roles), and they choose among the plugins and themes a system manager has installed. They can't install anything, create sites, or see or change sites they aren't assigned to.
- **Site managers can change anything on their sites (John, same day):** every part of the site's design, including the installed theme they picked (colours, fonts, layouts, headers, footers, templates). Theme updates must not overwrite a site's own changes, so a site's changes are stored separately from the theme.

- **Plugins** are new to the plan. What a plugin may do and how it is checked before install (it runs code on the server) is undecided and gets its own decision task before any plugin system is built (P-001).

## D-026 — Show or hide each field on a site's record pages (2026-11-21, John)

## D-027 — The check before publishing: serious problems block, minor ones warn (2026-11-21, John)

## D-029 — Records name their template; no version pin; a template registry (2026-11-21, autopilot T-012)
A record stores `templateKey?: string`, the key of the template it follows, checked with the same rule as a template's `key` (`isTemplateKey`: 1 to 64 of `a-z 0-9 _ -`, starting with a letter, never `constructor`, `prototype` or `__proto__`; `invalid_template_key`). The checks find the template from the record, and **a record is never checked against a template with another key**: `checkRecordAgainstTemplate`, `effectiveRecord` and `publicOutput` refuse it (`template_mismatch`, naming keys only). This closes the S-002 review's leak, where a lookup that put a record under another template (a bug, a stale cache, a record "moved" without anything in it saying so) had its staff values checked and published under a key the other template makes public.
- **A template registry.** `indexTemplates(list)` validates an organization's templates once and indexes them by their own `key` into a frozen, opaque `TemplateRegistry` (recognised by a WeakMap, never by shape), for `checkRecordAgainstTemplate` (in place of the template), `effectiveRecord` and `publicOutput`'s `templateFor`. It is a snapshot like `indexRecords`: rebuild it after a template edit. Any invalid template, a hole, getter or Proxy, or two templates with one key refuses the whole list (`duplicate_key`); at most `MAX_REGISTRY_TEMPLATES` (1,000). Through a registry, a record with no key is `no_template_key` and a key it doesn't hold is `unknown_template`. *Rejected:* a `templatesByKey` object map (its keys could disagree with the templates' own `key`, and an object invites prototype keys); caching by object identity (D-013's reason still holds; the registry holds its own validated copies).
- **The lookup function still works** (`TemplateLookup`; `TemplateSource` is either). Its answer must have the record's `templateKey`, when the record has one, so the function can no longer choose a template for a keyed record, only fail to find it. A Proxy function is now refused by `effectiveRecord` too (`no_template_lookup`), as `publicOutput` already did.
- **"No key" means no own `templateKey` property at all.** An own property that is undefined, a getter or not a valid key is refused (`invalid_template_key`), never read as a keyless record, and `checkRecordAgainstTemplate` now validates the record first (`invalid_record`), so a hand-made record can't pass as an old one.
- **`templateChanges` checks the records belong to the template:** a record naming another template refuses the whole comparison (`record_not_for_template`), so it is never listed in this template's confirmation; keyless records are allowed and counted in `legacyRecords`, since nothing confirms which template they use.
- **Records without a key** (stored before this) still validate, and can be checked only through a template given directly or a lookup function, as before; a registry refuses them. They keep the old risk, so T-025 stores `template_key` as NOT NULL with a foreign key to the templates table and a migration fills it; once no keyless records remain, the function lookup and the optional key can go. `createRecord` takes `templateKey`; it is optional in the type only so existing callers keep working. *Rejected:* refusing keyless records outright (every stored record and caller would break at once, before the database exists to migrate them).
- **No version pin.** A record names a template key, not a version: every record follows the current version of its template. Reasons: making a field staff (often the fix for a leak) must apply to every record at once, not wait for each pinned record to be moved; public output re-checks the current templates (D-020, D-021), which a pin would turn into re-checking an old version nobody edits; and D-023 already makes every change that could publish something confirmed against the records that use the template, which a record's key now names exactly. The database (T-025) keeps template versions for the change log and for restoring, not for records to follow. *Rejected:* pinning `templateVersion` on each record (two records of one template could publish one key differently, and old versions would have to stay live and checkable forever).
- **Moving a record to another template is a record edit:** its stored `templateKey` changes, so a kept public view of it is refused by `publicOutput`'s `records` option (`record_changed`, D-021). Comparing the two templates for such a move (what becomes public, which values become left-overs), as `templateChanges` does for a template edit, is not done yet.

## D-030 — Organizations in the core model: an `organizationId` on everything, and mixed sets are refused (2026-11-21, autopilot T-019)
How D-019's complete separation is modelled in `packages/core`, before there is a database.
- **Organizations and sites.** `organizations.ts` adds `Organization` (`id`, `name`) and `Site` (`id`, `organizationId`, `name`), with `validateOrganization` and `validateSite(site, organizations)`; a site must belong to one of the install's organizations (`unknown_organization`). Both IDs are random version 4 UUIDs, branded `OrganizationId` and `SiteId` so code can't pass one for the other or for a `RecordId`, and never change; names can (one line, trimmed, at most 200 characters). Site passwords (D-019) are not modelled yet: how they are stored and rate-limited needs the security review.
- **Everything an organization owns carries a required `organizationId`** in its stored value, as each database row will carry an `organization_id` column (T-025 onward). Done in this run: catalog records (`validateRecord` refuses a record without one, `invalid_organization`; `createRecord` takes it), identifier types and a record's identifiers (`RecordIdentifiers`). Templates and record types, vocabularies and terms, and rights settings follow the same rule in follow-up tasks (T-019a, T-019b). Presets stay organization-free: they are starting points that an organization copies into its own template. An `organizationId` never changes; moving a record between organizations is a copy, not an edit.
- **A set that mixes organizations is refused, never filtered.** An entry whose `organizationId` is missing, not an organization ID or behind a getter counts as another organization's, at any position (an organization-less set could be any organization's). `templateChanges`'s `records`, `validateArrangement` and `unfiledUnits` refuse mixed sets too, and so do `findByIdentifier` and `findIdentifierConflicts`; those two and `unfiledUnits` now return a `Validated` list instead of a bare array, since an empty list would look like "nothing found" (the least breaking shape that can refuse: callers read `.value` when `.ok`). `indexRecords` counts every entry's readable `organizationId`, valid record or not. `indexRecords` and `effectiveRecord` (and so `publicOutput`'s `records` option) refuse a set holding records of more than one organization; `uniquenessIssues`, `checkNewIdentifier`, `nextIdentifier` and `validateRecordIdentifiers` refuse record identifiers and types of more than one organization; `validateIdentifierTypes` refuses one list holding two organizations' types. All with the code `mixed_organizations`, and none of them quote the other organization's values. So an item can't inherit from another organization's fonds, a number is unique only within its own organization (the Society's archives and the library can both hold `DPL1`, D-019), the check for a free number never reveals what another organization holds, and auto-numbering never counts another organization's numbers.
- **Checked inputs are copied once.** The identifier set functions copy their `RecordIdentifiers` list into a plain, frozen snapshot (Proxies and getters refused, `not_a_list` / `invalid_identifiers`) and validate the types before the organization check, then work on the snapshot only, so a list that reads differently the second time can't pass the check with one set and be searched with another. `indexRecords` refuses an entry whose `organizationId` is missing, invalid or behind a getter rather than keeping it as "invalid".
- **Every caller's list is read once.** `validateArrangement` and `unfiledUnits` read their units into frozen shallow copies first (Proxies, non-arrays and getters refused: `not_a_list`, `unreadable_entry`), and `validateRecordIdentifiers` validates its types once with `validateIdentifierTypes` and uses that copy for both the organization check and the format checks. No function checks one read of a caller's list and works on another.
- **Identifier checkers belong to an organization.** `makeIdentifierChecker` remembers the organization of its (single-organization) types. Its checker refuses every value of a record of another organization (`wrong_organization_checker`); `effectiveRecord` keeps such public identifier values staff with that note, which blocks publishing; `publicOutput` refuses a checker of another organization outright. Otherwise one organization's `public` type could publish another's staff number with the same key.
- **Templates (T-019a).** `FieldTemplate` has a required `organizationId`, checked by `validateTemplate` and `validateLegacyTemplate` (`invalid_organization`; a stored template without one is no longer readable, which is safe while nothing is stored). `templateOfRecord`, which the record check, `effectiveRecord` (lookup function or registry, for the record and every ancestor) and `publicOutput` all go through, refuses a template of another organization than the record's (`wrong_organization`, naming only the template key). `indexTemplates` and `legacyTemplateIssues` refuse a list naming two organizations; `templateChanges` refuses two organizations' templates and records of another organization; `identifierTypeChanges` and `identifierTypeDeletion` refuse another organization's templates. `publicOutput`'s `currentTemplate` is compared with the view's template including `organizationId`, so another organization's copy gives `template_changed`. Presets are now `TemplatePreset` (a template without `organizationId`, a breaking type change) and no longer pass `validateTemplate`; `templateFromPreset(preset, organizationId)` makes an organization's validated copy and refuses anything that already names an organization, as a guard against mistakes rather than a security boundary. Dublin Core mapping checks read a template's fields only (`validateTemplateShape`, internal), so a mapping can still be checked against a preset; mappings themselves carry no organization yet (T-019b). Record types follow when T-013 adds them.
- **Where the session's organization comes in.** A session works in exactly one organization (D-019). The service layer (T-032) loads only that organization's rows and checks the result's `organizationId` against the session; roles (D-025, T-041) will be granted per organization and per site, keyed by `(personId, organizationId)` and `(personId, siteId)`, with system managers outside any one organization. The checks here are the second line, so a query that forgets its organization filter fails loudly instead of reading across.
- **Events (D-028)** will attach as records of their organization like any other. Importing one from another site makes a new event owned by the importing organization, with a note of the site it came from; the import reads only a published event and copies it, so no set ever holds both organizations' records and nothing here needs an exception.
- **Rejected:** an organization-scoped container or registry passed to every function instead of a field on the data (the data itself couldn't show it was loaded from the wrong organization, and the container is a second source of truth that can disagree with the rows); an optional `organizationId` (a missing one would silently match any organization); putting the organization in the record ID (record IDs are permanent random UUIDs, `record-id.ts`, and an organization's records would be guessable by prefix); silently leaving out records of another organization (a filtered result looks complete when it isn't and hides the bug that mixed the set); a per-call `organizationId` argument checked against the data (the same check the service makes against the session, done twice with two values that could disagree).
## D-031 — Identifier type changes are checked before saving; one key rule for identifier types (2026-11-21, autopilot T-005a)
`identifierTypeChanges(oldType, newType, existing?)` and `identifierTypeDeletion(type, existing?)` (identifier-type-changes.ts) are the identifier type half of D-023. They return the same frozen `{ changes, needsConfirmation, recordsChecked }`; each change has a `code`, the old type key, `needsConfirmation`, a message naming the key and counts only, and `recordIds` (at most `MAX_LISTED_RECORDS`, with the full `recordCount`). The codes:
- `key_changed` and `type_deleted`: every stored value keeps the old key, so current ones stop passing the check and former ones stop counting for uniqueness and auto-numbering (their numbers could be given out again). `recordIds` are the records holding any value of the type: current, former, or in a template `identifier` field. A new key another type already has is refused (`key_taken`).
- `key_adopts_values`: a rename onto a key, or a new type (`identifierTypeCreation`), takes over values already stored under that key from a deleted type, which were staff. It lists those records, with `misfitRecordIds` (off the type's format) and `clashRecordIds` (clashing under its uniqueness rule, counting the renamed type's own values), and always needs confirmation; a public type also reports them as `made_public`. Without this, renaming a public type onto a deleted staff type's key would publish its left-over values silently.
- `templates_reference_type`: on a rename or deletion, the templates in `existing.templates` whose `identifierTypes` name the old key (`templateKeys`); needs confirmation.
- `made_public` (D-022): **always needs confirmation**, like a field made public; `recordIds` are the records holding a value. `made_staff`: a staff type is refused in public fields, so it lists the records holding a value in an `identifier` field that is public for their kind in some template in `existing.templates` (any field when templates aren't given, since records don't name their template yet, T-012), and needs confirmation when there are any.
- `reserved_key`: a stored type keyed `constructor` or `prototype` (valid before this decision) edited without a rename; needs confirmation. Renaming onto a reserved key is refused.
- `format_changed`: a format added or changed; the records whose current values (identifiers and field values) no longer fit. Former values are history and never checked (D-009). A format removed is not reported.
- `uniqueness_tightened`: the records whose values clash under the new rule, compared with `identifierKey`, former values counting under `all_time`. Field values aren't in the uniqueness check (D-009), so they aren't counted. `uniqueness_loosened` is informational.
- `auto_number_changed`: added or changed numbering needs confirmation when a record holds a number it would give out again: a value not of exactly the new form that reads as the type's whole prefix (or a four-digit year) then a sequence number once separators are ignored (`DHS-0009` after the prefix becomes `DHS`, `M1 0009` under prefix `M1-`, `2026015` under year numbering), above the highest number of the new form. Only values made of the head, separators and a single run of digits count (`DHS-2026-0015` isn't a `DHS-` number), and with no separator after the head the run must be at least as wide as the numbering's padding (`123456` isn't year 1234). Its key differs, so the uniqueness check can't catch it. The scan uses the numbers the type owns after the change: after a rename, `nextIdentifier` counts the new key's values (adopted left-overs), so every old-key value is a candidate; `identifierTypeCreation` with numbering runs the same scan over the adopted values. Numbers held only in template `identifier` fields count too, even of exactly the new form, because `nextIdentifier` reads only `RecordIdentifiers`. Padding changes and a new prefix (a new series) aren't reported as reissues. Removing numbering is informational.
- **`existing` is `{ identifierTypes, identifiers, records, templates? }`, the first three required:** the organization's current types (which must contain `oldType` exactly, else `type_not_listed`, so a caller can't claim the type was already public), every record's identifiers and every catalog record. Without it, `recordsChecked` is false and every change that could affect records needs confirmation; the old type can't be checked either, so a public new type always reports `made_public` (it may have been staff). As in D-023, an empty list means "none"; a missing one is refused.
- **Stored identifier sets are read leniently** (`readStoredIdentifiers`, internal): every shape and safety rule applies, but a current value of a removed type or one that doesn't fit its format is already stranded, so it is counted, not refused; otherwise the first deletion would block every later check. Templates are read with `validateLegacyTemplate`.
- **One organization (D-030):** both types, every listed type, identifier set and record must name the same valid `organizationId`, else `mixed_organizations`; a stored set without one is refused (`invalid_entry`). Templates carry one too since T-019a, and the templates listed must be the type's organization's.
- **Refuses on any doubt:** every type, identifier set, template and record is validated, and one malformed entry, a duplicate record ID, a Proxy or a getter refuses the whole check (an unreadable entry could hide a value). Types are read through own properties only, so a polluted `Object.prototype` can't hide `made_public`. Work is linear in the values, each matched against the new format at most once, about the cost of validating them.
- **One key rule for identifier types.** Identifier type keys never allowed hyphens, but template `identifierTypes` codes and the `type` of identifier values did, so a template could name a type that could never exist. Both now use `isIdentifierTypeKey` (identifiers.ts): 1 to 64 lower case letters, digits and underscores, starting with a letter, and not `constructor` or `prototype`. Other template codes (template keys, standards, vocabularies) still take hyphens.
- **Stored data keeps working.** `validateIdentifierType(s)` still accept stored types keyed `constructor` or `prototype` (so `makeIdentifierChecker` keeps working); `validateNewIdentifierType` refuses them for new types, and edits report `reserved_key`. A template stored with hyphenated `identifierTypes` codes is read by `validateLegacyTemplate`, which `templateChanges` uses for the old side, so it can be fixed (`call-number` → `call_number` is reported as `identifier_type_removed` with the records); `validateTemplate`, used for new and edited templates and by every other reader, refuses it, so such a template fails closed until re-saved. `legacyTemplateIssues(templates)` lists the stored templates `validateTemplate` refuses (`fixable` when only the identifier type codes are at fault, with those codes), so an upgrade can have them re-saved before records using them stop being checked and published.
- **Rejected:** allowing hyphens in type keys instead (type keys follow the record field key rule, and no preset or test used a hyphenated type, so narrowing the template side broke nothing real: one test fixture was renamed); allowing `constructor` for new type keys (templates already refused it in `identifierTypes`, so one rule had to pick; refusing is the safer, and stored ones are migrated by rename rather than broken); simulating `nextIdentifier` for every year to find reissues (the loose comparison finds the same numbers without needing the caller's year); treating a renamed key as delete plus add (a rename is visible here, unlike for template fields).
- **Not covered:** templates naming a deleted or renamed type are only reported (`templates_reference_type`, when `existing.templates` is given), not changed; the caller updates them through `templateChanges`. Values in `RecordIdentifiers` and template `identifier` fields are still two stores until T-014, and `nextIdentifier` still counts only `RecordIdentifiers` (follow-up).

## D-036 — Scanner and Donor relations roles, and custom roles made by system managers (2026-11-22, John)
John's answer to Q-4: add both roles, and let system managers create custom roles too.
- **Roles are made of permissions.** The code defines a fixed list of permissions (for example: view staff records, edit descriptions, upload and attach scans, publish and unpublish, see and edit donor and accession records, manage a site's people). A role is a named set of them. The service layer checks permissions, never role names, so built-in and custom roles are checked the same way.
- **Built-in roles** below the site manager: cataloger, reviewer, read-only, and the two new ones:
  - **Scanner:** uploads scans and other files and attaches them to existing records; can see the records it attaches to; can't edit descriptions, publish, or see donor or accession records.
  - **Donor relations:** sees and edits donors, accessions and deeds of gift (always staff-only data, T-016); can see the records an accession produced; can't edit descriptions or publish.
- **Custom roles.** System managers can create, rename, edit and delete roles built from the same permission list, for any organization. Each custom role belongs to one organization (D-019, D-030) and is granted per site or for chosen fonds or collections, like a built-in role. A custom role can never include system-manager powers (installing plugins and themes, creating sites, System settings, managing users across the install); those stay with system managers only. Built-in roles can't be deleted, so there is always a working set.
- **Safe changes.** Editing or deleting a role that people hold shows who is affected first; deleting one in use needs those people moved to another role. Adding a sensitive permission to a role (publish, donor data, manage people) needs confirmation, like making a template field public (D-023). Every role change goes in the change log.
- **Rejected:** fixed roles only (John asked for custom roles); letting site managers create roles (not asked; they assign the roles that exist); roles checked by name in code (a renamed or custom role would then be checked wrongly).

## D-037 — Record types are an organization's own types built on the six kinds; the record's templateKey still decides its template (2026-11-23, autopilot T-013)
PLATFORM_PLAN.md §1 says admins can add more record types. The six record kinds (D-007) stay a fixed list; what an organization adds is a **record type** built on one of them ("Oral history" is a kind of `digital_asset`, "Photograph" of `object`, "Scrapbook" of `archival_unit`). `record-types.ts` adds `RecordType` `{ key, organizationId, label, description?, kind, defaultTemplateKey }`; keys follow the template key rule, the label is one trimmed line of at most 200 characters, the description at most 2,000.
- **Validation.** `validateRecordType(input, templates)` takes the organization's template registry or the one template the type names: the template must exist (`unknown_template`, `template_mismatch`), belong to the type's organization (`wrong_organization`, checked before the key lookup so nothing about another organization's keys shows) and apply to the type's kind (`template_wrong_kind`). Getters, Proxies, prototype keys and unknown properties are refused; the result is a frozen copy.
- **A registry.** `indexRecordTypes(types, templateRegistry)` validates an organization's types once into an opaque, frozen `RecordTypeRegistry` (at most 1,000), refusing the whole list for any invalid type, duplicate key, hole, getter, Proxy, mixed organizations or another organization's templates. `recordTypeTemplateIssues(types, templateRegistry)` reports per type what would be refused (a default template deleted, renamed or no longer applying to the kind), so an admin screen can show which types to fix; run with the registry as it would be after a template edit, it shows what the edit breaks.
- **A record names its type** in an optional `recordTypeKey`, and then must also name a `templateKey` (`template_key_required`). `recordTypeDefaults(registry, key, organizationId)` gives `{ kind, recordTypeKey, templateKey }` for a new record, refusing another organization's registry; it returns no `organizationId`, so spreading it into `createRecord` can't move the record to another organization (found in review). `checkRecordType(record, registry | type)` checks that the type exists in the record's organization and has the record's kind (`no_record_type`, `unknown_record_type`, `record_type_mismatch`, `wrong_organization`, `wrong_kind`); messages name keys only.
- **The type's template is a default, not a rule.** The record's own `templateKey` stays the one source of its template (D-029); checking and publishing never take a template from the type, so editing a type never changes what a record publishes. The type itself isn't published yet.
- **Rejected:** new organization-defined kinds (the arrangement tree, media types, agent types, place positions and Dublin Core classes all depend on the six); requiring `templateKey` to equal the type's default (two sources of truth); allowed-template lists per type (a template's `appliesTo` already limits kinds); an optional `organizationId` (D-030); `recordTypeDefaults` returning the type's organization.
- **Not covered yet:** edits and deletions of a record type aren't checked against the records using it (T-013a).

## D-038 — One home for numbers: `RecordIdentifiers`; identifier fields only point at a current identifier (2026-11-23, autopilot T-014)
A record's numbers live only in its `RecordIdentifiers` (D-009): current ones with exactly one primary, and former ones, where uniqueness, auto-numbering, retiring and search already work. A template field of kind `identifier` stores no number of its own: its `{ type, value }` names one of the record's current identifiers exactly (same type key, same value character for character; no `identifierKey` or lookalike matching).
- **Saving.** `identifierFieldIssues(record, template, identifiers)` (identifier-fields.ts) is the save-path check beside `checkRecordAgainstTemplate`: `identifier_not_held` for a field value that isn't a current identifier (naming the field, never the number), `wrong_record`, `mixed_organizations` / `wrong_organization`. Its caller is the service layer (T-032); nothing in core calls it yet.
- **Effective record.** `effectiveRecord` takes `options.identifiers`, the sets for the record and its ancestors, read once and frozen; another organization's set or one naming none gives `mixed_organizations`, a record listed twice `duplicate_identifiers`, a malformed set or one without exactly one primary or with a current number twice `invalid_identifiers` (a number both current and former is allowed: a reinstated number). A public identifier value its source record (the record itself, or the ancestor it is inherited from) doesn't hold as current is kept staff with `identifier_not_held`; without the option every public identifier value is staff with `identifiers_unknown`. Both block publishing.
- **Boundary.** `publicOutput` requires `identifiers` (the sets as they are now) whenever the view holds an identifier value (`identifiers_unknown`), and each number must still be a current identifier of the record it came from (`identifier_changed`), so a kept view can't publish a number retired, moved or re-typed since (found in review). Sets must already have passed `validateRecordIdentifiers` and `uniquenessIssues` on the save path; a value of a type that isn't one of the organization's public types is refused anyway by the identifier checker.
- **Public types** stay as D-022: the primary number, like any other, reaches public output only through a public `identifier` field and only when its type is public. A staff-type primary relabelled in the field as a public type is caught because the pair isn't held.
- **Rejected:** fields as the home (former numbers, the primary mark, uniqueness and auto-numbering don't fit field values); projecting fields from `RecordIdentifiers` with no stored value (which number goes in which field would be a guess); matching by `identifierKey`; silently dropping values that aren't held; `identifiers` optional on `publicOutput`; re-running format and uniqueness checks at publish time.
- **Consequence:** field values are a subset of current identifiers, so `nextIdentifier` counting only `RecordIdentifiers` is correct for valid data (D-031's open note).

## D-039 — Links between records: a `record_link` kind, a record link checker, and links named only when safe (2026-11-23, autopilot T-015)
A record links to another record of its own organization through a new field kind, `record_link`, value `{ recordId, label }` (both required). A field may limit what it links to with `recordKinds` (1 to 6 distinct kinds; refused on other field kinds, `not_for_kind`). A creator from the Authorities list is `record_link` with `recordKinds: ["agent"]`; related records are a repeatable `record_link`. `label` is this record's own text for the link, published only with the link itself (**amended by D-045**: when the linked record may not be named, nothing of the link is published, not even the label). A place's existing `recordId` is the same kind of link, to a place record.
- **The checker.** `makeRecordLinkChecker(records)` (a list or an `indexRecords` lookup; mixed organizations refused) is passed as both `checkers.record_link` and `checkers.place`. It refuses another organization's record (`wrong_organization_checker`), an ID not in the set (`unknown_record`), an unusable record, a kind the field doesn't allow (`wrong_record_kind`) and a self link (`self_link`); its messages never quote the linked record. It snapshots each record's ID, kind and organization only, so it is made again after records change. Without it `record_link` values are refused (`unchecked`); a place's `recordId` is still accepted but never linked publicly.
- **The public view holds no linked IDs.** `publicView` holds a place as `{ label, uri? }` and removes `recordId` from values of every kind; it holds no `record_link` value at all (D-045; before, `{ label }`). An own public value that doesn't fit its field as the template has it now (a link, identifier or rights value left in a field since made text) is held back as staff with a `does_not_fit_field` note that blocks publishing (found in review).
- **Public output (supersedes D-016's place rule).** A link goes out as `baseUrl` + ID, labelled, only when the linked record is in `published`, the checker given for that kind was made by `makeRecordLinkChecker` from this record's organization's records and holds it, its kind is allowed and it isn't the record itself; otherwise nothing of a `record_link` goes out (D-045; before, its label), and a place goes out as its name (and gazetteer URI) without the link, when its place record is vouched for (D-048). The linked record's title and values are never read. Another organization's checker is refused outright. In JSON-LD a link under a class-range term is `{"@id","rdfs:label"}`; Dublin Core and oai_dc get the label. Links inherit like any other value (D-013); an inherited link no checker checked is left out with a note.
- **Breaking, on purpose:** callers that pass only `published`, with no record link checker, now get place names without a link: the published list carries no organization, so trusting it alone could link another organization's place (D-030).
- **Rejected:** separate `agent`/`event` kinds or extending `place`; a link with an optional `recordId`; publishing the linked record's current title; trusting `published` alone; a separate `publicOutput` option for link targets; IDs or misfit values in the public view.

## D-040 — Storage locations and moves: one move log is the truth, staff-only, per organization (2026-11-23, autopilot T-017)
Spectrum "Location and movement control" in `storage.ts`.
- **Storage levels** are named by the organization top down (`StorageLevels { organizationId, levels }`: 1 to 8 one-line names, no two alike ignoring case); the default is Room › Shelf › Box › Folder (mockup Settings).
- **Locations** (`StorageLocation`): a random v4 UUID, `organizationId`, `kind` (`storage`, `display`, `external`), `name`, `level` (storage and display only), optional `parentId`, `container`, `agentId` (external only) and `note`. A location sits in one at a strictly higher level (levels may be skipped, so loops are impossible); outside locations (conservator, vendor, borrower) have no level or parent. Sibling names are unique ignoring case and can't contain "›". A container moves by editing its `parentId`, and its contents follow.
- **Moves** (`StorageMove`): `recordId`, `locationId`, `movedOn` (an EDTF day, D-008), `reason` (`placement`, `rehousing`, `return`, `correction`, `exhibition`, `loan_out`, `conservation`, `digitization`, `photography`, `research`, `other`, and `departure`, added by D-044), optional `expectedReturnOn` (temporary reasons only, not before the move) and `note`, and `recordedAt`. `placement` and `rehousing` set the normal location; a `return` must go to the normal location in force then.
- **The move log is the only truth.** Current and normal location, history, the away and overdue lists and box contents are worked out from the moves, never stored separately, so they can't disagree (Spectrum: one location entry per object). Moves order by `movedOn`, `recordedAt`, ID. An expected return date stays outstanding until a `return`; while it is outstanding, a later dated move replaces it only as an extension (the same reason, to the same location as the move that gave it), and any other dated move keeps the earlier date. While a date is outstanding the record is away, even at its normal location, and stays on `overdueReturns`, so a record out on loan can't be taken off the overdue list on paper (amended by D-044). A record never placed that is out with a date comes back by a placement followed by a return there.
- **Snapshots** as in D-029: `indexLocations` and `indexMoves` validate whole lists once into opaque frozen snapshots; the queries (`whereabouts`, `moveHistory`, `awayFromNormal`, `overdueReturns`, `locationContents`, `locationPath`) read only those. `withMove` checks one new move in its place in the history and refuses a `recordedAt` in the future; `reindexLocations` checks any level or location edit against the whole history; `checkLocationDeletion` refuses deleting a location with contents or history. Caller lists are read once (Proxies, getters, holes and prototype keys refused).
- **Organizations (D-030)** are required on levels, locations and moves; mixed sets are refused. A move's `recordId` and a location's `agentId` are only checked as IDs here; the service layer (T-032) checks they belong to the session's organization.
- **Staff-only.** Storage data is never a record field; nothing in `effective.ts` or `public-output.ts` reads it, and a test checks no module but `index.ts` imports it.
- **Rejected:** stored current or normal location on records (a second truth); free-text paths; planned future moves in the log; fixed level names.
- **Not done yet:** a container's own moves in its records' histories; who moved or authorised a move (logins, Phase 2); concurrent saves (T-032).
- Source: Spectrum 5.0 "Location and movement control" as reproduced by a museum (pitstonemuseum.co.uk); Collections Trust's own 5.1 page couldn't be reached.

Narrows D-022. An identifier value inherited into a public field whose only problem is `private_identifier_type` is checked again as a staff field and, if it passes, kept in the child's effective record as `staff` with an `inherited_staff_identifier` note. Before, the whole value was dropped from the child, staff side too, and a repeatable list lost its public numbers with it. Nothing of it reaches `publicView` or public output, and publishing the child isn't refused: the mistake is on the record that holds the number, where D-022 already blocks publishing. ## D-042 — dcterms:type has no range; jsonld as a test-only dependency (2026-11-23, autopilot T-009a/T-010a)
DCMI Metadata Terms (2020-01-20) declares no range for `dcterms:type`, so JSON-LD now writes it like `subject` and `relation`: an `@id` node (with `rdfs:label` for terms) when the value has a validated URI, otherwise plain text. ## D-043 — Accessions and deeds of gift: a staff-only register per organization, and a deed check only as fresh as that register (2026-11-23, autopilot T-016)
Spectrum "Acquisition and accessioning" in `accessions.ts`.
- **Accession:** a random v4 UUID, `organizationId`, `number` `{ type, value }` of one of the organization's staff identifier types (D-009; a public type is refused, `public_type`), `sourceAgent` and the produced `records` as record links (D-039), `receivedOn` (an EDTF day), `method` (`gift`, `purchase`, `bequest`, `transfer`, `field_collection`, `found_in_collection`, `other`), `materials`, optional `restrictions` and `note`, `deedStatus` (`missing`, `sent`, `signed`, `not_needed`) and optional `deedSignedOn`. A gift can't be `not_needed`: Spectrum asks for the donor's signed offer as evidence of transfer of title. **Donor contact:** `{ agentId, organizationId, email?, phone?, address?, note? }`, one per agent.
- **Register.** `indexAccessions(organizationId, { accessions, contacts?, records, identifierTypes })` validates everything once into an opaque, frozen register. Numbers are unique and fit their type; `nextAccessionNumber` counts through `nextIdentifier`. Links are checked with `makeRecordLinkChecker` from the register's own copy of the records (the source must be an agent; produced records objects, archival units or digital assets). Queries: `accessionById`, `accessionsByNumber`, `accessionsOfRecord`, `accessionsAwaitingDeeds` (mockup Deeds), `deedHoldsOn`, `recordsHeldBack`, `donorContact`. Nothing here checks roles: the Donor relations permission (D-036) is enforced by the service layer (T-032, T-041).
- **Organizations (D-030).** The register takes its organization as an argument, so even an empty one says whose it is; anything of another organization refuses the whole input, naming nothing of it.
- **Held back:** the records an accession with a `missing` or `sent` deed produced, the units filed below them, and the digital assets that represent any of those.
- **The check.** `effectivePublishIssues(effective, { accessions })` runs the deed check last. For an object, archival unit or digital asset it refuses with no register (`accessions_unknown`), with anything not made by `indexAccessions` (`invalid_accessions`, `invalid_options`), with another organization's register (`mixed_organizations`), when the record, any record in its current ancestry, or for a digital asset the record it represents and that record's ancestry (asset chains followed up to 8 hops, cycles stopped) is unknown to the register (`accessions_out_of_date`, `represented_record_unknown`), and when any of them is held (`deed_not_signed`, naming no donor, accession or number). Agents, places and events need no register. `publicOutput` takes the same option; with `records` it finds the ancestry again as it is now.
- **Links to held records.** A `record_link` or place link to an object, archival unit or digital asset goes out as `baseUrl` + ID only when `publicOutput` is given `records` and the target's current ancestry and represented chain are all known to the register and none is held; otherwise only its label goes out. So a page published without `records`, and an agent, place or event page published without `accessions`, shows such links as labels only (found in review: partial and stale registers made held records live links). **Amended by D-045:** a `record_link` that isn't linked now puts out nothing, not its label; a place keeps its name.
- **Only as fresh as the register.** Make it at publish time from the organization's records, accessions and contacts as they are now. A register that doesn't know a record refuses it rather than clearing it.
- **Staff-only.** Accessions and contacts are never records or fields; `effective.ts` and `public-output.ts` import only `accession-holds.ts`, which exposes the organization and two lookups (`isHeld`, `isKnown`). Messages never quote contact details, materials, restrictions or notes.
- **How T-034 calls it:** build `indexAccessions` at the moment of publishing, refuse on any `effectivePublishIssues(effective, { accessions })` issue, and pass the same fresh register and `records` to every `publicOutput` call. When an accession is saved (a deed back to missing, a record added), list the published records among `recordsHeldBack(register)` and offer to withdraw them.
- **Rejected:** an optional check, or one that passes without a register or with one that doesn't know the record; an `effectiveRecord` option (a kept view would keep a stale answer); donor contacts on agent records (agent records can be public); accessions as a seventh kind (D-037); accession numbers in `RecordIdentifiers` or of a public type; refusing a record listed by two accessions (accruals happen; the stricter hold wins).
- **Not done yet:** ~~restrictions are text and hold nothing back (T-016a)~~ structured restrictions hold since D-056; who changed a deed and when (Phase 2 change log); concurrent saves (T-032).
- Source: Collections Trust, "Acquisition and accessioning: suggested procedure" (Spectrum 5.0), read 2026-11-23.

## D-044 — Loans and condition checks: loans point at moves, checks are dated entries, both staff-only (2026-11-23, autopilot T-018)
Spectrum "Loans in", "Loans out" and "Condition checking and technical assessment" in `loans.ts` and `condition-checks.ts`, built on the move log (D-040), which this entry amends.
- **A loan:** a random v4 UUID, `organizationId`, `direction` (`in`, `out`), `number` (unique per organization and direction ignoring case), `agentId` (lender or borrower), `beginOn` and `endOn` (both required: "All loans are for fixed periods"; an extension edits `endOn`), `status` (`requested`, `agreed`, `declined`, `cancelled`, `closed`) with `statusOn` (not after tomorrow, `future_status`), optional `purpose`, `terms`, `note`, and 1 to 500 items.
- **Where things are stays in the move log.** A loan out item names its `loanOutMoveId` (a `loan_out` to an outside location whose `agentId` is the borrower) and, once back, its `returnMoveId`; a loan in item names its `arrivalMoveId` (a `placement`) and `departureMoveId` (a `departure` to the lender, or the place a correction straight after it names). The start move must fall within the loan period (`move_outside_loan`); the end move must be the record's first return or departure after it (`end_out_of_order`); nothing may have moved on a requested, declined or cancelled loan.
- **Problems stay with their loans, and never hide one.** The whole book is refused only for invalid loans, duplicate IDs or numbers and another organization's loans. Move-link problems (`unknown_move`, `move_reused`, `wrong_move_reason`, `not_agent_location`, `end_out_of_order`, `move_outside_loan`, `overlapping_loans`) are reported on every loan involved, never only the later one. A loan with problems has phase `unknown` and stays on `overdueLoans` once past its end date. `withLoan` refuses an edit with any problem of its own or that gives another loan a new problem, and an edit that drops a recorded move link or removes an item whose start is recorded unless its end is recorded (`link_removed`). A closed loan out whose record has an unexplained `loan_out` to the borrower in the loan period has `closed_with_unlinked_move`; a loan in closes only when every item's departure is linked or the item never arrived (`closed_without_departure`). `unexplainedLoanMoves` and `unexplainedDepartures` list moves no loan names (found in three review rounds: decoy and self-edits, problem loans and back-dated moves could all take an overdue loan off the lists).
- **The due date feeds storage.** `loanOutMove` builds the `loan_out` with `expectedReturnOn` = `endOn`, refusing a day outside the loan; an extension is another `loan_out` to the borrower. `loanState` reports `dueBack` and `dueMatchesLoan`; `overdueLoans(book, today)` lists late loans out and loans in not yet gone back.
- **`departure` (amends D-040):** a record leaving the organization's care for good (so far, a loan in going back). It goes to an outside location, takes no return date, and is allowed only when the record is in care and no return date is outstanding (`departure_while_away`). Afterwards only a `placement`, or a `correction` to another outside location written down after it, may follow (`move_after_departure`), so a back-dated departure can't wipe a normal location while the record is out.
- **A condition check** is one dated entry per record: `checkedOn`, `checkedBy` (and optional `checkerId`), `condition` (`good`, `fair`, `needs_conservation`, as in the mockup), `reason`, optional `fitToMove`, `loanId`, `note`, and `recordedAt` (Spectrum's minimum: "the date, name of the condition checker and the reason for checking"). `fitToMove(log, recordId, { on, maxAgeDays })` answers `fit`, `unfit`, `stale` or `unchecked`; `needingConservation` lists records whose latest check says so.
- **Snapshots, organizations and staff-only** as in D-040: opaque frozen books and logs, caller lists read once, required `organizationId` with mixed sets refused; agent, record and loan IDs are checked as IDs only (T-032 checks ownership); nothing in `effective.ts` or `public-output.ts` reads them.
- **Rejected:** locations or an "on loan" flag on the loan (a second truth); open-ended loans; organization-defined condition terms for now; checks that edit earlier ones; departures from anywhere; refusing a whole book for one stale loan; flagging only the later of two loans.
- **Not done yet:** a borrowed item that stays for good (bought or given) can't close its loan in until acquisitions can link to it; authoriser, valuation and insurance fields; linking a check's `loanId` to the loan book; saving a move and its loan edit in one transaction (T-032).
- Sources: Spectrum 5.0 "Loans in", "Loans out" and "Condition checking and technical assessment", as reproduced by a museum (pitstonemuseum.co.uk/pims/spectrum-5.0/), read 2026-11-23; the 5.1 procedure text couldn't be reached.

## D-045 — Links to private records show nothing on public sites (2026-11-23, John)
John's answer for S-011: when a published record links to a record that isn't published, or belongs to another organization, the public site shows nothing for that link: no ID, no label, no placeholder. Staff still see the link.
- **Why:** a label copied from the target (a donor's name, a private item's title) would reveal the private record. Showing nothing is the only answer that can't leak.
- **Rejected:** publishing the target's label without its ID (the D-039 behaviour, which this replaces); a staff-written public label (more work for staff, and an easy place to type a private name).
- **Changes:** S-011 implements it; the `record-links.ts` header and D-039 are updated to match.
- **How (S-011):** `publicView` holds no `record_link` values at all, since it can't know which records are published; `effectiveRecord` records the keys of the public link fields beside the view, and `publicOutput` reads those values from the effective record, template-checks them, and puts out each one that may be named (D-039's rules plus the deed check of D-043) as its URL and label. The others are dropped; a term left with no values is left out of every form. A place value keeps its own name (and gazetteer URI) without the link, only when the organization's place checker vouches for its place record (D-048).

## D-047 — Dublin Core mappings belong to an organization; built-in mappings are presets (2026-11-23, autopilot T-019b1)
Extends D-030 and D-012 to Dublin Core mappings, the one kind of organization data in `packages/core` that still had no owner (T-019a review: a mapping was matched to a template by key only, so one organization's mapping passed for another's template with the same key).
- **Shape.** `DublinCoreMapping` is `{ organizationId, template, entries }`, with a required `organizationId`, as the database row will carry an `organization_id` column. `DublinCoreMappingPreset` is the same without `organizationId`; the built-in `DACS_DUBLIN_CORE`, `SPECTRUM_DUBLIN_CORE` and `DIGITAL_ASSET_DUBLIN_CORE` (and `presetDublinCoreMapping`) are presets now, a breaking type change like `TemplatePreset`.
- **Checks.** `validateDublinCoreMapping(mapping, template)` validates the template with `validateTemplate`, so a preset template without an organization is `invalid_template` (D-030 let mappings be checked against presets through an internal `validateTemplateShape`; that function is removed). In `validateDublinCoreMapping`, a mapping whose `organizationId` is missing, invalid, inherited or behind a getter is `invalid_organization` (`mappingForTemplate` and `mappingFromPreset` answer `unreadable` for a getter), and one of another organization than the template's is `wrong_organization`. Either gives **that one issue only**, decided before any entry is looked at, so the result never names the mapping's template key, fields or either organization's ID. The mapping is read once into a frozen copy and the decision uses the copy; when the copy can't be made, the organization is read from the input's own data property instead, and its issues (which can quote the mapping's keys) are returned only if the mapping's own `organizationId`, read without running a getter, is the template's. `publicOutput` goes through this check, and the template it uses is already tied to the record's organization (T-019a), so a mapping publishes only for records of its own organization.
- **Copies.** `mappingFromPreset(preset, template)` makes an organization's mapping from a preset for one of its templates: `template` becomes the template's key and `organizationId` the template's organization, then the whole copy is checked. A mapping that already has an `organizationId` (even `null`) is refused (`has_organization`), as a guard against mistakes rather than a security boundary, as with `templateFromPreset`. `mappingForTemplate(mapping, template)` still re-targets a mapping to another template, but only within its own organization: it keeps the mapping's `organizationId`, so another organization's mapping or one without an organization is refused.
- **Rejected:** letting a mapping without an organization match any template (a missing owner would silently match every organization, D-030); having `mappingForTemplate` adopt the template's organization for an organization-less mapping (one function would both re-target and change ownership, so stripping `organizationId` from another organization's mapping would be enough to take it over; a separate `mappingFromPreset` makes the adoption explicit); keeping `validateTemplateShape` so mappings can still be checked against presets (nothing outside tests did that, and a check that accepts an unowned template is the kind of path that reads across organizations); reporting the usual entry issues alongside `wrong_organization` (they would name another organization's field keys).
- **Vocabularies, terms and rights settings (T-019b2).** Not changed here: in `packages/core` vocabularies and rights terms are built-in standard lists, controlled terms are stored inside records (which carry an `organizationId`), and there are no stored rights settings yet. When local term lists, stored authority terms (T-027) or rights settings become data, they get the same required `organizationId`.

## D-049 — PostgreSQL 15 to 19, and a throwaway test database inside the gate (2026-11-23, autopilot T-020)
**Versions.** Oculus supports every PostgreSQL major version the community still supports, and no others. On 2026-11-23 that is **15, 16, 17, 18 and 19**. PostgreSQL 14 had its final release on 2026-11-12 and is not supported. The range moves with postgresql.org's versioning page. Each major gets 5 years, so 15 drops after its final release on 2027-11-11 (16: 2028-11-09). A new major is added once CI passes on it.
- **Write SQL for the oldest supported version.** Nothing newer than 15 may be used until the floor rises. For example, `uuidv7()` is new in 18 and `JSON_TABLE()` is new in 17. UUIDs come from `gen_random_uuid()` or from Node's `crypto.randomUUID()`.
- **`db:migrate` checks the server first.** It reads `server_version_num` and refuses to run below 15. Above the newest major CI tests, it gives a warning.
- **Hosting may narrow the range later.** Q-2/D-035/D-046 may narrow it, for example to the versions SiteGround's shared plans offer. Its knowledge base lists PostgreSQL but no version could be read here, so this is checked with SiteGround before T-051. The range never widens to a version the community no longer supports. If a host offers only an end-of-life version, that host doesn't meet D-035.

**Database tests in the gate.** `npm run gate` stays one command, and database tests are ordinary Vitest tests that count toward `tests_passing`.
- **Where the gate gets its database.** If `OCULUS_TEST_DATABASE_URL` is set, the gate uses that server (CI does this). Otherwise it starts its own throwaway server:
  - It runs `initdb` into a new temporary directory, finding the binaries through `PG_BIN` or `pg_config --bindir`.
  - It starts the server with `pg_ctl start -w`, listening only on a Unix socket in that directory (`listen_addresses=''`, so no TCP port) and with `fsync=off`.
  - It runs Vitest, then always stops the server with `pg_ctl stop -m fast` and deletes the directory, whether the tests passed or not. No server is left running.
- **No password anywhere.** Local tests use trust authentication on the private socket.
- **Running as root.** `initdb` refuses to run as root, and the build sandbox runs as root. So under uid 0 the gate runs `initdb` and `pg_ctl` as the `postgres` system user (`runuser -u postgres`), with the temporary directory owned by that user.
- **The sandbox.** It has PostgreSQL 16.15 at `/usr/lib/postgresql/16/bin` (`pg_config --bindir`). The current 16.x minor is 16.16. There is a client-only Docker with no daemon. The system cluster `16/main` is stopped and stays unused.
- **No silent skips.** If there is no URL and no PostgreSQL binaries, the gate fails with a message saying how to provide one. A database test with no database fails; it is never skipped.
- **Test isolation.** Each test file works in its own freshly created database and drops it afterwards. T-024 decides the details, such as cloning a migrated template database.
- **GitHub Actions.** The `gate` job runs `npm run gate` once per PostgreSQL version: 15 (the oldest supported) and 19 (the newest). Each uses an official `postgres:<major>` service container:
  - It has a `pg_isready` health check and port 5432 mapped to the runner.
  - It uses `POSTGRES_HOST_AUTH_METHOD: trust`, so there is no password in the repository, not even for tests. The container is reachable only from that job.
  - `OCULUS_TEST_DATABASE_URL` points at `localhost`.
  - If no `postgres:19` image is published yet when T-024 runs, it uses 18 and adds a follow-up task.

**Rejected:**
- Supporting 14 or older (14 is end-of-life).
- Testing only the sandbox's 16 (misses both ends of the range).
- Testing all five majors in CI (the oldest and newest catch use of newer features and breakage on a new release, at a fraction of the CI minutes).
- Pointing tests at the long-running system cluster (state leaks between runs, and a server is left running).
- Docker or Testcontainers locally (the sandbox has no Docker daemon).
- `embedded-postgres`-style npm packages (they download server binaries the license check can't see).
- Skipping database tests when no database is available, or mocking the database (both weaken the gate).
- A password in the workflow file.

**Sources:**
- https://www.postgresql.org/support/versioning/ (supported versions and final-release dates; read 2026-11-23, page showing 19.0 released 2026-11-19)
- https://www.postgresql.org/message-id/attachment/201383/20260813updaterelease.md (14 end-of-life notice)
- https://www.postgresql.org/docs/release/18.0/ (`uuidv7()`)
- https://www.postgresql.org/docs/release/17.0/ (`JSON_TABLE()`)

- Not read (requests blocked): https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers and https://www.siteground.com/kb/postgresql-manager. T-024 reads the GitHub page before writing the workflow.

## D-050 — Database access: the `pg` driver with hand-written SQL through one `sql` tag; plain `.sql` migrations run by our own runner (2026-11-23, autopilot T-021)
**The driver and the queries.** `pg` (node-postgres) with hand-written SQL. `pg` is a runtime dependency of `packages/db` only, and `@types/pg` is a dev dependency.
- **One place imports the driver.** `packages/db` is the only package that imports `pg`, and lint enforces this with `no-restricted-imports`.
- **Every query goes through one `sql` tagged template.** It is written in `packages/db` and turns each `${value}` into a `$n` parameter, returning `{ text, values }` for `pg`.
  - There is no raw-string escape hatch. Table and column names are written in the SQL text, never interpolated.
  - Lint bans calling `.query()` with anything but the tag's result.
- **JSONB without building strings.** Values go in as parameters (`${JSON.stringify(v)}::jsonb`). A template field's key is a parameter too (`fields -> ${key}`), never part of a path string.
- **Full-text search without building strings.** It uses `websearch_to_tsquery(${config}::regconfig, ${q})`, and the search text is always a parameter.
- **TypeScript types.** Each query function declares its row type. Types aren't generated from the database, so every query has a test that runs it against the migrated test database (D-050 T-020), and a mismatch fails the gate.
- **Type parsers.** T-024 sets them explicitly: `int8` and `numeric` come back as strings, not lossy numbers, and dates come back the way D-008 stores them.
- **Separate roles.** The public sites' read-only path is a separate connection pool with its own database role (D-034).

**Migrations.** Plain SQL files in `packages/db/migrations/NNNN_short_name.sql`, forward only, applied by a small runner in `packages/db` (`npm run db:migrate`, T-024). The runner:
- takes a `pg_advisory_lock`, so two runs can't migrate at once;
- runs each file in its own transaction;
- records the file name, a SHA-256 of its contents and the time in an `oculus_migrations` table;
- refuses to run if an applied file was edited, is missing, or a new file sorts before an applied one.
- **No down migrations.** Undoing a migration is a restore from backup (T-052).
- **Statements that can't run in a transaction** (for example `CREATE INDEX CONCURRENTLY`) are left for T-024 to decide, if they're ever needed.

**Candidates checked** (npm registry and npm's advisory database, 2026-11-23):
- **`pg` 8.23.1** (released 2026-09-30):
  - MIT; 14 packages in all, every one MIT or ISC; no install scripts that run.
  - One advisory ever: GHSA-wc9v-mj63-m9g5, a critical code-execution bug affecting only versions before 7.1.2 (fixed in 2017).
  - One npm maintainer.
- **`postgres` 4.1.1** (porsager; released 2026-11-11):
  - Unlicense; no dependencies; no advisories; tagged templates built in.
  - One maintainer; 4.0.0 is a new major from 2026-10-29.
- **Kysely 0.29.9** (query builder; released 2026-11-12):
  - MIT; no dependencies, but needs `pg` to talk to PostgreSQL; two maintainers.
  - Four high-severity advisories in its 0.26–0.28 lines, injection through JSON path keys and `sql.lit`: GHSA-pv5w-4p9q-p3v2, GHSA-wmrf-hv6w-mr66, GHSA-8cpq-38p9-67gx, GHSA-fr9j-6mvq-frcv.
- **Drizzle ORM 0.45.4** (released 2026-10-08):
  - Apache-2.0; four maintainers; needs `pg` or `postgres`.
  - A high-severity SQL injection through identifiers, fixed in 0.45.2: GHSA-gpj5-g38j-94v9.
  - `drizzle-kit` 0.31.11, which writes its migrations, brings esbuild, tsx and the deprecated `@esbuild-kit` loader, with 4 moderate advisories (GHSA-67mh-4wv8-2f99).

  - MIT; three maintainers; 36 packages.

**Why `pg`.** It passes the license check and has a small, audited dependency tree. Plain SQL is exactly what the PostgreSQL docs describe, so JSONB, full-text search, roles and views (D-034) need no translation layer. Its 15-year record has one old advisory. It is also the driver Kysely, Drizzle and the migration tools are built on, so a query builder would add a layer, not replace `pg`.

**An exception to the Phase 2 rule "more than one maintainer, or a foundation behind it".** `pg` has one npm maintainer. So does `postgres`, and both ORMs and query builders still need one of these two drivers, while Node has no built-in PostgreSQL client. The risk is contained because only `packages/db` imports the driver. If `pg` stops being maintained, moving to `postgres` changes one package. Upkeep watches its release dates.

- **graphile-migrate.** One maintainer, and dependencies years out of date (chalk 3, yargs 15, `@types/node` 14).
- **dbmate.** A Go binary delivered through npm, outside the npm license check and audit.

## D-051 — The HTTP server: Fastify 5 (2026-11-23, John and autopilot T-022)
John chose a well-known framework over a hand-written layer, so a future maintainer meets something familiar. Oculus serves its JSON API, the admin's built files and the server-built public pages (D-034) with **Fastify 5** (MIT, an OpenJS Foundation project, five npm maintainers), pinned at 5.12.8 or later.
- **Why Fastify.** Of the frameworks compared it has the best defaults for this task: a 1 MiB body limit, protection against prototype poisoning in JSON bodies, schema-checked routes and an exact router (find-my-way) rather than route strings turned into regular expressions. It needs no WebSockets (D-035, D-046).
- **Its record, and what we do about it.** It installs 48 packages (all MIT, ISC or BSD-3-Clause, D-002) and has 20 GitHub advisories over its life, 10 high. Six were in 2026: Content-Type parsing that let bodies skip validation (GHSA-jx2c-rxcm-jvmq, GHSA-247c-9743-5963, GHSA-573f-x89g-hqp9), an authentication bypass through malformed URLs (GHSA-p68q-wchp-6fh7, fixed in 5.12.2) and X-Forwarded-* spoofing (GHSA-444r-cwp2-x5xf, GHSA-3m5p-2c4r-xxw2). So Oculus:
  - registers its own content-type parsers for exactly `application/json` and, on form routes, `application/x-www-form-urlencoded`, and refuses everything else with 415, including compressed bodies;
  - leaves `trustProxy` off unless an environment variable names the trusted proxy;
  - checks every body again with the core validators, never trusting the route schema alone;
  - doesn't use the default logger for request bodies or cookies.
- **The rules on top** (T-022a builds them; `(risky)`, independent review, an attack test for each):
  - **Bodies:** 1 MiB default, 8 KiB for sign-in, two-step and site password posts, counted for chunked bodies.
  - **Paths:** encoded slashes, backslashes, `..` and NUL refused; unknown routes 404, wrong methods 405, before any handler.
  - **Cookies:** `@fastify/cookie` (OpenJS, MIT), read only for Oculus's own names; the same Oculus cookie twice is refused; written only through one helper that sets `__Host-`, `Secure`, `HttpOnly`, `SameSite` and `Path=/` (ASVS 5.0 3.3.1–3.3.4).
  - **Changes:** any method other than GET or HEAD carries an `Origin` matching the host or `Sec-Fetch-Site: same-origin`, plus T-037's CSRF token (ASVS 5.0 3.5.1, 3.5.3).
  - **Timeouts** shorter than Node's defaults; **errors** without stack traces (T-042).
  - Any other Fastify plugin is its own dependency decision.
- **Rejected:**
  - **A small layer on `node:http`** (the autopilot's first draft): fewest outside parts, but security code that only the autopilot and its reviewers would know — John preferred the familiar framework.
  - **Express 5:** 65 packages and a history of body-limit and ReDoS bugs in its parts (body-parser GHSA-v422-hmwv-36x6, GHSA-27r3-jxmh-p828; path-to-regexp GHSA-9wv6-86v2-598j, GHSA-j3q9-mxjg-w52f); no cookie reading without another package.
  - **Hono:** one npm maintainer, and repeated body-limit and cookie bugs (GHSA-9vqf-7f2p-gf9v, GHSA-26pp-8wgv-hjvm and others).
- **Upkeep:** Fastify's advisories are watched like every dependency (npm audit in the gate, Dependabot); a Fastify major version gets its own decision entry.
- Sources: https://fastify.dev/docs/latest/Reference/Server/ ; https://nodejs.org/api/http.html ; the npm advisory bulk endpoint (GitHub Advisory Database) for fastify, @fastify/cookie, find-my-way, express, body-parser, path-to-regexp, hono and @hono/node-server; OWASP ASVS 5.0 V3; `npm view` and trial installs, all read 2026-11-23.

## D-052 — Passwords with scrypt now and Argon2id later, two-step sign-in required for all staff (TOTP and recovery codes), sessions stored in PostgreSQL (2026-11-23, autopilot T-023)
Everything here uses `node:crypto` (`scrypt`, `randomBytes`, `createHmac`, `createHash`, `timingSafeEqual`, AES-256-GCM). No new dependency is needed. Checked against OWASP ASVS 5.0 V6 (Authentication), V7 (Session Management) and V3.3 (cookies).

**Passwords**
- **scrypt from `node:crypto` for now, N=2^14, r=8, p=5 (16 MiB).** This is one of OWASP's equal-strength scrypt settings, and the one that uses the least memory per sign-in, which matters on shared hosting (D-046). It took about 0.2 s in the sandbox, against 0.5 s and 128 MiB for N=2^17, p=1.
  - The salt is 16 random bytes and the key is 32 bytes.
  - Hashing always uses the async `crypto.scrypt` (the libuv thread pool), never `scryptSync`, and only a few hashes run at once, so a burst of sign-ins can't starve the server.
  - Each hash is stored as one PHC-format string with the algorithm and its settings (`$scrypt$ln=14,r=8,p=5$<salt>$<hash>`). When the settings or the algorithm change, a password is re-hashed at the next sign-in. Hashes are compared with `timingSafeEqual`.
- **Argon2id later.** OWASP prefers Argon2id (m=19456 KiB, t=2, p=1), and `crypto.argon2()` exists only from Node 24.7.0 and needs OpenSSL 3.2 or later. Oculus still supports Node 22 (D-006), and the build sandbox runs 22.23.5, where it is missing, so the gate couldn't test it. When the `engines` floor is raised to 24.7 or later (Node 22's support ends in April 2027), a decision entry switches new hashes to Argon2id, and the PHC format moves each user over at sign-in.
- **Password rules (ASVS 5.0 6.2):**
  - Length is at least 8 characters (6.2.1), with 15 recommended on the form. At least 64 characters are allowed (6.2.9); the cap is 1,024 bytes, which keeps request size bounded.
  - There are no composition rules (6.2.5), no forced rotation (6.2.10) and no hints or secret questions (6.4.2).
  - The password is hashed exactly as received, with no trimming, case changes or truncation (6.2.8).
  - A new password is checked against a bundled list of at least the 3,000 most common passwords (6.2.4) and a list of context words such as "oculus", "dickinson", "historical" and the organization's name (6.1.2, 6.2.11). The list's own license must pass D-002.
  - A check against breached passwords (6.2.12, for example the Have I Been Pwned range API) would be an outbound request. It is left as a later, off-by-default option with its own security review.
- **Sign-in throttling (ASVS 6.1.1, 6.3.1, 6.3.8):**
  - Failures are counted in PostgreSQL (no Redis needed) per account and per client address. The client address comes from the socket unless a trusted proxy is configured (D-051).
  - Each counter brings a growing delay and then a temporary block, never a permanent lockout, so nobody can lock a colleague out by guessing.
  - A wrong user name gets the same reply and the same timing as a wrong password: it is checked against a dummy hash.
  - The rules are written down, as 6.1.1 asks.
- **Rejected:**
  - The npm `argon2` package: a native add-on with prebuilt binaries, a poor fit for shared hosts, and a new dependency where Node will soon do the job.
  - bcrypt: legacy only, and it ignores everything past 72 bytes.
  - PBKDF2.
  - A pepper: an extra secret in the environment that, if lost, makes every password fail. OWASP calls it defence in depth only.

**Two-step sign-in**
- **TOTP per RFC 6238, built with `node:crypto` alone.** It uses HMAC-SHA-1, which every authenticator app supports, with 6 digits and 30-second steps. One step either side is accepted for clock drift, using the server's clock only (ASVS 6.5.5, 6.5.8).
  - The secret is 20 random bytes (160 bits, RFC 4226's recommended length). It is shown as RFC 4648 base32 text and as an `otpauth://` link.
  - The last accepted time step is stored per user, so a code is never accepted twice, even within its window (RFC 6238 §5.2, ASVS 6.5.1).
  - Code attempts are throttled like passwords.
- **The TOTP secret is encrypted at rest** with AES-256-GCM under a key from an environment variable (`OCULUS_SECRET_KEY`, never in the repository). It can't be hashed, because the server must read it to check codes. If that key is lost, two-step sign-in stops working but nothing else does. People then use recovery codes, or a system manager resets their two-step sign-in (D-019).
- **Recovery codes:** 10 single-use codes, each 120 random bits (24 Crockford base32 characters in groups of 4). They are shown once and stored as SHA-256 hashes. ASVS 6.5.2 allows a plain hash at 112 bits or more, so checking a code is not ten scrypt runs. Making a new set replaces the old set, and each use is logged.
- **QR code:** the setup screen needs an encoder to show the `otpauth://` link as a QR code. Choosing one (for example `uqr`, MIT, no dependencies) is T-038's own dependency decision. Without one, the screen shows the key as text.
- **WebAuthn (passkeys) later, not now.** It needs CBOR and COSE parsing of authenticator data, which means either a library or a lot of hand-written parsing, and ASVS asks for phishing-resistant factors only at Level 3 (6.3.3). Factors are stored in their own table, keyed by type, so WebAuthn can be added later without a schema rewrite.
- **Required for every staff account (John, 2026-11-23; ASVS 5.0 6.3.3 Level 2).** A new account sets up two-step sign-in at its first sign-in, before it can do anything else; it can't be turned off, only reset (new secret, new recovery codes) by the person or a system manager. This replaces the plan's "optional, admins can require it" (§3).
- Resetting two-step sign-in, changing a password and changing the sign-in email all need the password again, and the second factor if it is on (ASVS 7.5.1). Afterwards the person is offered "sign out everywhere else" (7.4.3).

**Sessions: server-side in PostgreSQL**
- **The session token:**
  - The token is 32 random bytes from `randomBytes` (256 bits; ASVS 7.2.3 asks for 128). Only its SHA-256 hash is stored, so a database leak gives no usable sessions.
  - It is a new token at every sign-in and at any change of role or privilege (7.2.4).
  - Each session row holds the user, the one organization the session is working in (D-019), the creation and last-seen times, and the sites unlocked in it (T-019d).
- **The cookie:** `__Host-oculus_session`, with `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` and no `Domain` (ASVS 3.3.1–3.3.4), written only through T-022's cookie function.
  - The admin should be served from its own hostname, separate from the public sites (ASVS 3.5.4), so the session cookie is never sent to a public page. T-050 and T-051 set that up.
- **CSRF:** a token for each session, required on every change, together with T-022's Origin check.
- **Time limits:**
  - **4 hours idle (John, 2026-11-23)** and 12 hours absolute by default. John chose 4 hours so long cataloguing sessions aren't interrupted; it is longer than NIST SP 800-63B's 30-minute AAL2 figure, which is acceptable here because two-step sign-in is required for everyone. System managers can change both within bounds in System settings, and T-037 documents them as ASVS 7.1.1 asks.
  - There is no limit on parallel sessions, but a person can see their sessions and end any of them (7.1.2, 7.5.2), and a system manager can end anyone's (7.4.5). Deactivating an account or resetting a password ends all of its sessions (7.4.2, T-039).
  - Expired rows are deleted by a cleanup command any scheduler can run (D-035). An expired session is refused even if the cleanup never runs.
- **Rejected: signed tokens (JWT or signed cookies).** Sign-out, sign-out everywhere, deactivation and role changes would all need a revocation list in the database anyway (ASVS 7.4.1). A signing key would have to be managed and rotated, and the history of JWT algorithm-confusion bugs (for example GHSA-f67f-6cw9-8mq4 in Hono) shows the risk. PostgreSQL is already required, so stored sessions cost nothing extra.

**Site passwords (T-019d)**
- **Stored:** a site's password is hashed exactly like a user's password, as a PHC string on the site row. Only a system manager can set it, after entering their own password again. It is never shown or emailed.
  - Because many staff share it, its minimum is 15 characters (ASVS 6.2.1's recommended length), and it is checked against the same common-password and context-word lists.
  - The row keeps a version number. Changing the password raises the version, which ends every existing unlock.
- **Unlocking:** after sign-in, entering the right site password records an unlock (site and password version) on the server-side session row, never in a separate cookie, and issues a new session token. The unlock ends with the session or when the password changes. The service layer checks for the unlock on every request for that site, not only in the admin screens.
- **Rate limiting:** the same PostgreSQL throttle as sign-in, counted per user per site and per site overall, with growing delays and a temporary block (never a permanent lockout). Every failure is written to the change log, and the form is an 8 KiB form post with the CSRF token and the Origin check.

## D-053 — Record type edits and deletions list the records they strand (2026-11-23, autopilot T-013a)
`recordTypeChanges(oldType, newType, existing?)` and `recordTypeDeletion(type, existing?)` (record-type-changes.ts) are the record type counterpart of D-023 and D-031, with the same frozen `{ changes, needsConfirmation, recordsChecked }` and changes carrying `recordIds` (at most `MAX_LISTED_RECORDS`) and `recordCount`. The codes:
- `key_changed`: records naming the old key in `recordTypeKey` stop passing `checkRecordType` until moved; a new key another type has is refused (`key_taken`).
- `key_adopts_records`: records already naming the new key (left from a deleted type) are taken over; `mismatchRecordIds` are those of another kind (listed up to the cap, all counted in `mismatchCount`). Always needs confirmation; reported without `existing` in case there are any.
- `kind_changed`: the type's records whose kind isn't the new one (they fail with `wrong_kind`).
- `type_deleted`: the records naming the type.
- `unverified`: `recordTypeChanges` without `existing`. The old type is then only the caller's word (stale, or claiming the new kind already), so the edit always needs confirmation, even when the two versions look the same (found in review).

Each needs confirmation when it affects records, and always when `existing` isn't given. Label, description and default template edits aren't reported: the type never decides a record's template or what it publishes (D-037). The new type's default template isn't checked here; `validateRecordType` does that.
- **`existing` is `{ recordTypes, records }`, both required**; the old type must be in the list exactly (`type_not_listed`), so with `existing` a caller can't hide a kind change by claiming the old kind; without it, the edit always needs confirmation (`unverified`). An empty list means none.
- **One organization (D-030), checked first:** the new type's `organizationId` is compared with the old type's before its shape is checked, so another organization's malformed type gets only `mixed_organizations`; both lists are read slot by slot once, as own data properties, and their organization checked before any entry is validated or any key looked up, so another organization's list, valid or not, gets no message naming its keys. Any invalid entry, duplicate type key or record ID, hole, getter or Proxy refuses the whole check; `recordTypeKey` and `description` are read as own properties, so a polluted `Object.prototype` adds nothing. Lists are capped at `MAX_RECORD_TYPES` and `MAX_RECORD_SET`, refused before any slot is read.
- **Rejected:** checking the new default template here (that needs the template registry and is `validateRecordType`'s job); reporting label or default template changes (they strand nothing); a `recordTypeCreation` for a new type adopting left-over records (a type changes no publication, so this is only data hygiene; the rename case covers the common path).
- **Not covered:** `templateChanges` doesn't yet take `recordTypes` (a template edit that drops a kind a type's default needs is found by `recordTypeTemplateIssues`); records are not moved to a renamed key here, the caller does that.

## D-055 — Narrowed link kinds in template changes, and a staff report of stale link labels (2026-11-23, autopilot T-015a)
- **`record_kind_removed`.** `templateChanges` takes a fourth argument, `options`, whose `linkChecker` is the organization's `makeRecordLinkChecker`. When a `record_link` field's `recordKinds` narrows (no `recordKinds` counts as all six), the change lists the records linking to a kind the field no longer allows, with `removedCodes` naming the kinds dropped, and needs confirmation when any record is affected or none were given. Without the checker every record holding a link under the key is listed, since any may be affected. A link the checker can't resolve to a kind (a record it doesn't hold, such as a deleted one or one added after the checker was made, an ID used twice, an invalid record) is counted too: its kind is unknown, so it may be affected (fail closed, from the review). A place field always links to places, so it can't narrow; `record_link` to `place` is `kind_changed`. The checker must be one `makeRecordLinkChecker` made (a Proxy of one or a hand-made function is `not_a_link_checker`) for this template's organization (`wrong_organization_checker`; one that belongs to no organization, made from an empty set with none given, is `no_organization_checker`; both checked before any record is read); options that are a Proxy, not a plain object or hold a getter are `invalid_options`. No message names a kind's record, title or label.
- **`findStaleLinkLabels(organizationId, records, templates, options?)`** (link-label-report.ts), for Data Cleaning: the `record_link` and place values whose label differs from the linked record's current title (after NFC, trimming and collapsing white space; case counts), with the label and title quoted. **Staff only**: titles may be private. The caller names its organization; records of another organization (decided from every entry of the set, valid or not, so a set of another organization's invalid records is refused too), a set mixing organizations or another organization's template registry refuse the whole report, naming nothing, and a template a lookup gives for another organization skips that record. Titles come only from the records given, so a link to an ID outside them is only counted (`unknownTargets`). Only own values are read. Entries and skipped records are capped by `maxEntries` (default 500, at most 10,000) with full counts.
- **The checker's organization (review).** `makeRecordLinkChecker` took its organization from valid records only, so a set of another organization's invalid records made a checker with none, which `templateChanges` accepted and which counted nothing. Now the organization is the set's, read from every entry valid or not (as `indexRecords` already requires), and `makeRecordLinkChecker(records, organizationId?)` may be told whose records these must be (another organization's: `wrong_organization`; an empty set then makes that organization's checker). A checker of no organization (an empty set with none given) refuses every value that names a record with `no_organization_checker` (a place holding only a name needs no checker and passes); `publicOutput` refuses it outright as `checkers.record_link` or `checkers.place` (as it does another organization's), `effectiveRecord` shows none of its place names, and `templateChanges` refuses it. `indexAccessions` reads the records' organization the same way (another organization's invalid records are `mixed_organizations`) and makes its checker for the register's organization, so a set with no valid records gives `unknown_record`.
- **Rejected:** a list of target records as the `templateChanges` option (the checker already holds a per-organization snapshot of kinds and is what callers pass elsewhere); leaving links the checker can't resolve uncounted (first version: an empty, partial or stale checker then reported nothing and needed no confirmation, failing open). Counting them closes that for records the checker doesn't know, but not for a record it knows under an old kind: a checker made before a linked record changed kind still answers with the old kind and can under-report. So callers must make the checker from the organization's current records at save time, in the same snapshot as the records given; the service layer (T-032) does this; scanning values by shape without templates (a left-over or a field of another kind could be read as a link); case-insensitive matching (a case change in a title is a real difference staff may want to copy).

## D-056 — Structured access restrictions on accessions hold records back like an unsigned deed; "today" comes from the caller (2026-11-23, autopilot T-016a)
Extends D-043.
- **Shape.** An accession may have `accessRestriction`, one of `{ kind: "closed_until", until }` (`until` an EDTF day `YYYY-MM-DD`: the first day the records may be published, as the mockup's "Nothing from this accession will be published before then") or `{ kind: "staff_and_researchers" }` (never on the public site). One per accession, as the mockup offers one choice. The free-text `restrictions` stay notes in the donor's words and hold nothing; the mockup's "Other condition" is notes only. Malformed parts are refused (`invalid_restriction`, `invalid_date`, `unknown_property`) without quoting them (an unknown key is reported once at `accessRestriction` itself, never by name); only own data properties are read, both when checking and when the register judges restrictions, so nothing on `Object.prototype` can add, complete or end a restriction.
- **"Today" is given, never read.** `indexAccessions` requires `today`, the organization's calendar day in its own time zone, `YYYY-MM-DD` (`invalid_today` otherwise, including a `Date`, a number or an ISO instant). Core never reads the clock or converts an instant to a day, so a time zone edge is the caller's to get right (T-034 works it out from the organization's time zone). The register keeps it as `heldAsOf`. A `closed_until` restriction is in force while `today < until`, compared as days; `staff_and_researchers` always is. Precedent: `overdueLoans(book, today)` and `overdueReturns(log, today)`.
- **The hold is the deed hold.** An accession holds when its deed is `missing`/`sent` or its restriction is in force on `today`; the same traversal then holds what it produced, the units filed below, and the digital assets representing any of them. `accession-holds.ts` gains `holdReasons(id)` (`deed`, `restriction`) beside `isHeld`, so `effective.ts` and `public-output.ts` still never see an accession, a restriction's kind or its date. The publish check reports `deed_not_signed`, `access_restricted` or both, naming no accession, restriction or date. Links to a restricted record go out exactly as links to a deed-held one (through `isHeld`). New query `restrictionHoldsOn`; `recordsHeldBack` covers both reasons.
- **Freshness.** A register kept past its day still holds a restriction that has since ended (errs on holding). A register given a day later than the real one lets records out early; core can't detect that, so T-034 must build the register at publish time with the real day, and should rebuild published pages when a `closed_until` date passes (a follow-up, not a leak).
- **Rejected:** `today` as a `publicOutput`/`effectivePublishIssues` option (two more places to forget it, and a register would answer differently per call); reading the clock in core (untestable, and the server's UTC day is wrong for Texas evenings); an optional `today` that holds every `closed_until` when left out (silently "closed forever" hides a caller bug); restriction holds as a separate check from deed holds (two traversals that could drift apart); a list of restrictions per accession (the mockup offers one choice; more can come later as a schema change); a "researchers" role check here (reading-room access is the service layer's, T-041).

## D-057 — `packages/db` details: the migrations table, the lock, the sql tag's values, type parsers, test databases (2026-11-23, autopilot T-024)
How T-024 built D-049 and D-050.
- **Environment variables.** `npm run db:migrate` reads `OCULUS_DATABASE_URL` and never prints it (it may hold a password; put passwords in `~/.pgpass` or `PGPASSWORD`). **The migrating role** must own the database or at least hold `CREATE` on the `public` schema: since PostgreSQL 15, `public` is owned by `pg_database_owner` and ordinary roles can no longer create in it, and the bookkeeping table lives in `public`. Tests read `OCULUS_TEST_DATABASE_URL` (D-049).
- **The empty schema.** `0001_migrations_table.sql` creates only `public.oculus_migrations (name text PRIMARY KEY, sha256 text, applied_at timestamptz)`, with checks on the name and hash formats. The runner treats it like every other file: it runs the file and inserts its row in the same transaction, so the table's own shape can change later through migrations. The runner always names it with its schema (`to_regclass('public.oculus_migrations')`, the `SELECT` and the `INSERT`), so a fresh database has nothing applied and no `search_path` can point it at another table.
- **Files.** Every entry in `packages/db/migrations` must be a file named `NNNN_lower_case_name.sql` (anything else, including a README or `.SQL`, is refused rather than skipped), non-empty and valid UTF-8; two files with the same number are refused. Gaps in numbering are allowed. The SHA-256 is of the file's bytes, so `.gitattributes` keeps migrations at LF line endings on every checkout.
- **Refusals,** checked under the lock before anything runs: an applied file missing or renamed (`missing`), edited by even one byte (`edited`), a pending file sorting before the last applied one (`out_of_order`), a server below 15 (`server_too_old`; above 19 only warns). A failing file rolls back completely and later files don't run; the codes are listed below, with `lock_lost` and `transaction_ended`.
- **The lock.** A session-level `pg_advisory_lock(0x6f63756c7573)` ("oculus") on the runner's one connection, held across all files (a transaction-level lock would be released between files). It waits up to `lockTimeoutMs` (default 60 s, through `lock_timeout`, which in a test is shown to cover advisory locks) and then refuses (`lock_timeout`). A second runner that waits finds nothing left to do.
- **One transaction per file, checked.** A file is recorded, or reported as plain `failed`, only when the runner can prove the file never left the runner's own transaction; anything else is `transaction_ended`. The exact rules:
  - **Before the file:** `BEGIN`, then the transaction is given an ID and its start time is read (`pg_catalog.pg_current_xact_id()`, `pg_catalog.now()`), then `SAVEPOINT oculus_migration`. The file runs as one simple-protocol script.
  - **"Still in the runner's transaction"** means all three: the server's last ReadyForQuery said "in a transaction block" (`T`); `pg_catalog.pg_current_xact_id_if_assigned()` equals the ID read before the file (IDs are never reused, so a file that ended the transaction in any way, `PREPARE TRANSACTION` included, can't be in it again, and then no other transaction can have committed in between); and `pg_catalog.pg_xact_status` of that ID is `in progress`. `pg_xact_status` alone is not enough: after `PREPARE TRANSACTION` the ID is still `in progress`, in a prepared transaction.
  - **After a file that succeeded:** the block must still be `T`; then, inside the transaction, the session is reset (`RESET ALL`, `RESET ROLE`, `RESET SESSION AUTHORIZATION`, `DISCARD TEMP`, `DEALLOCATE ALL`) so a file's settings, temporary tables and prepared statements can't touch the runner's own statements; then "still in the runner's transaction" must hold, and no prepared transaction may exist in this database (`pg_catalog.pg_prepared_xacts`) prepared since the transaction began; then the runner must still hold its advisory lock (below). Only then the bookkeeping `INSERT` and `COMMIT`.
  - **After a file that failed:** a statement that fails inside the runner's transaction leaves the block failed (`E`). So if the session is not in a failed block (it is outside any block, or in one that still runs queries), the file ended the runner's transaction: `transaction_ended`. In a failed block the runner runs `ROLLBACK TO SAVEPOINT oculus_migration`, which works only inside the runner's own transaction (unless a file made a savepoint of that name itself, which the next check catches); if it fails, `transaction_ended`. Then "still in the runner's transaction" must hold, else `transaction_ended`. Then the runner rolls back, and `pg_xact_status` of its ID must be `aborted`, else `transaction_ended`. Only a file that passes all of this is reported as `failed`, and nothing of it stays.
  - **So these are `transaction_ended`:** `COMMIT`, `END`, `COMMIT AND CHAIN` and `ROLLBACK` in the file, with or without a new `BEGIN`/`START TRANSACTION` after, whether the file then succeeds or fails (for example `ROLLBACK; CREATE TABLE ra (id int); COMMIT; SELECT * FROM nowhere;`, which leaves `ra` committed). A file that rolls back the runner's transaction and commits nothing of its own is reported the same way, because the runner can't tell it apart from one that did. `PREPARE TRANSACTION` is `transaction_ended`, and the message names every gid prepared in this database since the runner's transaction began and says to resolve it with `COMMIT PREPARED` or `ROLLBACK PREPARED`. A file that releases the runner's savepoint (`RELEASE SAVEPOINT oculus_migration`) and then fails is also reported as `transaction_ended`, on the safe side. If the runner can't ask (the connection is gone), it is `transaction_ended` too. The message always says the file is not recorded and a person must check the database.
  - **After every file** the session is reset again; if that fails after the file committed, the run stops with a message saying the file was applied and recorded.
  - The runner names its table, functions and casts with their schemas (`public.oculus_migrations`, `pg_catalog.*`). Statements that can't run in a transaction (`CREATE INDEX CONCURRENTLY`) are not supported; if one is ever needed, it gets its own decision.
- **A file can't drop the lock.** Session-level advisory locks aren't transactional, so a file calling `pg_advisory_unlock_all()` or `pg_advisory_unlock(<key>)` would let another run in. Before each file's bookkeeping `INSERT`, the runner checks `pg_catalog.pg_locks` for its own granted advisory lock (this backend's `pid`, `classid` and `objid` the key's high and low 32 bits, `objsubid = 1`); if it is gone, the file is rolled back and the run stops (`lock_lost`).
- **Recording failures.** If the bookkeeping `INSERT` fails, the message blames the first migration ("must create public.oculus_migrations") only when the table doesn't exist (SQLSTATE `42P01`); any other cause is reported as itself.
- **The `sql` tag's values.** Strings, finite numbers, bigints, booleans, null, valid Dates, `Uint8Array` (bytea) and arrays of these (up to 6 deep, no holes), copied when the query is made. Refused: `undefined`, NaN and infinities, plain objects (JSON is `${JSON.stringify(v)}::jsonb`), objects with `toPostgres`, functions, symbols, fragments inside arrays, more than 65,535 parameters. Fragments made by `sql` (or `joinSql(fragments, separator)`) are spliced in with their parameters renumbered; a fragment is recognised by a private-field check, not `instanceof`, so a forged object is just a refused value. There is no identifier or raw helper. Two placeholders may not touch (`${a}${b}`, or `joinSql` with an empty separator, would give `$1$2`), and a placeholder may not touch the text around it: an identifier character, digit or `$` just before it (`col${x}`, `$${x}`) or just after it (`${x}0` would read `$10`) is refused when the query is made.
- **Lint.** Outside `packages/db`, importing `pg`, `pg-*`, `pgpass`, `postgres`, `postgres-*` or `@types/pg` is refused, including `import()`, `require()` and `import x = require()`. Outside `packages/db/src/client.ts`, any `.query(` call is refused; `sql(...)`, `sql.call`, `sql.apply` and `sql.bind` are refused everywhere. This covers `.ts`, `.mts`, `.cts`, `.tsx` (all parsed as TypeScript by `eslint.config.js`) and JavaScript files, tested through the real config, and `client["query"](...)`. Lint is a guardrail for mistakes; the run-time checks in `sql.ts` and `client.ts` are the real guard. `client.ts` itself sends only `sql` values, always with the extended protocol (`queryMode: "extended"`; pg would otherwise send a query with no values by the simple protocol, which runs several statements); its two internal exceptions are the runner's whole-file script (simple protocol, from `packages/db/migrations` only) and `createDatabase` / `dropDatabase`, which accept only names matching `^[a-z][a-z0-9_]{0,62}$`. These are not exported from the package.
- **Type parsers,** per connection, never pg's global ones: `int8`, `numeric`, `date`, `timestamp`, `timestamptz`, `interval` and their arrays come back as the server's text. Every session sets `TimeZone=UTC`, `DateStyle=ISO,YMD` and `IntervalStyle=iso_8601`, so that text is the same on every server (`2026-11-23 12:00:00+00`, `P1DT2H`).
- **Test databases.** Each test file creates its own databases (`oculus_test_` + 16 random hex digits, from `template0`, UTF-8) and drops them `WITH (FORCE)` afterwards. Database tests set up inside each test rather than in `beforeAll`, so with no server every test fails on its own instead of being reported as skipped. Cloning a migrated template database waits until migrations take long enough to matter.
- **The gate's throwaway server** (`scripts/test-database.mjs`): `initdb --no-sync --no-locale -E UTF8 -U postgres -A trust`; the server settings go on `pg_ctl -o` (`-h ''` so no TCP, `-k <dir>` with socket permissions `0700`, `-F` for fsync off, `synchronous_commit` and `full_page_writes` off), and the directory path must be shell-safe because pg_ctl hands `-o` to a shell. Nothing is written into the data directory by root. `initdb` and `pg_ctl` get only a fixed `PATH=/usr/bin:/bin` and a C locale, never the caller's environment, and `runuser` is called by its full path. Two commands still use the caller's `PATH`: `pg_config --bindir` (only to find the binaries when `PG_BIN` is not set) and, under uid 0, `id -u postgres` / `id -g postgres` (to chown the directory). The server also gets `max_prepared_transactions=10`, so the runner's `PREPARE TRANSACTION` test runs. `PG_BIN` must hold both `initdb` and `pg_ctl`. The server runs only for the test step. Stopping tries `-m fast`, then `-m immediate`; if it is still running, its directory is left and reported, never deleted under a live server. Gate steps run as async child process groups, so SIGINT, SIGTERM or SIGHUP stop the running step and then the server at once. About 1 second in the sandbox.
- **CI** runs the gate against `postgres:15` and `postgres:19` (19 is published: the official-images library lists `19.0, 19, latest`, read 2026-11-23), `POSTGRES_HOST_AUTH_METHOD: trust`, a `pg_isready` health check, port 5432 on `localhost`, as GitHub's service-container guide shows. A step before the gate sets `max_prepared_transactions = 10` with `ALTER SYSTEM` and restarts the service container (a service container can't be given server options), and checks it took; without it the prepared-transaction test fails rather than skipping. The matrix jobs are `gate-postgres`; a final job named `gate` needs them and passes only if all passed, so a single required check named `gate` keeps working. The images are not pinned to digests: docker-library's repo-info lists them, but no digest could be checked against the registry from the sandbox (Docker Hub was blocked), so pinning waits for a run that can check one.
- **Rejected:** the runner creating its table in code (its shape could then only change in code); `pg_try_advisory_lock` in a loop (busy waiting); pg's global type parsers (they change every `pg` user in the process); timestamps as JavaScript Dates (local-time shifts, lost microseconds); refusing gaps in numbering (no safety gained); skipping unknown files in the migrations directory (a misnamed migration would silently never run); an identifier helper in the tag (no query needs one yet).
